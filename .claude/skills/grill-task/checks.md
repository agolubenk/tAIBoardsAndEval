# Проверки

Каждый пункт — `PASS / FAIL / OPEN / N/A` (N/A — с причиной). Показывать владельцу только FAIL/OPEN и значимое;
полный прогон — в pre-flight перед утверждением.

## Соответствие запросу
- Каждое обязательное требование из запроса отражено (сверка по исходному тексту/карточке, не по памяти).
- Предложения агента и проверяющих отделены от требований владельца.
- Нет несогласованного расширения scope; запреты (N-ID) перенесены и проверяемы в приёмке.

## Внутренняя согласованность
- Нет несовместимых решений; зависимые решения опираются на актуальные (не `superseded`) предпосылки.
- Числа, порядок действий, значения по умолчанию совпадают с формулировками владельца дословно.
- У терминов нет конфликтующих определений.

## Связь с проектом
- Значимые факты имеют источник; непроверенные предположения помечены.
- Не предложено дублирование существующей функции (проверено `rag_query.py --type done_entry|spec`, Serena).
- Учтены контракты и совместимость: `packages/*`, Connect RPC/REST, старые клиенты (web, extension, mobile).
- Не нарушены законы `.claude/rules/*` для затронутых мест (ссылкой на правило, не пересказом).

## Ресурсы (линза «Африка-тест» — канон `.claude/memory/chunks/process/adversarial-review.md`)
- Таблица «Бюджет ресурсов» в спеке заполнена: в каждой строке число с источником (замер, `EXPLAIN`, расчёт,
  `npm run bundle:check`) или «не измерено → Q-ID»; N/A — с причиной. **PASS без числа = FAIL.**
- Нет N+1, `take ≤ 100`, операции > 200 мс и внешние API — через очередь.
- Цена для пользователя: лишние шаги, ожидание, трафик.

## Контрпримеры — только применимые
- нет прав / не тот тариф · данные одной компании видны другой · данных нет, они устарели или некорректны ·
  действие повторено или выполнено одновременно · внешняя зависимость недоступна (hh.ru, Huntflow, Telegram, LLM) ·
  операция завершилась частично · пользователь отменил действие · старый клиент против нового поведения ·
  внешнее действие без HITL.

Каждый найденный риск: условия → действие → сбой → последствие → мера (или Q-ID).

## Проверяемость
- Критерии приёмки описывают наблюдаемое поведение; каждый связан с R/N-ID.
- Нет «удобно», «быстро», «корректно» без числа или определения.
- Проверка не опирается на несуществующие возможности проекта.

## Завершение (pre-flight перед утверждением)
- Блокирующие вопросы закрыты или явно приняты владельцем как отсрочки.
- Адверсариальная проверка проведена на этой версии (x ≥ 3, разные линзы, участники перечислены поимённо),
  возражения разобраны, блок есть в спеке.
- «Бюджет ресурсов» заполнен (см. «Ресурсы»).
- Владелец утверждает конкретную версию; «понятно»/молчание утверждением не считаются.
- Утверждение спеки не подменено разрешением на код, запись на карточку t-boards или в `docs/`.
