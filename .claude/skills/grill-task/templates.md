# Шаблоны

Два файла на задачу: `state.md` (рабочее состояние, переписывается каждый раунд) и `spec.md` (версионируемый
результат). Пустые разделы оставлять с «—», не удалять: пустота тоже информация. Таблицы не плодить по файлам.

## state.md

```markdown
# <task-id> — состояние прожарки

Версия: <n> · Этап: <1–8 из protocol.md> · Обновлено: YYYY-MM-DD
Источники: <запрос / ключ карточки t-boards / документы>
Последняя сверка с кодом: YYYY-MM-DD (<ветка или коммит>)
Согласие на локальное сохранение: <да, путь> · Утверждённая версия спеки: <— | v3 approved-with-deferred>

## Проблема и границы
Пользователь (роль): · Проблема: · Ожидаемый результат: · Входит: · Не входит:

## Проверенные факты
| ID | Факт | Источник | Граница проверки |
|---|---|---|---|

## Требования
| ID | Требование | Источник (запрос / D-ID) | Статус |
|---|---|---|---|

## Запреты и исключения
| ID | Запрет / исключение | Источник |
|---|---|---|

## Решения
| ID | Решение | Формулировка владельца (дословно) | Обоснование | Статус | Зависит от |
|---|---|---|---|---|---|

## Открытые вопросы
| ID | Вопрос | Блокирует | Кто решает | Когда |
|---|---|---|---|---|

## Риски
| Сценарий отказа (условия → действие → сбой) | Последствие | Мера / Q-ID |
|---|---|---|

## Термины
| Термин | Определение | Статус (предложен / согласован) |
|---|---|---|

## История решений
YYYY-MM-DD · D-ID: было → стало · причина

## Следующий шаг
<действие, которое ещё не выполнено>
```

## spec.md

Порядок разделов совпадает с форматом `docs/specs/CLAUDE.md` — при переносе в `docs/specs/<модуль>.md`
спеку не нужно перекраивать.

```markdown
# <Модуль> — <суть задачи>

> **Статус (YYYY-MM-DD):** draft | approved | approved-with-deferred · версия <n> · источник: <карточка/запрос> ·
> состояние: `prototipes/grill/<task-id>/state.md`

## Проблема
Кто, какая боль в HR-процессе, ожидаемый результат, метрика успеха (если есть).

## Пользователи и сценарии
Основные сценарии по ролям; для каждого — R-ID.

## Модель домена
Сущности, статусы и переходы, термины (только согласованные).

## Правила
| ID | Поведение | Источник (D-ID / запрос) |
|---|---|---|
Сквозные требования (`docs/specs/CLAUDE.md` → «Логика») — применимое явно, неприменимое — N/A с причиной.

## Бюджет ресурсов
| Ось | Значение | Источник (замер / расчёт / «не измерено → Q-ID») |
|---|---|---|
| Запросы к БД на действие, `take` | | |
| Операции > 200 мс → очередь | | |
| Вызовы и токены LLM, квоты внешних API на действие | | |
| Запросы на экран · ответ, КБ gzip | | |
| JS на критическом пути, КБ gzip | | |
| Слабый Android / 3G: время до результата | | |
Строка без числа и без Q-ID — не заполнена; неприменимая — N/A с причиной.

## Ошибки, крайние случаи и запреты
N-ID и сценарии отказа (условия → действие → ожидаемое поведение).

## Приёмка
| AC-ID | Связь (R/N) | Дано | Когда | Тогда (наблюдаемо) |
|---|---|---|---|---|

## Не входит
Явные исключения из scope.

## Открытые вопросы и принятые отсрочки
Q-ID, кто решает, что блокируют; отсрочки — с формулировкой владельца.

## Инженерные ограничения
Только подтверждённые источником (`путь:символ`, правило, ADR).

## Предложения вне scope
Идеи агента и проверяющих, не утверждённые владельцем.

## Связи
Карточка t-boards · план фазы · ADR · затронутые приложения и контракты.

## Адверсариальная проверка
x участников (линзы) → главные возражения → решение, отклонённые альтернативы, цифры.
```
