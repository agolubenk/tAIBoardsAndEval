## Хард-стопы (не обсуждаются без явного ОК владельца)

1. **Сырая идея** (`halfBaked`, бывший `Half-baked idea = true`) — карточка не берётся в работу. Аренду на неё сервер не
   выдаёт (403 `half_baked`). Прожарка по просьбе владельца — обсуждение, а не взятие в работу. Снимает флаг только
   владелец в UI.
2. **Порядок:** открытые «Ошибки» (по severity: critical → high → medium → low) обгоняют «Задачи».
3. **Статус и обсуждение — на карточке, не в чате.** Смена статуса — `update_task_status` под своей арендой
   (`forest_acquire_lease` → `fencingToken`); переход в ревью — со ссылкой на PR или коммит (`link`), что сделано — в
   `note`. Уточнения и решения «на доработку» — `create_task_comment`. Запись отклонена по `fencingToken` (аренда
   истекла или перехвачена) — молча аренду не перевыдавать: `forest_list_work_state`, кто держит карточку, и доложить.
4. **Удаления нет:** агенту сервер его не даёт. Дубликат — `[Дубликат — см. <ключ>]` в заголовке и закрывающий статус
   (по «да» владельца, п. 6).
5. **Постановка читается из карточки, не из git и не из Notion.** Карточка без описания — её связанная страница Notion
   (`notionPageId`) читается как история, а не как канон. Нет ни описания, ни `notionPageId` — постановки нет: спросить
   владельца, не додумывать. Вывод инструмента обрезан или инструмент недоступен — сказать об этом, не угадывать.
6. **Финальный статус — только по «да» владельца.** Агент сам доводит карточку максимум до ревью. Закрытие и смена
   приоритета — `forest_request_approval` (`close_task` / `set_priority`); «да» даёт владелец в UI t-boards, своё «да»
   агента сервер отклоняет. Одобренный запрос передаётся в `approvalId` и тратится на этой записи.

## Пайплайн завершения

Колонки перенесены из Notion вместе с названиями (`list_project_columns` — их slug):
**Задачи** — `задача от пользователя` → `прожаренные явные задачи` → `в работе` → `на ревью` → `выполненные` →
`завершённые`; **Ошибки** — `открыто` → `в работе` → `на ревью` → `закрыто`.

- Агент сам двигает карточку: взял — `в работе`; реализация готова и узкий гейт DoD прошёл — `на ревью` со ссылкой
  на PR и отчётом DoD в `note`.
- **Дальше — стоп.** Закрытие (`выполненные`/`завершённые`, `закрыто`) — только через одобренный `close_task`. Код уже
  влит, а «да» нет — карточка остаётся на ревью.
- Задачи: `выполненные` — владелец принял результат, а запись в git (шаг 1 закрытия) ещё не сделана; `завершённые` —
  оба шага закрытия выполнены. Обычно запись делается в том же ходе, и карточка сразу идёт в `завершённые`;
  `выполненные` нужен, когда запись откладывается.
- Точечная механика без видимого эффекта (опечатка, формат, lint-fix при зелёном CI) закрывается сразу только по
  прямому «закрой» владельца в этом же ходе.

## Пачки записей и сбой коннектора

- Много записей подряд — сначала тексты всех записей в файл, затем применение с журналом «ключ → время»: повторный
  запуск пропускает выполненное, комментарий не уходит дважды.
- Закрывающую запись перед применением сверить с `get_task`: карточка уже в целевом статусе — отметить в журнале и
  идти дальше. `approvalId` уже потрачен — сверить статус, новый запрос не создавать: владелец не должен одобрять
  дважды.
- t-boards недоступен (хаб, туннель, лимит частоты) — тексты в файл отложенных записей, применить пачкой, когда доступ
  вернётся; в отчёте — список неприменённого. В Notion вместо t-boards не писать.

## Закрытие пункта — оба шага обязательны

1. **Git:** запись в `docs/plans/done/<модуль>.md`, раздел «Журнал» (формат — `docs/plans/DONE.md`): дата · что
   сделано · коммит · ключ карточки t-boards; закрытая ошибка — с тегом `#bug`.
2. **t-boards:** закрывающий статус по одобренному `close_task`.
