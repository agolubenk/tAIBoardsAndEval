# Адверсариальная проверка решений — канон (≥ 3 участника)

Обязательна для **каждого специалиста** любой роли. Цель — не согласовать, а сломать решение до пользователя и
выбрать **лучший инженерный вариант**, который следует продуктовой мысли и экономит ресурс на всех уровнях:
сервер → сеть → устройство и браузер пользователя. Карточки ролей (`CLAUDE.md`) задают свои линзы; здесь — общее.

## Сколько участников (x)

| Ситуация | x |
|---|---|
| Механика без выбора: опечатка, форматирование, перенос/ссылки по утверждённому плану, правка по уже принятому ревью | 0 (в отчёте — «проверка не требуется: механика») |
| **Любое решение или предложение:** подход, фича, контракт/схема/UX, план, рефакторинг с выбором | **3 — минимум** |
| + auth/PII/биллинг/безопасность, миграция данных, прод-инфраструктура, необратимое, ≥ 2 приложения | 4–5 |
| Уровень ADR: граница сервиса, смена технологии, массовая миграция, всё для всех пользователей | 6+ |

Участник добавляется, только если приносит **новую линзу**; повтор линзы — злоупотребление. Срезать ниже трёх для
решения нельзя. Автор не проверяет сам себя; участники независимы (отдельный контекст, без подсказки «как надо»).

## Базовые линзы (всегда три)

1. **Корректность и отказы** — границы (пусто/null/10× данных), конкурентность и повторная доставка, частичные
   отказы внешних систем, обратная совместимость контрактов, откат.
2. **Экономия ресурсов («Африка-тест»)** — сервер: запросы к БД (N+1, индексы, `take ≤ 100`), CPU/RAM, очереди,
   квоты внешних API, токены LLM, хранилище; сеть: число запросов на экран, размер ответа, кэш (HTTP, React Query),
   компрессия; клиент: JS на критическом пути (потолок entry — 260 КиБ gzip = 266 240 Б, `bundle-budget.json`; потолок, не цель),
   рендеры, память и батарея. Профиль пользователя: 3G/медленный 4G (≈ 0,4–1,6 Мбит/с, RTT 300–600 мс, платный
   трафик), Android на 2–3 ГБ RAM, старый WebView. **Измерять, не угадывать:** `npm run bundle:check`, DevTools
   «Slow 3G + 4× CPU», `EXPLAIN`, счёт запросов в логе, размер ответа.
3. **Продукт и простота** — следует ли продуктовой мысли и решает ли задачу пользователя; есть ли вариант проще
   или дешевле; что сознательно НЕ делаем; не создаёт ли решение работу пользователю (лишние шаги, ожидание, трафик).

Доп. линзы по сложности: безопасность и PII · данные и миграции · эксплуатация и наблюдаемость · доступность и
i18n · домен HR и юридика · стоимость владения (TCO).

## Как провести

- **Участники:** субагенты с явной линзой (`code-reviewer` — корректность, `performance-expert` — ресурсы,
  `architecture-expert` — альтернативы и простота, `security-expert`, `telegram-expert`, `agent-engineer`;
  иначе `general-purpose` с промптом линзы). Аналитические агенты работают только на чтение (+ Serena): первый ход
  ~25K токенов против ~65K со всеми MCP-инструментами; для дешёвой базовой линзы — `model: sonnet` в вызове.
  Для карточек борда — роли ИИ-консилиума (critic/adversary/arbiter,
  `infra/ai-council`); в Continue — лестница рецензентов `.continue/rules/06-adversarial-review.md`.
- **Каждый участник** получает материал (план или дифф, цель, приёмку) и одну линзу; возвращает возражения с
  доказательством (`файл:строка`, команда, расчёт) или проверенное «не сломано по осям …». «Всё хорошо» без
  протокола — не проверка.
- **Синтез делает автор:** по каждому возражению — принять, отклонить с доказательством или измерить. Побеждает
  вариант, лучший по совокупности линз, а не самый «правильный» по одной.

### Кто проверяет по умолчанию (решение владельца 30.10, `d-review-participants` → `council-default`)

- **По умолчанию — линзы консилиума GLM** (`infra/ai-council/glm_pr_review.py <pr> <out> glm-5 <lenses.json>`), одна
  линза — один участник. Запуск без отдельного «да» (`CLAUDE.local.md`). Повторы — через ротацию и в лимитах окна
  (`council_cloud_budget` показывает текущие), без немедленного повтора после 429.
- **Сложный случай** — поверх линз GLM агенты Claude без отдельного «да», **не больше 2 на PR суммарно** по всем
  критериям. Больше 2 — только по «да» владельца с ценой. Если у сессии есть локальное правило команды строже этого,
  действует правило команды.
  - **Видно до запуска** — Claude стартует параллельно с GLM, каждый агент со своей новой линзой (безопасность,
    эксплуатация, данные), не повтором линзы GLM:
    1. меняется путь поставки: `infra/scripts/prod/**`, `infra/docker/**`, `infra/nginx/**`, `.github/workflows/**`.
       Основание — 29.10 агенты Claude нашли на деплой-скриптах 2 ошибки, которые пропустили линзы GLM;
    2. auth, личные данные, миграции;
    3. ≥ 2 приложений, или несгенерированный дифф больше 144 тыс. символов — больше 6 частей по 24 000 (строка «План:»
       печатается `glm_pr_review.py` до первого вызова модели);
    4. хотфикс P0/critical — 1 агент Claude.
  - **После GLM** — 1 агент Claude как арбитр одной линзы, а не новый участник:
    5. линзы разошлись в вердикте и у провалившей есть находка major или critical — Claude проверяет провалившую;
       находка critical — линзу, которая её нашла; `not_passed` на коде, который деплоится (любой файл, кроме `.md`
       и dev-ai), — эту линзу.

  Не сложный — если не выполнен ни один критерий выше: обычно документы, dev-ai, тесты. Время GLM-5 на PR по
  замерам 29.10 — 7,5–22 мин.
- **Другие модели.** Решение владельца — «GLM + OpenRouter по умолчанию». OpenRouter и Gemini приостановлены до
  проверки модели: 3 PR с известными находками, сравнение с GLM. Пул `free`/`auto` шлюза на #413 30.10 не дал ни одного
  ответа: рассуждающие модели съели лимит ответа, gemma-4-31b получила 429. Как подключать дальше — решение
  `d-review-openrouter`.
- **Ответ не той модели — «нет данных»**, как упавший участник (раздел ниже). Шлюз может подменить модель (ротация,
  локальный фолбэк), а отчёт ревью пишет запрошенное имя. Пока это не исправлено (карточка «Ошибки» 30.10), один раз
  на прогон сверяй `infra/llm-gateway/.state/requests.jsonl` за время прогона: `model` ≠ `requested` или
  `fallback: true` — линза не засчитана. `glm-5` идёт к GLM напрямую, мимо шлюза: записей за прогон нет — это норма.
  Не больше 2 попыток на линзу. Засчитанных линз меньше 3 — вердикт не выносится, вопрос владельцу.
- **Качество:** в блоке результата — кто нашёл каждую принятую находку (GLM-линза или Claude). На 10-м PR с таким
  блоком — пункт `d-` владельцу с таблицей «кто что нашёл» и предложением по критериям сложного случая.

### Перед запуском и после

- До запуска — таблица «факторы риска → x» и «участник → базовая линза». Не покрыта базовая линза или x ниже
  таблицы — участников не запускать.
- Вердикт засчитывается, только если участник вернул явную строку VERDICT. Упавший участник — «нет данных», а не
  «нет находок». Перед решением — подсчёт: вернулись, упали, нет. Вернулось меньше x — перезапусти недостающие
  линзы, а не иди дальше.
- Хотя бы один участник получает путь к реальным данным об исходах (только чтение) и цитирует примеры. Правка
  автоматического правила решений — офлайн-прогон по сохранённым решениям: матрица до/после и инвариант
  монотонности, до слова «готово».
- Расхождение двух лимитов — сначала единицы: оба в байты (KiB ≠ kB), цитировать сырое значение из конфига.
- Цена участника — измеренная, не плановая: lens-агент на изменение одного приложения ≈ 150–250 тыс. токенов, на
  кросс-приложенческое — около 320 тыс. Агенту — список файлов для проверки; владельцу перед запуском — цифры
  прошлых прогонов.
