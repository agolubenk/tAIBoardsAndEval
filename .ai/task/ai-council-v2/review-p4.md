## Находки

**Находка #1 — `Api.open_session()`: TOCTOU-гонка позволяет ДВЕ одновременно открытые сессии (CONCURRENCY, блокирует)**

- **Severity:** HIGH
- **File:Line:** `infra/ai-council/gateway.py:1014-1022` (`Api.open_session()`);
  корневая причина — `infra/ai-council/store.py:371-374` (`open_session()`
  докстрингом сам заявляет: «не закрывает предыдущую открытую сама — решает
  вызывающий»); отсутствие защиты на уровне схемы —
  `infra/ai-council/schema.sql:312-322` (`sessions.status` без `UNIQUE`/частичного
  индекса, гарантирующего не больше одной строки `status='open'`).
- **Why:** `open_session()` в `gateway.py` — check-then-act из ТРЁХ отдельных
  вызовов store (`get_open_session()` SELECT → опционально
  `_close_and_summarize()` → `store.open_session()` INSERT), и НИ ОДИН из них не
  обёрнут в общий `BEGIN IMMEDIATE` вокруг всей последовательности — в отличие от
  каждого низкоуровневого примитива, который сам по себе честно атомарен
  (`close_session_if_open`/`add_session_run_if_open`, оба — `store.py:406`/`444`,
  `self.conn.execute("BEGIN IMMEDIATE")` до чтения и до записи). `gateway.py` —
  `ThreadingHTTPServer` (по потоку на запрос, `gateway.py:1837`), и
  `Api._store()` открывает НОВОЕ sqlite3-соединение на каждый вызов — то есть это
  гонка между двумя РАЗНЫМИ соединениями/потоками, не иллюзия GIL. Два запроса,
  прошедшие `get_open_session()` до того, как любой из них успел вызвать
  `store.open_session()` (INSERT), оба увидят «нет открытой» и оба вставят новую
  строку `status='open'` — план явно требует «активная сессия одна: открытие
  новой при живой открытой — авто-закрытие прежней», это условие нарушается
  напрямую.
- **Repro (воспроизведено дважды: один раз до компакции этого ревью, второй раз —
  свежо, прямо в рамках финального прохода, см. «Проверено вживую» выше):**
  ```python
  import json, threading, urllib.request
  base = "http://127.0.0.1:8790"
  def post(path, payload):
      req = urllib.request.Request(base+path, data=json.dumps(payload).encode(),
                                    method="POST", headers={"Content-Type":"application/json"})
      with urllib.request.urlopen(req, timeout=10) as r: return json.loads(r.read())
  barrier = threading.Barrier(2); results = [None, None]
  def worker(i, title):
      barrier.wait(); results[i] = post("/api/sessions", {"title": title})
  t1 = threading.Thread(target=worker, args=(0, "A")); t2 = threading.Thread(target=worker, args=(1, "B"))
  t1.start(); t2.start(); t1.join(); t2.join()
  print(results)   # обе -> {"ok": true, ..., "status": "open", "closed_prior": null}
  ```
  Наблюдалось: `sess_db5dbff6ba7d`/`sess_aaf71eda9538`, идентичный `opened_at`,
  оба `status:"open"`, оба `closed_prior:null` (ни один не увидел другого).
  Последствие: «проигравшая» дублирующаяся открытая сессия становится вечным
  зомби — `get_open_session()`/`_auto_close_idle()` оба используют
  `ORDER BY opened_at DESC LIMIT 1` и видят только ОДНУ (последнюю по времени)
  из двух `open`-строк; вторая никогда не попадёт ни в idle-автозакрытие, ни в
  `session_context_block()`, ни в явное закрытие через UI (которое всегда бьёт
  по «текущей», то есть по той же самой последней) — то есть механизма
  самоизлечения нет вовсе, зомби-сессия остаётся `open` до прямого SQL-вмешательства.
- **Fix:** обернуть всю последовательность `Api.open_session()` в один
  `BEGIN IMMEDIATE`-блок на уровне store (например, добавить
  `store.open_session_exclusive(title) -> tuple[dict, dict | None]`, которая сама
  внутри одной транзакции делает SELECT текущей открытой → закрывает её (сохраняя
  in-place логику `close_session_if_open`) → вставляет новую и возвращает обе), ИЛИ
  как более простой fix прямо на схеме — частичный уникальный индекс
  `CREATE UNIQUE INDEX sessions_one_open ON sessions(status) WHERE status='open'`,
  который сделает вторую конкурентную INSERT физически невозможной (SQLite
  вернёт `IntegrityError`, который `Api.open_session()` тогда обязан поймать и
  превратить в retry/409, а не в 500).

**Находка #2 — Headroom `/v1/compress` не существует в рантайме; сжатие для MCP-инструментов функционально мёртво, и собственный комментарий кода фактически неверен (FUNCTIONAL / STALE-COMMENT)**

- **Severity:** MEDIUM
- **File:Line:** `infra/ai-council/mcp_server.py:96-107` (комментарий, заявляющий
  «/v1/compress в этом окружении отдаёт 401 без Authorization-заголовка
  (проверено вживую 2026-08-19)») и `mcp_server.py:131-149` (`_maybe_compress()`).
- **Why:** реальный, живой Headroom v0.34.0 на `:8787` отдаёт **404 Not Found**
