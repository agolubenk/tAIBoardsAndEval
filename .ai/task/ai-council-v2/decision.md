# Решения владельца — AI Council v2 (2026-08-16)

Четыре развилки из plan.md закрыты владельцем дословно; ниже — решения и их
следствия в плане. План переработан под них и готов к реализации P0→P4.

## A — локальный черновик

Форма на главной создаёт карточку `db='draft'` в council.db. В Notion не
пишем вовсе; инвариант «шлюз в Notion не пишет» сохранён. Перенос черновика
в Notion — отдельное явное действие через emit-механику с apply-флагом,
в v1 не обязательно.

Следствия: P0 — cards.linked_card_ids; P2 — POST /api/tasks + черновики в
вкладке «Карточки»; emit/planner пропускают draft.

## B — сессия = рабочая сессия владельца (от запуска до остановки)

Не цепочка прогонов карточки (моя рекомендация отклонена): границы задаёт UI —
кнопки «Начать/Завершить сессию» + автозакрытие по простою (idle_close_hours).
Контекст принадлежит СЕССИИ: за сессию сколько угодно карточек; свёртка
генерируется ОДИН раз на закрытии (S-модель extractor, локально); в новой
сессии summary последней закрытой идёт в pinned капсулы.

Следствия: P0 — sessions/session_runs/session_contexts; P4 — жизненный цикл
открытие→прогоны→закрытие; corpus kind='session' для дальних сессий;
ленивое закрытие забытой сессии.

## C — новый MCP для других целей; хранилище исключительно консилиумное; встройка Headroom

Не интеграция serena/headroom внутрь retrieval. Новый `mcp_server.py` (stdio
JSON-RPC) читает ТОЛЬКО council.db/corpus/graph.json и служит внешним агентам
(Continue, Claude Code). Встройка Headroom — в самом сервере: длинные ответы
инструментов сжимаются через Headroom-прокси, при недоступности — сырой ответ
с пометкой uncompressed=true (fail-safe).

Следствия: P4 — 4 инструмента (knowledge_search, session_context, card_runs,
graph_neighbors); вынос graph_index.py из gateway; [sources.mcp] council=true.

## D — LOD по сообществам + ленивая догрузка области графа

Да, LOD (свёртка по сообществам для лимитов >2500 и «все»), плюс вариант
владельца «область графа можно подтянуть с задержкой»: тяжёлые срезы
подгружаются лениво при клике/зуме (drill-down /api/graph/community/<id>),
скелет суперузлов — сразу.

Следствия: P3 — шкала 150…25000/все; серверная агрегация сообществ;
ленивый drill-down; prisma-экстрактор для связей моделей БД.

## Почему не принято альтернативное (зафиксировано, чтобы не пересуживать)

- B-цепочка прогонов: отклонена владельцем; технически дешевле, но контекст
  сессии шире контекста карточки — владелец хочет наследовать именно рабочее
  состояние, а не историю одной задачи.
- C-интеграция serena/headroom в retrieval: дороже (LSP-прогрев), не является
  «хранением контекста сессий».
