### Адверсариальное ревью — 1-й проход: CHANGES_REQUESTED

Независимый `code-reviewer` (см. `review-p2.md`) нашёл 6 находок, 2 блокирующих:

1. **HIGH, блокирующая** — TOCTOU-гонка в анти-спам-проверке `create_task`:
   `SELECT`-проверка дубля и `INSERT` черновика+прогона не были в одной
   транзакции (в отличие от `claim_run()` в `store.py`, который берёт
   `BEGIN IMMEDIATE`). Воспроизведена живым тестом на двух потоках — оба
   прохода создавали отдельные черновики. Фикс: `create_task` теперь
   оборачивает анти-спам-проверку + резолв упоминаний + запись + `enqueue` в
   явный `BEGIN IMMEDIATE`/`COMMIT`/`ROLLBACK` (тот же паттерн, что у
   `claim_run()`), а не в `UNIQUE INDEX` — индекс на `(db, content_hash)`
   поменял бы семантику с «отклонить повтор в течение 10с» на «отклонить
   идентичный текст навсегда» (записи не удаляются), что шире, чем требует план.
2. **MEDIUM** — `%`/`_` в тексте упоминания — это LIKE-wildcard'ы SQLite, не
   литералы (ложная неоднозначность на заголовках с `_`). Фикс: `_escape_like()`
   + `LIKE ? ESCAPE '\\'`.
3. **MEDIUM, блокирующая (латентная бомба)** — `linked_evidence()`/`build()`
   в `retrieval.py` парсили `linked_card_ids` через `try/except ValueError`
   без проверки, что результат — список; валидный-но-не-список JSON (`null`,
   `{}`) не бросает `ValueError`, но падает на `[:5]`/итерации. Сейчас
   недостижимо (единственный писатель — `create_task` — всегда пишет список),
   но нарушает контракт модуля «источник молча выключается». Фикс: общий
   `Retriever._linked_ids()` с `except (ValueError, TypeError)` +
   `isinstance(parsed, list)`, дублирующий фрагмент в `build()` убран.
4. **LOW/MEDIUM** — снятие чипа не убирало вставленный `@[Title] ` токен из
   текста — текст и структурные связи расходились. Фикс: `renderHomeChips()`
   при удалении чипа убирает и первое совпадение токена из `#h-body`;
   поправлена и переоценивающая формулировка в docstring/`TAB_DOC["home"]`
   (только выбор из дропдауна становится связью, не произвольный `@[...]`-текст).
5. **LOW** — разметка радио-выбора профиля дублировалась 3 раза (`openSeries`,
   карточка, `renderHome`) с чуть разным текстом предупреждения об облаке.
   Фикс: вынесено в общий `renderProfileRadios(models, radioName,
   selectedName, warnText)`.
6. **LOW** — тест на несуществующее упоминание и анти-спам не проверял
   текст ошибки/состояние БД, а анти-спам-тест звал `create_task`
   исключительно последовательно — структурно не мог поймать гонку из
   находки №1. Фикс: усилены оба ассерта + добавлен настоящий конкурентный

## P3 — Ф3: граф (Prisma-слой + фильтр связей + LOD-сообщества) (готово, 2026-08-20) — TAI-3

### §3а — Prisma-слой в графе

- `graph_build.py` — парсер DSL `schema.prisma` (`model X {...}`/`enum X {...}`),
  узлы `prisma:<Label>` (kind `prisma_model`/`prisma_enum`), рёбра `prisma_relation`
  между моделями по FK-полям + рёбра модель→код через `git grep` (один батч-вызов
  с N `-e <ModelName>` вместо N сабпроцессов) — находит места фактического
  использования (`prisma.model.*`/camelCase) в бэкенде.
- Реальная схема: 358 моделей/enum → 439 узлов, 359 code-reference рёбер, всё за
  ~56 секунд на полном прогоне.

### §3б — фильтр по типу связи (`GET /api/graph?rel=calls,imports,...`)

- `_filter_adj(adj, rels)` — режет рёбра ДО пересчёта связного среза (`_graph_slice`/
  `_graph_communities`), не после: иначе связность могла подтвердиться рёбрами,
  которые фильтр должен был исключить.
- `available_relations` (список всех типов связей в графе) отдаётся в ответе
  `/api/graph` **и** `/api/graph/community/<id>` — изначально забыл добавить во
  второй эндпоинт, из-за чего чекбоксы фильтра пропадали при drill-down в
  сообщество (сервер продолжал принимать `rel=`, просто UI не мог его выставить);
  найдено живым браузерным тестом, исправлено до ревью.
- UI — чекбокс-ряд из `d.available_relations`, `graphPrefs.rel` в localStorage.

### §3в — бюджет узлов + LOD-агрегация по сообществам

- Шкала бюджета `<select>`: 150…25000 + «все». ≤2500 — обычный связный срез
  (`_graph_slice`, cap рёбер поднят 8000→25000 по плану). >2500 или «все» —
  автопереключение на `level=communities`: сервер сворачивает узлы графа в
  супер-узлы по сообществу (`_graph_communities`), рёбра — веса межобщинных связей;
  «все» никогда не отдаёт браузеру сырые узлы одним ответом.
- Клик по супер-узлу → ленивая догрузка `GET /api/graph/community/<id>?limit=...`
  (`graph_community()`) — детальный связный срез ТОЛЬКО внутри этого сообщества
  (`_community_subgraph` + тот же `_graph_slice`), не весь граф.
- Оба лимита жёстко клампятся на сервере независимо от клиентского ввода:
  `files`/`symbols` → `[50, 2500]`, `communities`-drill → `[50, 25000]`;
  `level=communities` игнорирует `limit` вовсе (число супер-узлов = число
  сообществ, естественно ограничено).
- `community:<id>` содержит `:` — путь `/api/graph/community/community%3A1`
  должен были декодироваться сервером; `unquote` не был подключён изначально
  (ни один существующий route в этом файле раньше не нуждался в декодировании
  path-сегмента) → drill-down молча возвращал `available: false`. Найдено живым
  HTTP-тестом (не unit-тестом — изолированные smoke-тесты вызывали
  `api.graph_community()` напрямую в Python, минуя роутинг), исправлено импортом
  `unquote` и применением к сегменту пути в `do_GET`.
