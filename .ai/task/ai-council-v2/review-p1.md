### 1. Границы — детали

Эмпирическая проверка (`python3` REPL против временной SQLite БД, см. команды в
транскрипте ревью — не входит в диф):

```
empty corpus (no docs)      -> {'kinds': [], 'hits': [], 'page': 1, 'page_size': 50, 'total': 0, 'pages': 1, 'mode': 'catalog'}
page=0                       -> клэмпится до 1
page=-5                      -> клэмпится до 1
page_size=0                  -> 0 falsy → `page_size or 50` → 50 (не 1; не баг — 50 безопасный дефолт, не OOM)
page_size=-10                 -> клэмпится до 1
page_size=999999              -> клэмпится до 100 (потолок соблюдён, «take > 100» не нарушен)
kind, не matching ничего      -> total=0, hits=[], pages=1 (не ошибка)
page далеко за пределами (99999 при pages=1) -> hits=[], total эхом от факта, page эхом от запроса — не ошибка, 200 OK
```

Малформед non-numeric `page`/`page_size` в query-string (`?page=abc`) — `int("abc")`
кидает `ValueError` **до** входа в `Api.knowledge()` (в `do_GET`, gateway.py:1517-1518),
но перехватывается внешним `except Exception` в `do_GET` (gateway.py:1541-1544) →
`500 {"error": "ValueError: ..."}`. Не крашит процесс (`ThreadingHTTPServer`,
исключение съедено внутри потока одного запроса), не течёт PII. Тот же паттерн уже
существовал до дифа для `/api/graph`, `/api/runs` и т.д. (`int(one("limit", …))`
без try/except) — не новый риск, не блокирует.

**Вывод:** не сломано ни по одной из проверенных границ.

### 2. Конкурентность — детали

- `Api.__init__(self, cfg, db_path=None)` — аддитивный параметр, дефолт сохраняет
  старое поведение (`Store()` без пути). `serve()` (gateway.py:1636) создаёт
  `Handler.api = Api(cfg)` — однопозиционный вызов, `db_path` не передаётся →
  прод-путь физически не может указать на другую БД. Подтверждено чтением кода и
  `git diff 76627f764` (в этой строке дифа нет вообще — `serve()` не тронут).
- Каждый вызов `Api._store()` создаёт новое `sqlite3`-соединение (паттерн не менян
  этим дифом) — конкурентные `/api/knowledge`-запросы от разных потоков
  `ThreadingHTTPServer` не делят состояние, гонки на уровне соединения исключены тем
  же механизмом, что и раньше.

**Вывод:** не сломано — новый параметр не создаёт пути, которым прод мог бы
случайно попасть на нештатную БД.

### 3. Обратная совместимость — Находка C (см. «Находки»)

`git diff 76627f764 -- infra/ai-council/gateway.py` (последний known-good) показывает
**ровно** два места изменений: `Api.__init__`/`_store()` (db_path) и
`Api.knowledge()` + его единственный вызов в `do_GET`. Всё остальное — `do_POST`,
`serve()`, `main()`, `/api/events`, `/api/stream` (включая heartbeat 25с),
`/api/verdict`, `/api/enqueue` и т.д. — **побайтово идентично** last-known-good.
Утверждение задачи «git diff 76627f764 показывает ТОЛЬКО целевой диф knowledge()»
подтверждено, не опровергнуто.

Внутри самого целевого дифа, однако, сигнатура `knowledge()` сменилась с
`(query, limit)` на `(query, kind, page, page_size, limit)` — `limit` не удалён,
а сдвинут на 5-ю позицию и **не используется в теле метода ни разу** (было:
`min(limit, 100)` в SQL, стало: `page_size`/`offset`). Единственный HTTP-вызов
(`do_GET`, gateway.py:1516-1518) обновлён на новый порядок и не передаёт `limit`
вовсе. Единственный другой источник в репозитории (`selftest.py`) зовёт метод
только именованными аргументами. `grep -rln "api\.knowledge("` по всему репо —
только эти два файла, других потребителей нет.

**Контрпример (латентный, не triggered сейчас):** гипотетический будущий вызов
`api.knowledge(q, 40)` (старый стиль «query, limit позиционно») в новой сигнатуре
свяжет `40` не с `limit`, а с `kind` (2-й позиционный параметр). `kind=40` (int) →
`kind_filter = " AND kind = ?"`, `kind_params=(40,)` → сравнение INTEGER `40` со
столбцом `kind` (TEXT) в SQLite не совпадёт ни с одной строкой → `total=0, hits=[]`
**без исключения, без ошибки** — тихий пустой результат вместо «выведи топ-40».
Это ровно паттерн «backward-incompatible contract change» из протокола атаки, просто
пока без активного потребителя.

### 4. Безопасность — детали

- `serve()` host-check (gateway.py:1629-1634) — `if host not in ("127.0.0.1",
  "localhost", "::1"): return 1` — присутствует, не тронут дифом (подтверждено:
  вне зоны диффа против `76627f764`).
- `kind_filter`/`kind_params` (gateway.py:864-865, 891, 897): `kind_filter` — ВСЕГДА
  один из двух хардкод-литералов (`""` или `" AND kind = ?"`), выбор определяется
  **truthiness** значения `kind`, а не его содержимым. Само значение `kind`
  (пришедшее от пользователя через `?kind=`) идёт исключительно как bound-параметр
  через `?`-плейсхолдер (`store.q(...)` использует `sqlite3` parameterized query,
  не f-string). `.replace("kind", "m.kind")` применяется к строке-шаблону
  (`kind_filter`), а не к пользовательскому вводу — детерминированная замена внутри
  двух фиксированных литералов, не инъекция. **Не SQL-инъекция** — попытка
  контрпримера `?kind=1 OR 1=1--` не работает: значение уходит в bound-параметр,
  сравнивается как строка `"1 OR 1=1--"` с колонкой `kind`, не как SQL.
- Секреты/PII в логах: `do_GET`/`do_POST` логируют `f"! {route}: {type(exc).__name__}: {exc}"`
  при исключении — `route` это только путь без query string (`urlparse(self.path).path`),
  `exc` — текст исключения (SQLite/ValueError), не тело запроса и не query-параметры
  целиком. Не новый риск, паттерн не тронут этим дифом.

**Вывод:** не сломано — гипотеза инъекции опровергнута параметризацией; loopback-guard
цел.

**Вывод:** неприменимо по большей части набора; единственный применимый пункт

## Находки

**A · MEDIUM · `infra/ai-council/selftest.py:731-736`**
**Pattern:** дублирующийся `if __name__ == "__main__": sys.exit(main())` — блок
целиком продублирован дважды подряд в хвосте файла.
**Why:** функционально безвреден (`sys.exit()` в первом блоке поднимает
`SystemExit` до того, как второй блок мог бы выполниться), но это ровно тот же
класс артефакта редактирующего инструмента (потерянный/задвоенный хвост файла),
который стал причиной исходной порчи `gateway.py` и `ui/index.html`, описанной в
задаче. Прямо противоречит заявлению задачи о «precise string-replace,
verified via git diff --stat». Пятно на доверии к остальным «verified»-заявлениям
этого же патч-сета, даже если конкретно здесь impact нулевой.
**Fix:** удалить строки 734-736 (второй `if __name__ == "__main__": sys.exit(main())`
блок), оставить только первый.

**B · LOW · `infra/ai-council/selftest.py:393,417-431,717,719`**
**Pattern:** остаточные артефакты правки — (1) 12 пустых строк подряд между
`api = gw.Api(cfg, db_path=str(db))` (строка 417) и следующим комментарием (строка
431) внутри `test_knowledge`; (2) заголовок-комментарий `# ── 7. планировщик …`
(строка 393) стоит перед `def test_knowledge`, хотя относится к секции
`test_planner`, которая физически идёт ниже; (3) в `main()` вывод содержит номер
секции «8.» дважды подряд («8. знания…», строка 717, и «8. обучение…», строка 719)
вместо «8.» и «9.».
**Why:** не функциональный баг (тесты по-прежнему запускаются и проходят — 84/86
подтверждено прогоном), но тот же класс небрежности правки, что и Находка A —
сигнал, что список изменённых файлов в этом фикс-патче стоит перечитать целиком,
а не доверять построчно заявлению «диф точечный».
**Fix:** убрать лишние пустые строки, передвинуть/исправить комментарий-заголовок
секции, перенумеровать печатаемые заголовки в `main()` (7→8→9 без дублей).

**C · MEDIUM · `infra/ai-council/gateway.py:853-854`**
**Pattern:** «тихая» смена контракта — неиспользуемый (dead) параметр `limit`
на новой 5-й позиции после смены порядка аргументов `Api.knowledge()`.
**Why:** старая сигнатура `knowledge(query, limit)` вызывалась бы позиционно как
`knowledge(q, 40)`. Новая сигнатура `knowledge(query, kind, page, page_size,
limit)` без изменений в вызывающем коде тихо перетолковала бы второй позиционный
аргумент как `kind=40` вместо `limit=40` — SQLite сравнит INTEGER `40` со
столбцом TEXT `kind`, ничего не совпадёт, метод вернёт `total=0, hits=[]` без
исключения. Сейчас в репозитории нет ни одного такого вызывающего кода (проверено
`grep -rln "api\.knowledge("` — только `gateway.py`/`do_GET` с новым порядком и
`selftest.py` с именованными аргументами), поэтому это **не активный баг**, но
дефект контракта: параметр `limit` физически висит в сигнатуре, ничего не делает,
и представляет собой ловушку для любого будущего/внешнего вызывающего кода.
**Fix:** либо удалить `limit` из сигнатуры полностью (он не читается в теле
метода — dead code), либо, если сохраняется ради обратной совместимости
гипотетических внешних вызовов, сделать его keyword-only (`*, limit: int = 40`)
вместе с остальными параметрами после `query`, чтобы позиционный вызов из двух
аргументов был невозможен в принципе.
