## Находки

**Находка #1 — TOCTOU в анти-спам guard'е `create_task` (CONCURRENCY)**

- **Severity:** HIGH
- **File:Line:** `infra/ai-council/gateway.py:358-400` (`Api.create_task`, блок
  `dupe = store.q1("SELECT card_id FROM cards WHERE db='draft' AND content_hash = ? ...")`
  … далее `store.upsert_card(...)` и `store.enqueue(...)` без общей транзакции)
- **Why:** `SELECT` анти-дубликата и последующие `INSERT`ы карточки+прогона идут как
  отдельные автокоммит-операции (`isolation_level=None`, без `BEGIN IMMEDIATE`, в отличие от
  `claim_run()` в `store.py:190-207`, где та же гонка защищена явно). Каждый HTTP-запрос
  открывает своё соединение (`Api._store()` → новый `Store()` на запрос, `ThreadingHTTPServer`
  — по потоку на соединение), поэтому два «почти одновременных» POST (двойной клик, retry
  после таймаута сети, повторная доставка от прокси) видят пустой результат `SELECT`
  одновременно и оба проходят.
- **Repro (воспроизведено вживую в рамках этого ревью):** два потока Python вызывают
  `Api.create_task("Гонка анти-спама 2", "один и тот же текст задачи", [], "fast")`
  синхронно через `threading.Barrier`, на предварительно прогретой БД (без гонки на
  `PRAGMA journal_mode=WAL` при первом создании файла). Результат:
  ```
  results: [{'ok': True, 'card_id': 'draft_28cda3372b5238e3', ...},
            {'ok': True, 'card_id': 'draft_6a6d6fb485333026', ...}]
  draft cards created: 2   runs created: 2
  ```
  Оба запроса успешны, созданы ДВА разных черновика и ДВА прогона с идентичным
  title+body — то самое дублирование, которое анти-спам обязан предотвращать (плюс
  `card_id = "draft_" + sha16(f"{title}{ts}")` не может служить защитой: `ts=time.time()`
  вызывается независимо в каждом потоке, поэтому `card_id` почти гарантированно разный, и
  `ON CONFLICT(card_id)`-upsert в `store.py:128-132` не срабатывает как барьер — на
  `content_hash` нет ни `UNIQUE`, ни индекса в `schema.sql`).
- **Fix:** обернуть проверку+вставку в `BEGIN IMMEDIATE ... COMMIT` (тот же паттерн, что уже
  есть в `claim_run()`), либо создать `UNIQUE INDEX` на `(db, content_hash)` там, где
  `db='draft'`, и ловить `sqlite3.IntegrityError` как штатный «уже отправлено» ответ —
  второй вариант надёжнее первого (переживает будущий рефакторинг, не завязан на порядок
  операций).

**Находка #2 — незаэскейпленные LIKE-wildcard'ы в тексте упоминания (BOUNDARIES / CORRECTNESS)**

- **Severity:** MEDIUM
- **File:Line:** `infra/ai-council/gateway.py:372-378` (`like = store.q("SELECT card_id FROM
  cards WHERE title LIKE ? LIMIT 2", (f"%{mention}%",))`)
- **Why:** параметризация SQL корректна (никакой инъекции), но сам текст `mention`
  не эскейпится перед подстановкой в LIKE-паттерн — символы `%` и `_` в упоминании
  интерпретируются SQLite как wildcard'ы LIKE, а не буквально. Заголовки задач в этом
  проекте регулярно содержат `_` (имена переменных/таблиц/веток: `FOO_BAR`,
  `linked_card_ids`, `AI_COUNCIL_CLOUD`) — упоминание такого текста ломает резолвинг.
- **Repro (воспроизведено):** карточки `w1: "миграция FOO_BAR на новый пайплайн"` и
  `w2: "миграция FOOXBAR на новый пайплайн"` в базе; `create_task(..., links=["FOO_BAR"], ...)`
  → `{'ok': False, 'error': 'не найдены/неоднозначны упоминания: FOO_BAR'}` — хотя
  пользователь буквально процитировал заголовок `w1`, `_` в паттерне `%FOO_BAR%`
  матчит и `w2` (`FOOXBAR`), запрос возвращает 2 строки → «неоднозначность» →
  отклонено. В более редком раскладе (когда в базе есть только «случайно совпавшая»
  карточка, а буквально совпадающей нет) тот же механизм даёт не отказ, а тихую
  привязку к чужой карточке — то есть возможен не только false-reject, но и
  false-link (не путать с security-уязвимостью — оба сценария происходят в пределах
  собственных данных пользователя на localhost, без пересечения границ доступа).
- **Fix:** эскейпить `%`/`_`/`\` в `mention` перед подстановкой (
  `mention.replace('\\', '\\\\').replace('%', '\\%').replace('_', '\\_')` +
  `LIKE ? ESCAPE '\\'` в SQL) — как в фолбэке `create_task`, так и в `cards()`/
  `cards_autocomplete()` (тот же паттерн, не новый в этом дифе, но эксплуатируется
  впервые именно там, где результат — не список для человека, а решение "резолвить/
  отклонить").

**Находка #3 — `linked_evidence()`/`build()` падают на валидном, но не-list JSON в `linked_card_ids` (BOUNDARIES)**

- **Severity:** MEDIUM (сейчас недостижимо через единственный путь записи; LOW как
  реальный риск сегодня, MEDIUM как латентная бомба на будущее)
- **File:Line:** `infra/ai-council/retrieval.py:556-557` (`linked_evidence`) и
  `infra/ai-council/retrieval.py:629-630` (`build`, формирование `head`) —
  оба места: `try: linked_ids = json.loads(card.get("linked_card_ids") or "[]")
  except ValueError: linked_ids = []`, сразу за этим `linked_ids[:5]`.
- **Why:** `except ValueError` перехватывает только ошибку самого `json.loads` (невалидный
  JSON-текст). Если значение колонки — валидный JSON, но не список (`null`, `{}`, число,
  строка), `json.loads` не бросает исключения, а `[:5]`/цикл `for linked_id in linked_ids`
  падает с неперехваченным `TypeError`/`KeyError` — это уронит построение капсулы для
  карточки целиком (а не просто "молча отдаст пустой список", как явно предполагает try/except).
- **Repro (воспроизведено):**
  ```
  json.loads("null")[:5]  → TypeError: 'NoneType' object is not subscriptable
  json.loads("{}")[:5]    → KeyError: slice(None, 5, None)
  ```
  Оба — не `ValueError`, оба не пойманы существующим `except`.
- **Почему не CRITICAL сейчас:** единственный путь записи в `linked_card_ids` —
  `gateway.py:387`, всегда `json.dumps(linked_ids)` от списка `str`; остальные вызовы
  `upsert_card()` этот ключ не передают → колонка либо `NULL` (тогда `"[]"` по `or`),
  либо валидный JSON-список. Через штатный UI/API добраться до "валидный JSON, не список"
  сегодня нельзя.
- **Fix:** `except (ValueError, TypeError, AttributeError)` **и** явная проверка
  `isinstance(linked_ids, list)` перед `[:5]` — раз уже есть defensive try/except, он
  должен реально покрывать «битые данные», а не только «битый JSON-текст». Заодно
  вынести повторяющийся блок (строки 556 и 629 идентичны) в приватный хелпер
  `Retriever._linked_ids(card)`, чтобы фикс не разъехался по двум копиям.

**Находка #4 — удаление чипа не убирает `@[Title]` из текста; чип не редактируется текстом (PLAN-FIDELITY / UX-CORRECTNESS)**

- **Severity:** LOW/MEDIUM
- **File:Line:** `infra/ai-council/ui/index.html:1588` (`a.onclick = (e) => {
  e.preventDefault(); homeLinks.splice(Number(a.dataset.i), 1); renderHomeChips(); };`)
  против `ui/index.html:1667-1677` (`pickMention` — вставляет `` `@[${card.title}] ` ``
  в `#h-body` И пушит в `homeLinks`).
- **Why:** удаление чипа трогает только массив `homeLinks` (то, что реально уйдёт в
  `POST /api/tasks` как `links`) и не трогает уже вставленный текст `@[Title]` в
  textarea. Конкретный сценарий: пользователь набирает «@» + 2 символа → выбирает
  карточку из дропдауна → в тексте появляется `@[Название]`, в чипах — тег → пользователь
  жмёт «×» на чипе (например, решил не связывать) → чип пропал, но `@[Название]` осталось
  в тексте задачи как обычный текст. На сервере `linked_card_ids` для этой карточки
  НЕ будет (её не было в отправленных `links`), при этом текст задачи, который увидит
  консилиум и который попадёт в капсулу как plain text, продолжает буквально утверждать
  связь, которой нет в структурных данных — расхождение между тем, что видит пользователь
  (чип снят), и тем, что "видит" ИИ (текст с `@[...]` остался).
  Отдельно: план (`plan.md:89`) прямо говорит «чипы редактируемы» — реализация
  поддерживает только удаление, не редактирование текста чипа; собственный комментарий
  кода в `gateway.py:84` ("чип мог быть отредактирован пользователем после выбора из
  дропдауна") описывает возможность, которой в реализованном UI нет — резолвинг на
  сервере всё равно правильный выбор архитектуры, но обоснование в комментарии не
  соответствует тому, что реально можно сделать в UI.
- **Fix:** при удалении чипа либо (а) вырезать соответствующий токен `@[Title]` из
  `body.value` тем же движком, что вставлял его (сохранить позицию вставки/длину при
  вставке, чтобы знать, что удалять), либо (b) честно снять формулировку «чипы
  редактируемы» из UI-текста/плана и явно задокументировать, что чип = только add/remove,
  а свободный текст `@[...]` — не более чем подсказка для человека, не разбираемая
  сервером (тогда стоит и явно написать это в пояснении к вкладке, `TAB_DOC["home"]`,
  где сейчас написано «до 5 @-упоминаний … они попадут консилиуму как контекст» — это
  верно только для чипов, а не для любого текста `@[...]` в теле).

### Находки (остаточные — после фикс-прохода)

**Находка R1 (была #3) — `linked_evidence()`/`build()` всё ещё падают на списке с не-скалярными элементами**

- **Severity:** MEDIUM (латентно, как и оригинальная #3) — контракт нарушен не
  полностью закрыт, находка #3 не может считаться ЗАКРЫТОЙ.
- **File:Line:** `infra/ai-council/retrieval.py:552-561` (`_linked_ids` —
  проверяет только `isinstance(parsed, list)` на верхнем уровне, не типы
  элементов) → `infra/ai-council/retrieval.py:568-569` (`linked_evidence`,
  `self.store.get_card(linked_id)`) и `retrieval.py:636-640` (`build`, тот же
  паттерн) → `infra/ai-council/store.py:144-145` (`get_card` →
  `self.q1(..., (card_id,))`, где `card_id` — не строка).
- **Why:** `json.loads('[[1,2],[3,4]]')` — валидный JSON, верхний уровень —
  список, проходит `isinstance(parsed, list)`. Каждый элемент (`[1,2]`, `[3,4]`)
  — тоже список, а не строка/скаляр. `sqlite3` не умеет биндить `list` как
  параметр запроса → `store.get_card(linked_id)` бросает
  `sqlite3.ProgrammingError: Error binding parameter 1: type 'list' is not
  supported`. Это не `ValueError`/`TypeError`, поэтому `except (ValueError,
  TypeError)` в `_linked_ids()` его не ловит — там ему и неоткуда ловиться,
  оно летит из `linked_evidence()`/`build()`, где try/except вообще нет.
- **Repro (воспроизведено, детерминированно):**
  ```
  card = {"linked_card_ids": "[[1,2],[3,4]]"}
  Retriever._linked_ids(card)          # OK -> [[1, 2], [3, 4]], не падает
  Retriever.linked_evidence(retriever, card)
  # sqlite3.ProgrammingError: Error binding parameter 1: type 'list' is not supported
  ```
- **Fix:** в `_linked_ids()` дополнительно отфильтровать нестроковые элементы —
  `return [x for x in parsed if isinstance(x, str)] if isinstance(parsed, list) else []`
  — тогда контракт «список card_id, и только он» держится на всех уровнях.

**Находка R2 (была #4) — снятие чипа не убирает второе вхождение того же `@[Title]`, и молча не убирает вхождение при расхождении текста**

- **Severity:** LOW/MEDIUM (как и оригинальная #4) — простой случай теперь чист,
  но находка не закрыта полностью.
- **File:Line:** `infra/ai-council/ui/index.html:1588-1596` (onclick чипа —
  `body.value.replace(`@[${title}] `, "")`, `String.replace` со строковым
  аргументом снимает только первое вхождение) и `ui/index.html:1668-1678`
  (`pickMention` — дедуплицирует `homeLinks` по `title`, но не дедуплицирует
  вставки текста).
- **Why:** (а) Если пользователь дважды выбирает одну и ту же карточку из
  дропдауна в разных местах текста, `homeLinks` получает один элемент (проверка
  `!homeLinks.includes(card.title)`), но текст получает два `@[Title] `. При
  снятии единственного чипа удаляется только первое вхождение — второе
  остаётся в тексте без способа его снять (чипа для него больше нет). (б) Если
  пользователь вручную отредактировал текст так, что точная подстрока (включая
  один конкретный пробел на конце) больше не совпадает, `.replace()` возвращает
  исходную строку без изменений — тихий no-op, чип пропадает из UI, текст
  остаётся, никакого предупреждения не показывается.
- **Repro (воспроизведено):** построчная копия `pickMention`/`onclick` из
  `ui/index.html` прогнана в Node с фейковым textarea (симулирующим реальное
  перемещение курсора):
  ```
  after 2x insert: "@[Foo] some more text before second mention @[Foo] "
  after remove:    "some more text before second mention @[Foo] "   ← осиротевший токен
  ```
  и отдельно:
  ```
  after manual edit: "@[Foo]\n"     (пробел стал переносом строки)
  after remove attempt: "@[Foo]\n" ← без изменений, чип пропал молча
  ```
- **Fix:** хранить позицию/длину вставки при `pickMention` и снимать ровно тот
  диапазон при удалении чипа; либо явно запретить `pickMention` вставлять
  второе упоминание уже связанной карточки (дизейбл пункта в дропдауне, если
  `homeLinks.includes(card.title)`), чтобы сценарий (а) стал недостижим, и
  показывать предупреждение при неудачном `.replace()` для сценария (б).

**Находка R3 (была #2) — `cards()`/`cards_autocomplete()` не используют `_escape_like` (не блокирует)**
