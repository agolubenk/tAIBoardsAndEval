# План AI Council v2 — 4 фичи

Статус: УТВЕРЖДЁН владельцем 2026-08-16 (решения A–D — в decision.md и в конце
файла). К реализации — по фазам P0→P4.

Базовые факты (recon.md): UI — один index.html 2334 строки (TABS/RENDERERS);
gateway.py — Api + Handler, /api/graph потолок 1200; graph.json = 68 320 узлов /
142 814 связей, relations: contains 39.5k, references 26.4k, calls 23.7k, imports
20.8k, imports_from 14.5k, method 13.3k, inherits/implements/extends ~550 —
функции/классы/вызовы УЖЕ есть; schema.prisma в корпусе графа ОТСУТСТВУЕТ;
/api/knowledge без запроса не возвращает документов; «сессии» как сущности нет.

## Порядок фаз (по соотношению ценность/риск)

| Фаза | Фича | Оценка | Почему так
|---|---|---|---|
| P1 | Ф4 знания+пагинация | ~0.5–1 д | изолирована, gateway+UI, даёт быстрый результат |
| P2 | Ф1 главная форма | ~2–3 д | высшая пользовательская ценность; A решён (локальный черновик) |
| P3 | Ф3 граф | ~3–4 д | самодостаточна; prisma-экстрактор + LOD + ленивая догрузка (D) |
| P4 | Ф2 сессии + контекст + MCP | ~4–5 д | UI сессий + свёртка на закрытии (B) + MCP с Headroom (C) |

Общая фаза P0 (миграции, ~0.5 д):
- schema.sql — `sessions` (id TEXT PK, title TEXT, opened_at INTEGER, closed_at
  INTEGER, status TEXT, summary TEXT, summary_model TEXT, summary_tokens INTEGER)
  и `session_runs` (session_id TEXT, run_id TEXT, PRIMARY KEY(session_id, run_id))
  и `session_contexts` (session_id TEXT PK, summary TEXT, version INTEGER,
  source_run_id TEXT, updated_at INTEGER). Решение B: сессия = рабочая сессия
  владельца от запуска до остановки — границы задаёт UI, а не цепочка карточек.
- store.ADDED_COLUMNS — («cards», «linked_card_ids», «TEXT»).
Ничего не меняет в поведении, катится автоматически (Store._migrate executescript
+ ALTER).

## P1. Ф4 — Знания: полный список с пагинацией

Проблема: Api.knowledge без `q` возвращает только агрегаты kinds; документы —
только через FTS5 MATCH.

**API** (gateway.py):
- `Api.knowledge(q, kind, page, page_size)`:
  - q пусто → листинг: `SELECT c.doc_id, c.kind, c.title, substr(c.content,1,260)
    snippet, m.module, m.source_ref, m.indexed_at FROM corpus c JOIN corpus_meta m
    USING(doc_id) [WHERE kind=?] ORDER BY c.kind, c.title LIMIT ? OFFSET ?` +
    `COUNT(*)` того же фильтра для пейджера.
  - q непусто → прежний FTS5 MATCH, но с теми же page/page_size (OFFSET после rank).
- page_size по умолчанию 50, потолок 100 (правило «findMany без take» — аналог).
- GET /api/knowledge?q=&kind=&page=&page_size=.

**UI**: renderKnowledge — режим по умолчанию «каталог»: чипы-фильтры по kind
(все/правила/агенты/скиллы/чанки/граф/карточки/закрытое/образцы/сессии), таблица
(тип, заголовок, источник, фрагмент, дата индексации), пейджер «← стр. N из M →».
Поиск сверху: при вводе q режим переключается на FTS, пейджер общий.

**Проверки**: selftest — пагинация без q возвращает все документы суммарно
(page_size итерациями); с q — ранжирование не сломано; kind-фильтр считает
правильно. Узкий чек: `npm run ai-council:selftest`.

**Риски**: corpus до ~4600 документов (463 знания + ≤400 graph_node + карточки +
DONE) — листинг лёгкий, эмбеддинги не трогаем.

## P2. Ф1 — Главная страница: форма задачи с @[упоминаниями]

Проблема: вход в консилиум сегодня — только через существующую карточку Notion;
ад-hoc задачу завести негде.

**Семантика** (решение A — локальный черновик):
- Submit создаёт ЛОКАЛЬНУЮ карточку-черновик: `cards` с db='draft',
  card_id='draft_'+sha16(title+ts), source='home-form', status='черновик',
  linked_card_ids=JSON[@-упоминаний]. Notion НЕ пишется вообще (инвариант шлюза
  «в Notion не пишет» цел). Черновик виден во вкладке «Карточки» с тегом
  «черновик — нет в Notion»; кнопка «Отправить в Notion» (позже, через
  emit-механику с require_apply_flag) превращает его в настоящую карточку —
  отдельный шаг, в v1 не обязателен.
- Инвариант шлюза «пишет ровно две вещи» расширяется ДОКУМЕНТИРОВАННО до трёх:
  вердикты, очередь, черновики задач (docstring gateway.py). Это осознанная
  правка контракта, а не тихое исключение.
- emit.py: карточки db='draft' пропускаются (нет page_id) с пометкой в отчёте.
- planner: db='draft' не попадает в рабочие окна (жёсткое правило).
- context_service.index_cards индексирует черновики как обычные карточки —
  «соседние задачи» начнут видеть их сразу.

**@-упоминания**:
- Синтаксис `@[точное название]` в тексте задачи. UI: триггер по «@» →
  dropdown (debounce 200 мс, ≥2 символа) из `/api/cards?q=&limit=8`
  (tasks+bugs, отметка half_baked/backlog_id); выбор вставляет токен + чип;
  чипы редактируемы. Лимит 5 связей.
- Сервер валидирует: точное совпадение title → card_id; иначе LIKE;
  неразрешённые — ошибка со списком (никаких угадываний молча).

**API**:
- GET /api/cards/autocomplete?q= — лёгкий (title, card_id, db, backlog_id,
  half_baked), без подзапросов runs/readiness.
- POST /api/tasks {title, body, links[], profile} → черновик + enqueue
  (track=elaborate, dedupe=False) → {card_id, run_id}; гварды: title 1..1900,
  body ≤ 8000, links ≤ 5, профиль из allowed; простое анти-спам окно 10 с.

**Капсула** (retrieval.py): новый источник улик `linked` — для каждого
linked_card_id: цель последнего done-прогона, заголовки декомпозиции,
open_questions, активное указание владельца (SQL по runs.payload + card_notes),
клип 80 токенов на карточку, бюджет per_source. В pinned — строка
«Связанные задачи: …» с url.

**UI**: вкладка «Главная» первой в TABS и по умолчанию (activeTab='home');
крупная форма: заголовок, текст, @-автокомплит, чипы связей, профиль (как в
openSeries, с disabled для облачных при выключенном облаке), оценка
(/api/estimate, count=1), окно запуска не нужно (одна карточка). Сабмит →
тост + переход на прогон. TAB_DOC для вкладки — в Api.TAB_DOC/guide.

**Проверки**: selftest — парсер упоминаний (точное/LIKE/битое), черновик+
enqueue, emit-skip для draft; вручную — вкладка, автокомплит, прогон черновика.
Узкий чек: `npm run ai-council:selftest`.

**Риски**: черновики накапливаются — контекст: вкладка «Карточки» с фильтром;
решение «удалить черновик» = отмена queued-прогонов (уже есть cancel_queued).
Coverage/quality считают черновики карточками — приемлемо, помечено тегом.

## P3. Ф3 — Граф: связи всего + управление количеством

Три части.

**3а. Данные БД в графе** (graph_build.py):
- Новый шаг Part A2 после AST: парсер `apps/backend/prisma/schema.prisma`
  (stdlib, построчный): модели → узлы `prisma:<Model>` (kind='prisma_model',
  community='backend', label=ModelName); `@relation`/`@@relation` → рёбра
  relation='prisma_relation'; enum'ы → узлы + contains.
- Привязка к коду: `git grep -l 'prisma.<Model>\.'` (детерминированно, без LLM),
  до 5 файлов → рёбра references модель↔файл. Легенда на вкладке пополняется.
- Слияние в Part C (узлы prisma:* не дедуплицируются с AST-узлами).
- Пересборка графа инвалидирует кэш gateway само (ключ по mtime+size — уже есть).

**3б. Фильтр по типам связей**:
- GET /api/graph&rel=calls,imports,inherits,references,prisma_relation — фильтр
  рёбер ДО свёртки уровней; UI — мультиселект «связи: вызовы/импорты/
  наследование/ссылки/модель БД/contains(по умолчанию выкл. на уровне файлов)».
- relation в рёбрах ответа уже есть (мажоритарный по паре) — фильтр серверный,
  чтобы срез оставался связным после фильтрации (пересчёт _graph_slice по
  отфильтрованному adj).

**3в. Шкала бюджета узлов**: 150, 300, 500, 1000, 1500, 2500, 5000, 8000,
10000, 15000, 25000, все.
- ≤2500: прежний путь (связный срез _graph_slice, потолок API поднят до 2500;
  рёбра cap 8000→25000 с тем же дедупом-весами).
- >2500 и «все»: режим LOD «сообщества» — серверная агрегация: узел =
  community (размер = число участников, вес = сумма рёбер), рёбра = счётчики
  межсообщественных связей; уровни files|symbols|communities. «Все» = все 68k
  узлов, свёрнутые до ~сотен суперузлов — честное «все» без вранья о картинке.
  Клиент рисует суперузлы тем же canvas (их сотни), клик по сообществу →
  drill-down `/api/graph/community/<id>&limit=…` (связный срез внутри).
- UI: селект лимита из шкалы (значение из localStorage, как сейчас); при
  выборе >2500 автоматически уровень «сообщества» + пояснение; при «все» —
  то же с бейджем «68 320 узлов свёрнуто в N сообществ».
- Ленивая догрузка области (решение D): на уровне сообществ рендерится сначала
  укрупнённая картина (суперузлы), детальный срез выбранного сообщества или
  окрестности узла подтягивается вторым запросом `/api/graph/community/<id>`
  при клике/зуме — UI не блокируется, тяжёлый срез приходит с задержкой и
  подменяет суперузел разворачиванием (drill-down). Скелет суперузлов виден
  сразу, «все 68k» никогда не грузятся в клиент одним ответом.
- Производительность: _graph_index уже в кэше процесса; агрегация сообществ —
  один проход по adj (мс); срез 2500 — heap, десятки мс. Рендер: canvas 2D
  тянет ~2–3k узлов (пространственный хеш уже есть), LOD это снимает.

**Проверки**: selftest — prisma-парсер на фикстуре схемы (модели/relations
  считаются), rel-фильтр не роняет связность среза, LOD-агрегация сходится
  (сумма весов суперрёбер = числу межсообщественных рёбер); вручную — вкладка
  на всех лимитах, drill-down. Узкий чек: `npm run ai-council:selftest` +
  `npm run ai-council:graph`.

**Риски**: парсер prisma — регекс, ломается на экзотике; фикс: падение шага ≠
  падение сборки (граф без prisma-узлов + warning в job output, как в main
  graph_build уже сделано для индексации).

## P4. Ф2 — Сессионный контекст (RAG) + MCP-сервер

**Определение сессии** (решение B — рабочая сессия владельца): сессия —
интервал от запуска до остановки, границы задаёт UI (кнопки «Начать сессию» /
«Завершить сессию», автозакрытие по таймауту простоя — гейт в конфиге).
За одну сессию — сколько угодно карточек; итоговый контекст принадлежит
СЕССИИ, а не карточке. Прогоны вне открытой сессии в сессию не попадают,
но контекст последней закрытой сессии (если гейт включён) всё равно уходит
в капсулу как pinned-улика; дальние сессии доступны корпусу kind='session'.

**Хранилище (P0-схема)**: `sessions` (id, title, opened_at, closed_at, status
open|closed, summary, summary_model, summary_tokens), `session_runs`
(session_id, run_id, PK пара), `session_contexts` (session_id PK, summary,
version, source_run_id, updated_at).

**Жизненный цикл**:
- Открытие: POST /api/sessions {title?} → store.event('session.opened').
  Активная сессия одна: открытие новой при живой открытой — авто-закрытие
  прежней с пометкой в ответе.
- Во время сессии: council_worker.process после finish_run(done/abstained)
  дописывает session_runs (INSERT OR IGNORE) — накапливаются факты,
  промежуточной генерации нет.
- Закрытие («итоговый контекст перед завершением сессии» — требование задачи):
  POST /api/sessions/{id}/close → context_service.summarize_session(): роль
  extractor (S-модель, локально, бесплатно): вход — карточки сессии с
  целями/вердиктами/статусами прогонов, goal последнего done-payload,
  open_questions, причины воздержаний, затронутые файлы; выход — компакт
  ≤ [council.session_context] max_summary_tokens (300): чем занимались, что
  решено, что открыто, на чём остановились. Пишется в sessions.summary и
  session_contexts; документом corpus kind='session' (заголовок = дата+title,
  upsert по content_hash, эмбеддинг штатно) → RAG-поиск по прошлым сессиям.
- Использование в новой сессии: retrieval.build добавляет в pinned блок
  «КОНТЕКСТ ПРЕДЫДУЩЕЙ СЕССИИ (…назад, N карточек)» — summary последней
  закрытой сессии, бюджет ~200 ток. из council.context; corpus kind='session'
  отдаёт дальние сессии как обычные улики опыта.
- Гейт [council.session_context] enabled=true, idle_close_hours=12,
  max_summary_tokens=300; выключено → поведение сегодняшнее. Сессия, забытая
  открытой, закрывается лениво при следующем обращении к API (свёртка — тогда же).

**MCP** (решение C — новый сервер для ДРУГИХ целей, хранилище исключительно
консилиумное, с встройкой Headroom): НОВЫЙ MCP-сервер
`infra/ai-council/mcp_server.py`, stdlib, stdio JSON-RPC (initialize,
tools/list, tools/call). Хранилище — ТОЛЬКО council.db + corpus + graph.json,
ничего постороннего. Назначение — внешние агенты (Continue, Claude Code)
читают контекст консилиума; сам консилиум по-прежнему ходит в БД напрямую.
Встройка Headroom: сервер сам зовёт Headroom-прокси (127.0.0.1:8787,
models.cloud.headroom.url из конфига) для сжатия длинных ответов
инструментов (соседи графа, свёртки сессий); прокси недоступен → сырой ответ
с пометкой `uncompressed: true` (fail-safe, здоровье кэшируется 30 с, как в
cloud-клиенте). Инструменты:
- `council_knowledge_search(q, kind?)` — FTS5 по corpus (+vec при живой Ollama);
- `council_session_context(session_id?)` — summary последней закрытой сессии
  (или конкретной) + её прогоны с итогами;
- `council_card_runs(card_id|backlog_id)` — статусы, readiness, open questions;
- `council_graph_neighbors(node, hops?, limit?)` — соседи по graph.json через
  общий graph_index.py (вынести из gateway._graph_index); ответ длиннее порога
  сжимается Headroom.
Регистрация: строка в MCP-конфиге внешнего агента
(`python3 infra/ai-council/mcp_server.py`); [sources.mcp] пополняется
`council = true`. Секретов наружу нет: stdio, локальная БД, только чтение.

**Проверки**: selftest — жизненный цикл сессии мок-моделью (открыть → два
фикстурных прогона → закрыть → summary написан и ≤ бюджета, corpus kind='session'
появился; следующая сессия получает pinned-блок); MCP: tools/list + два
tools/call поверх stdio (subprocess) на фикстурной БД; Headroom: с поднятым
прокси ответ промаркирован сжатым, с потушенным — uncompressed=true без
падения. Узкий чек: `npm run ai-council:selftest`.

**Риски**: сессия забыта открытой — ленивое автозакрытие idle_close_hours
(свёртка генерируется в этот момент, не теряется); качество свёртки
S-моделью — вход только факты runs/payload, потолок токенов, гейт
enabled=true (выключено → подсистема как сегодня); Headroom как зависимость
— fail-safe по /health; гонка «закрытие во время идущего прогона» — прогон
доfinish_run дописывается в сессию перед свёрткой (один SELECT + INSERT,
транзакция), идущие после закрытия прогоны в закрытую сессию не попадают.

## Решения владельца (2026-08-16)

**A — ПРИНЯТО: локальный черновик.** Submit создаёт карточку db='draft' в
council.db, в Notion не пишем вовсе; перенос черновика в Notion — отдельное
явное действие владельца (кнопка «Отправить в Notion» через emit-механику с
require_apply_flag), в v1 не обязательна. Инвариант «шлюз в Notion не
пишет» сохранён.

**B — ПРИНЯТО: сессия = рабочая сессия владельца от запуска до остановки.**
Границы задаёт UI (кнопки «Начать/Завершить сессию», автозакрытие по простою
idle_close_hours), итоговый контекст принадлежит сессии, а не карточке;
свёртка генерируется на закрытии. См. «Жизненный цикл» в P4.

**C — ПРИНЯТО: новый MCP-сервер для других целей, хранилище исключительно
консилиумное, с встройкой Headroom.** Сервер читает ТОЛЬКО council.db /
corpus / graph.json (никаких посторонних источников), предназначен внешним
агентам (Continue, Claude Code), длинные ответы сжимает через Headroom-прокси
(models.cloud.headroom.url), при его недоступности — сырой ответ с пометкой
uncompressed=true. См. блок «MCP» в P4.

**D — ПРИНЯТО: LOD по сообществам + ленивая догрузка области графа.**
До 2500 узлов — связный срез как сейчас; выше и «все» — свёртка по
сообществам с drill-down; выбранная область подтягивается с задержкой
(лениво, при клике/зуме на интересующую область), а не весь массив сразу.

## Definition of Done (на фазу)

1. Изменённые файлы и зачем — в evidence.md фазы.
2. `npm run ai-council:selftest` — pass (расширенный новой фазой).
3. Для P3 дополнительно `npm run ai-council:graph`; для P4 — прогон одной
   карточки с двумя последовательными прогонами (свёртка унаследована).
4. Риски/непроверенное — явно в evidence.md.
5. Миграции — только P0-форма (ADDED_COLUMNS + CREATE IF NOT EXISTS),
   существующие данные не переносятся/не удаляются.
