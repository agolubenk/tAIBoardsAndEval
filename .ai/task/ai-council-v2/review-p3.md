## Находки

**Находка #1 — LOD (`level=communities`) молчаливо «пустеет» при фильтре по реально доступной, но чисто внутрикоммьюнити связи (BOUNDARIES / UX-CORRECTNESS)**

- **Severity:** MEDIUM
- **File:Line:** `infra/ai-council/gateway.py:1239-1247` (`graph()`, ветка
  `level == "communities"`) в паре с `gateway.py:1250-1254` (та же проверка на
  ветке files/symbols).
- **Why:** на ветке files/symbols пустой-после-фильтра adjacency ловится явно
  (`if not adj: return {"available": False, "hint": "после фильтра связей граф
  пуст — нечего показывать"}`, строка 1253-1254). На ветке `communities` такой
  проверки нет: `nodes_out` в `_graph_communities` считается из `meta` **независимо
  от `rels`** (размеры сообществ не зависят от типа связи), поэтому `nodes_out`
  почти никогда не пуст, и метод всегда возвращает `available: True` — даже когда
  `edges_out` пуст целиком. Это не синтетический «мусорный» rel — воспроизведено
  реальными, доступными через UI чекбоксами связей.
- **Repro (воспроизведено вживую, реальные данные этого репозитория):**
  ```
  GET /api/graph?level=files                → available_relations:
    ['calls','case_of','cites','contains','defines','extends','implements',
     'imports','imports_from','indirect_call','inherits','method',
     'prisma_relation','rationale_for','re_exports','references','requires_env']

  GET /api/graph?level=communities&rel=extends        -> available=True, edges=0
  GET /api/graph?level=communities&rel=defines         -> available=True, edges=0
  GET /api/graph?level=communities&rel=cites            -> available=True, edges=0
  GET /api/graph?level=communities&rel=rationale_for     -> available=True, edges=0
  GET /api/graph?level=communities&rel=requires_env      -> available=True, edges=0
  ```
  5 из 17 реальных, чекбоксом выбираемых в UI типов связи дают именно такой
  результат: пользователь заходит на вкладку «Граф», переключает уровень на
  «сообщества», отмечает галочкой один из этих типов — получает 3101 висящую в
  пустоте точку без единой линии и без единого поясняющего сообщения (в отличие
  от уровня files/symbols с тем же самым фильтром, где вместо графика показывается
  понятный текст «после фильтра связей граф пуст — нечего показывать»). Данные не
  повреждены (сумма весов остаётся математически верной — см. проверку инварианта
  в п.7 протокола), баг чисто в отсутствующем UX-сигнале ровно там, где план §3б
  явно требует «честного» сигнала о связности после фильтра.
- **Fix:** после построения `edges_out` в ветке `communities` добавить тот же
  паттерн, что уже есть у files/symbols:
  ```python
  nodes_out, edges_out = self._graph_communities(symbols["meta"], symbols["adj"], rels)
  if rels and not edges_out:
      return {"available": False,
              "hint": "после фильтра связей нет межкоммьюнити рёбер — все сообщества изолированы"}
  ```
  (не блокировать case без активного фильтра — граф из одних сообществ без единой
  связи в принципе может быть реальным состоянием при `rels=None`, туда правило не
  должно лезть).

**Находка #2 — некорректный `limit` эскалируется к МАКСИМУМУ, а не к безопасному дефолту (BOUNDARIES / ROBUSTNESS)**

- **Severity:** LOW (недостижимо через штатный UI — см. ниже; актуально только для
  прямых HTTP-запросов, минуя фронтенд)
- **File:Line:** `infra/ai-council/gateway.py:1757` (`limit_val = int(limit_raw) if
  limit_raw.strip().isdigit() else 2500`) и `gateway.py:1765` (тот же паттерн,
  `else 25000`).
- **Why:** `str.isdigit()` возвращает `False` для `"-5"` (минус — не цифра), для
  `"all"`, для `""`, для любого нечислового мусора — во всех этих случаях роутинг
  подставляет **верхнюю границу клэмпа** (2500 / 25000), а не что-то безопасное
  вроде дефолта самого метода (`limit: int = 300` / `limit: int = 1000`) или нижней
  границы (50). Комментарий на строке 1752-1755 («Финальный клэмп — внутри
  api.graph()») вводит в заблуждение: внутренний клэмп `max(50, min(int(limit),
  2500))` (`gateway.py:1257`) получает на вход уже эскалированное до максимума
  значение и не может его уменьшить — по построению `min(2500, 2500) == 2500`.
- **Repro (воспроизведено вживую):**
  ```
  GET /api/graph?limit=-5    -> limit=2500 (2500 узлов, 2 986 071 байт ответа)
  GET /api/graph?limit=abc   -> limit=2500 (тот же результат)
  GET /api/graph?limit=all   -> limit=2500
  GET /api/graph/community/1?limit=-1    -> limit=25000 (658 узлов — вся община)
  GET /api/graph/community/1?limit=abc   -> limit=25000 (тот же результат)
  GET /api/graph/community/1?limit=50    -> limit=50 (для сравнения — корректный клэмп)
  ```
- **Почему LOW, не MEDIUM:** штатный UI не может отправить такой `limit` —
  `<select id="g-limit">` предлагает только значения фиксированной шкалы
  `GRAPH_BUDGET_SCALE` плюс `"all"`, а `"all"` на клиенте явно уводит на
  `level=communities` (`graphEffectiveLevel()`, `index.html:2099-2100`), где
  `limit` внутри `graph()` вовсе не участвует (ветка `communities` игнорирует его
  целиком) — байпас срабатывает раньше, чем баг №2 мог бы проявиться. Даже парсинг
  на самом клиенте (`parseInt(raw, 10) || 300`, `index.html:~2248`) откатывается к
  безопасному 300, не к максимуму. Баг реален и воспроизводится только при ручных/
  прямых HTTP-запросах к API, минуя интерфейс — что для локального инструмента без
  auth-периметра снижает практическую цену до «локальный пользователь заставил
  собственный сервер на своей же машине посчитать больше, чем нужно».
- **Fix:** заменить фолбэк в роутинге на дефолт метода, а не на потолок:
  `limit_val = int(limit_raw) if limit_raw.strip().isdigit() else 300` (и `1000`
  для community-эндпоинта) — тогда мусорный ввод получает разумный средний размер,
  а не гарантированно самый тяжёлый ответ.

## Находки — низкий приоритет (принятый долг, не блокируют APPROVED)

**N1 — стейл `graphPrefs.limit` из до-P3 localStorage рассинхронизирует `<select>` (BACKWARD COMPATIBILITY)**

- **File:Line:** `infra/ai-council/ui/index.html:1797` (новая `GRAPH_BUDGET_SCALE`)
  vs. диф, строка со старым `const limits = [150, 300, 600, 1000];` (удалена).
- Возвращающийся пользователь, у которого в localStorage под ключом
  `ai-council-graph-prefs` сохранён `{"limit": 600, ...}` от версии UI до этого
  дифа, получит `graphPrefs.limit === 600` после `Object.assign` при загрузке —
  значения `600` больше нет в `GRAPH_BUDGET_SCALE`, поэтому ни один `<option>` не
  получит `selected`, и браузер по стандартному поведению `<select>` покажет
  первый пункт («150 узлов»), в то время как фактические запросы всё ещё уходят с
  `limit=600` (валидное число, не крэш) — до первого клика по дропдауну, который
  самоисправляет расхождение. Не блокирует, потому что не крэш и не потеря данных,
  только один экран визуальной путаницы для узкого подмножества старых
  пользователей.

**N2 — буквальный `/` в `community_id` тихо усекается `rsplit` (SECURITY-ADJACENT ROBUSTNESS)**

- **File:Line:** `infra/ai-council/gateway.py:1763` (`route.rsplit("/", 1)[-1]`).
- `GET /api/graph/community/foo/bar` матчит роут (в отличие от пустого сегмента,
  который даёт честный 404) и молча ищет сообщество `"bar"`, отбрасывая `"foo/"`.
  Недостижимо через сегодняшний UI (всегда `encodeURIComponent`) и недостижимо на
  сегодняшних данных (id сообществ — целые числа или `"?"`, слэшей не бывает) —

### Находки (остаточные, после фикс-прохода)

**N6 — гард атрибутирует пустоту фильтру даже когда причина — «сообщество одно» (не сам фильтр) (EDGE CASE, не блокирует)**

- **Severity:** LOW
- **File:Line:** `infra/ai-council/gateway.py:1248-1251`
- **Why:** условие `if rels and not edges_out` не различает «фильтр вычистил
  межкоммьюнити рёбра, которые были» от «межкоммьюнити рёбер не может быть в
  принципе, потому что сообщество одно (или все связаны только внутри себя)» —
  во втором случае `edges_out` пуст независимо от того, какой конкретно `rel`
  выбран, а сообщение всё равно говорит «после фильтра связей нет ни одной
  межобщинной связи», подсказывая, что дело в выбранном типе связи.
- **Repro (воспроизведено, синтетическая фикстура, отдельный Python-процесс, не
  трогает репозиторий):** граф из 4 узлов в ОДНОМ сообществе `"only"`, рёбра
  `n0–n1` и `n2–n3` реально помечены `relation="x"`.
  ```
  api.graph(level="communities", rel="x")
    -> {'available': False,
        'hint': 'после фильтра связей нет ни одной межобщинной связи — '
                'сообщества остались бы не связаны друг с другом'}
  api.graph(level="communities")           # без фильтра — та же топология
    -> {'available': True, 'nodes': [...1 сообщество...]}
  ```
  При отсутствии фильтра тот же (структурно) случай «межкоммьюнити рёбер нет»
  спокойно проходит как `available:true` (гард не срабатывает — `rels` ложно);
  стоит указать ЛЮБОЙ реально существующий `rel`, и то же самое отсутствие
  межкоммьюнити рёбер вдруг подаётся как последствие фильтра.
- **Почему не блокирует:** на реальном графе этого репозитория — 3101
  сообщество (не 1), сценарий структурно недостижим сегодня. Сообщение не
  фактически неверно (межобщинных рёбер действительно 0 после применения
  фильтра), только не называет главную причину в этом гипотетическом случае.
  Не крэш, не потеря данных, не путает files/symbols уровень.
- **Fix (не обязателен для этого APPROVED, кандидат в тот же техдолг-список, что
  N1–N5 из первого прохода):** сравнить также случай без фильтра — если
  `_graph_communities(meta, adj, None)` тоже дал бы 0 межобщинных рёбер, писать
  другой hint («граф не имеет межобщинных связей независимо от фильтра») —
  или просто смягчить формулировку до нейтральной («после фильтра нет ни одной
  межобщинной связи» без утверждения о причинности).
