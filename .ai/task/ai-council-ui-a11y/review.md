## Находки

**Severity: HIGH** · **File:Line:** `infra/ai-council/ui/index.html:1620-1621` (поле `#h-title`, нет `onkeydown`) в связке с `:1617` (`<form id="h-form">`) и `:1644` (`<button type="submit" form="h-form">`)
**Pattern:** незащищённая нативная implicit-submission формы
**Why:** `#h-title` — это `<input type="text">` без обработчика `keydown`. По спецификации HTML любой однострочный текстовый `<input>` внутри `<form>` с submit-кнопкой (даже вынесенной за пределы `<form>` через атрибут `form=`) триггерит нативный submit при нажатии обычного Enter — независимо от продуманного дизайна «только Cmd/Ctrl+Enter из textarea». Раньше (до диффа) поля были в `<div>`, а не в `<form>`, и такой имплиситный submit был физически невозможен — это чистый регресс, введённый именно этим диффом. Пользователь печатает заголовок и жмёт Enter (привычка «перейти дальше» или просто Enter как пунктуация в макете) — и черновик уходит в очередь с чем угодно, что успело оказаться в `body` (часто — пустым), минуя весь описанный в коммите UX «Cmd/Ctrl+Enter — привычка чат-композеров».
**Repro (live, Playwright MCP, подтверждено):** navigate `http://127.0.0.1:8790/#home` → `fill('#h-title', 'Проверка premature submit')` (поле `#h-body` не трогать) → `press('Enter')` с фокусом в `#h-title` → в `browser_network_requests` появляется `POST /api/tasks => 200`, следом `GET /api/runs/run_3134b224908a` (реальная карточка создана в живой системе с пустым `body`). Без диффа (поле в `<div>`) это невозможно физически.
**Fix:** добавить `titleEl.onkeydown = (e) => { if (e.key === "Enter") e.preventDefault(); };` (аналогично тому, что уже сделано для textarea), либо убрать нативный submit-контракт вовсе (`type="button"` + явный `goBtn.onclick = submitHome` вместо `type="submit" form=...`, оставив Cmd/Ctrl+Enter единственным клавиатурным путём, как заявлено в коммите).

**Severity: HIGH** · **File:Line:** `infra/ai-council/ui/index.html:1744-1748` (ветка `Enter`/`Tab` в `body.onkeydown`)
**Pattern:** keyboard trap (WCAG 2.1.2) — `e.preventDefault()` вызывается для `Tab` безусловно, даже когда нет активного `@`-контекста
**Why:** Когда дропдаун открыт (`!dropdown.hidden`), код входит в ветку `else if (e.key === "Enter" || e.key === "Tab") { e.preventDefault(); ... if (at !== -1 && mentionSel >= 0) pickMention(...) }`. `e.preventDefault()` стоит ДО проверки `at !== -1`. Если пользователь подвинул курсор стрелками влево/вправо за пределы `@word` (что не закрывает дропдаун — `hideMentions()` вызывается только из `oninput`/явных веток `keydown`, не из движения курсора), дропдаун остаётся открытым и визуально «залипшим», а нажатие Tab не переводит фокус на следующий элемент формы (радиокнопки профиля / кнопку отправки) — стандартный способ выйти из textarea клавиатурой молча блокируется, без вставки упоминания (`at === -1` → `pickMention` не вызывается) и без какой-либо подсказки пользователю.
**Repro (live, Playwright MCP, подтверждено):** в `#h-body` набрать `@te` (дропдаун открывается, `aria-expanded="true"`) → `setSelectionRange(0,0)` (курсор перед `@`, дропдаун остаётся `hidden:false`) → `page.keyboard.press('Tab')` → `document.activeElement.id` **остаётся `"h-body"`** (фокус не переместился), значение textarea не изменилось (`"@te"`, `pickMention` не сработал). Выход есть (`Escape` закрывает дропдаун — проверено live, `dropdownHidden:true` после `Escape`), но это не тот способ, которым пользователь обычно выходит из поля, и нигде не подсказан.
**Fix:** проверять `at !== -1 && mentionSel >= 0` ДО `e.preventDefault()` для ветки `Tab` (для `Enter` внутри textarea preventDefault можно оставить безусловным — Enter не должен переводить фокус в любом случае); если `at === -1`, не глушить `Tab`, дать браузеру перевести фокус естественно (и вызвать `hideMentions()` — раз `@`-контекст потерян, дропдаун показывать нечего).

**Severity: MEDIUM** · **File:Line:** `infra/ai-council/ui/index.html:1674-1681` (`markMentionSel`)
**Pattern:** дублирующийся `id` в DOM → сломанный `aria-activedescendant`
**Why:** `markMentionSel()` присваивает `el.id = "h-mention-opt"` только выбранному элементу, но никогда не снимает `id` с ранее выбранных при смене `mentionSel` (нет `else`-ветки с `removeAttribute("id")`). При навигации ↑/↓ по списку в DOM накапливаются НЕСКОЛЬКО элементов с одинаковым `id="h-mention-opt"` одновременно — невалидный HTML. `aria-activedescendant` резолвится браузером/screen-reader'ом через `getElementById`, который возвращает только ПЕРВЫЙ элемент с этим id в документе — то есть после первого же перемещения выбора скринридер продолжит озвучивать/подсвечивать первый когда-либо выбранный пункт, а не реально текущий. Это хуже, чем отсутствие `aria-activedescendant` вовсе: пользователю screen reader'а сообщается неверная информация о текущем выборе, при том что визуально (класс `.sel`) подсветка двигается корректно — расхождение между видимым и озвученным состоянием.
**Repro (live, Playwright MCP, подтверждено):** набрать `@te` в `#h-body` (дропдаун с 8 карточками) → отправить 3× `KeyboardEvent('keydown', {key:'ArrowDown'})` на `#h-body` → `document.querySelectorAll('#h-mention-opt').length === 4` (4 элемента с одинаковым id одновременно в DOM после всего 3 перемещений).
**Fix:** в `markMentionSel` снимать id у не выбранных: `else if (el.id === "h-mention-opt") el.removeAttribute("id");` — либо использовать заранее присвоенный уникальный `id` на каждый пункт (`h-mention-opt-${i}`) и указывать в `aria-activedescendant` актуальный id по индексу, не общий константный id.

**Severity: MEDIUM** · **File:Line:** `infra/ai-council/ui/index.html:2650-2653` (`tabFromHash`), проявляется также через слушатель `:2654-2657`
**Pattern:** необработанное исключение (`URIError`) в валидации, обходящее собственный whitelist-guard
**Why:** `tabFromHash()` вызывает `decodeURIComponent(location.hash.slice(1))` без `try/catch`. Для хэша с невалидной `%`-последовательностью (`#%zz`, `#%`, `#%E0%A4%A`) `decodeURIComponent` синхронно бросает `URIError`, что происходит РАНЬШЕ, чем отработает задуманная защита `TABS.includes(name) ? name : null` — то есть ровно тот механизм, который должен превратить «мусорный хэш» в безопасный `null`/`"home"`, сам не переживает один из классов мусорного хэша. На верхнем уровне (`:2658`, после уже выполнившихся `render()`/`renderTabDoc()`/`connectStream()`) это не роняет уже отрендеренное приложение, но: (а) не нормализует хэш в адресной строке под невалидным значением; (б) при ПОСЛЕДУЮЩЕЙ ручной правке хэша пользователем (после загрузки, через слушатель `hashchange`) даёт необработанное исключение в консоли на каждый такой ввод.
**Repro (live, Playwright MCP, подтверждено):** `navigate('http://127.0.0.1:8790/#%zz')` → `browser_console_messages(level: "error")` возвращает `URIError: URI malformed at decodeURIComponent ... at tabFromHash (...:2651:16) at (...:2655:16)`. Приложение остаётся кликабельным (nav-кнопки — статический HTML, не зависят от этого кода), но хэш не нормализуется, вкладка не переключается, ошибка попадает в консоль без обработки.
**Fix:** обернуть `decodeURIComponent` в `try/catch` внутри `tabFromHash`, возвращая `null` при `URIError` — ровно то же поведение, что уже задумано для прочих невалидных значений:
```js
function tabFromHash() {
  let name;
  try { name = decodeURIComponent(location.hash.slice(1)); } catch (e) { return null; }
  return TABS.includes(name) ? name : null;
}
```

## Опровергнутые аргументы

- Гипотеза автора задачи «`activeTab` присваивается ДО проверки `stopGraph3d`, что может маскировать off-by-one баг» (`index.html:327-328`) — **опровергнута чтением кода**: `if (activeTab === "graph" && name !== "graph") stopGraph3d();` выполняется, используя ЕЩЁ СТАРОЕ значение `activeTab`, и только СЛЕДУЮЩЕЙ строкой `activeTab = name;` происходит переприсвоение. Порядок корректный, off-by-one отсутствует.
- Гипотеза «два независимых event-хендлера (`form.onsubmit` и клик по кнопке) могут запустить `submitHome()` параллельно до того, как `sending=true` успеет проставиться» — **опровергнута живой проверкой**: оба пути (Cmd+Enter → `requestSubmit()`, клик/дубль-клик по `type="submit"`-кнопке) сходятся в ОДНО и то же DOM-событие `submit` формы → один и тот же обработчик; JS run-to-completion гарантирует синхронную установку `sending=true`/`goBtn.disabled=true` до первого `await` внутри `submitHome`. Живой тест: 3× `requestSubmit()` подряд и отдельно нативный `dblclick()` по кнопке — в обоих случаях ровно 1 `POST /api/tasks`.
- Гипотеза «`#<script>`/произвольная строка в хэше могла бы стать вектором self-XSS» — **опровергнута чтением кода**: значение хэша никогда не попадает в `innerHTML`/любой DOM-синк, используется только для сравнения со статическим whitelist `TABS` и для `history.replaceState`. Единственная найденная проблема с хэшем — не безопасность, а необработанное исключение при `%`-мусоре (см. находку MEDIUM выше), это другой угол атаки (границы/устойчивость, не безопасность).

### Находки

**Severity: LOW** (pre-existing, НЕ регрессия фикса, раунд 2 не блокирует) ·
**File:Line:** `infra/ai-council/ui/index.html:1749-1756` в коммите `7121d80a6`
(логика идентична в `d872e30bf`, раундом 1 не флаговалась)
**Pattern:** вставка упоминания по «чужому» `@` (stale @-контекст)
**Why:** ветка Enter/Tab вычисляет `at = before.lastIndexOf("@")` по позиции курсора,
но валидирует только `at === -1`, не проверяя, что между `@` и курсором нет пробельных
символов (как это делает `oninput`). Если в тексте есть более ранний `@`-токен, курсор
перемещён после него без ввода (стрелки/мышь не закрывают дропдаун), а дропдаун открыт
по другому, «живому» `@` — Tab/Enter глушится и вставляет результат ЧУЖОГО поиска в
позицию старого токена.
**Repro (live, подтверждено):** `#h-body` = `aa@dom @te` (дропдаун открыт по `@te`,
8 опций) → `setSelectionRange(6,6)` (курсор после `dom`) → Tab → текст стал
`aa@[AGT-ENV: Агентная система — архитектурные gaps (бывш. AGENT_SYSTEM.md §21–22)]  @te`
— токен `@dom` заменён карточкой из результатов поиска по `te`, «живой» `@te` остался
глухим текстом. Поведение побайтово то же в коде до фикса (`if (at !== -1 &&
mentionSel >= 0) pickMention(mentionHits[mentionSel], at)`) — фикс лишь добавил
`at === -1` guard, семантику вставки не менял.
**Fix (на будущую итерацию, не блокер раунда 2):** в ветке Enter/Tab зеркалировать
валидацию `oninput` — `const term = before.slice(at + 1); if (at === -1 || /\s/.test(term))
{ hideMentions(); return; }` — либо использовать запомненный `atPos` из замыкания
`runMentionSearch` вместо пересчёта `lastIndexOf`, и закрывать дропдаун при покидании
живого контекста.
