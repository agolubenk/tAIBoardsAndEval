# Headroom — контур разработчика

Инструмент ассистента (Claude Code / Continue / ИИ-консилиум), а не часть продукта. Продуктовый контур — `../runtime/`.

## Что это

| | |
|---|---|
| Контейнер | `headroom-default`, образ `ghcr.io/headroomlabs-ai/headroom:0.41.0` — версия закреплена в манифесте `~/.headroom/deploy/default/manifest.json`, не `:latest` |
| Адрес | `127.0.0.1:8787` на хосте; на него указывает `ANTHROPIC_BASE_URL` — в `.claude/settings.local.json` основной копии и в управляемом блоке `~/.zshrc`/`~/.bashrc` (его пишет `headroom install apply`), поэтому сессии в worktree, где нет `settings.local.json`, тоже идут через прокси |
| Управление | `npm run ai-pipeline:start` / `:stop` / `:status` / `:doctor` / `:logs`; конфиг — `npm run ai-pipeline:headroom-apply` (`infra/scripts/dev-ai/ai-tooling-pipeline.sh`). `:status` показывает версии, фактический конфиг и расход по аккаунтам |
| MCP `headroom` | `headroom_compress` / `headroom_retrieve` / `headroom_stats` — stdio-процесс `headroom mcp serve` на хосте (user-scope MCP Claude Code и сервер `headroom` в MCP-хабе `infra/mcp-hub/`), а не этот контейнер. CLI на хосте — той же версии, что образ: `uv tool install 'headroom-ai[all]==0.41.0'` |
| Дашборд | <http://127.0.0.1:8787/dashboard>; сырые цифры — `/stats`, история — `/stats-history` |
| История | `~/.headroom` хоста (рабочий каталог контейнера): `proxy_savings.json` — пожизненные итоги (переживают всё), `savings_events.jsonl` — журнал запросов. **Журнал Headroom хранит только 30 дней** (`MAX_RETENTION_DAYS` в `savings_ledger.py`) и при сжатии файла стирает старое — новый процесс делает это при первой же записи (2026-10-15 при первом рестарте ушли 309 событий за 15–16.09). Поэтому вся история копится в архиве `~/.headroom-archive/events/<ГГГГ-ММ>.jsonl` (дописывают `ai-pipeline:start`, `:status`, `:headroom-apply`; строки сверяются по хэшу, дублей нет; достаточно запуска реже, чем раз в 30 дней). Архив начат с 15.09 — с первого дня журнала. Перед заменой контейнера `headroom-apply` ещё и копирует весь `~/.headroom` в `~/.headroom-backups/<время>/` |

В `/tmp/headroom-home/…` контейнера смонтированы домашние каталоги хоста (`~/.claude`, `~/.codex`, `~/.gemini`,
`~/.headroom`, `~/.config/opencode`, `~/.config/litellm`) — ради удобства разработчика, а не изоляции.

## Конфигурация — что включено и почему

Канон — `cmd_headroom_apply` в `ai-tooling-pipeline.sh`; ручная команда `headroom install apply` в обход него
сотрёт часть флагов.

| Настройка | Значение | Почему (замер 2026-10-15, 0.39.1, 10,5 ч трафика) |
|---|---|---|
| Режим | `--mode cache` | Кэш префикса Anthropic: hit rate 94,7 %, $941 условной экономии против $5 от сжатия. `token` переписывает прошлые реплики и сбрасывает этот кэш |
| Сжатие | `HEADROOM_LOSSLESS=1` — только без потерь, без маркеров CCR | Сжатие с потерями давало 0,26 % входа (685 тыс. из 262 млн токенов), а модель получала обрезанные выводы вида «[111 lines omitted: 1 ERROR, 3 FAIL…]» |
| Kompress | выключен (`HEADROOM_DISABLE_KOMPRESS=1`) | В lossless не нужен. У 0.39.1 он был сломан: кэш HuggingFace не пишется под uid 501 — 446 неудачных загрузок. Без него контейнер занимает 285 МиБ вместо 882 |
| Кэш ответов | выключен (`--no-cache`, дописывается в `proxy_args` манифеста — `apply` такого флага не знает) | 383 записи, 0 попаданий; риск отдать сохранённый ответ на повторный запрос — health-check консилиума уже получал старый «ok» за 20 мс |
| Лимитер | `HEADROOM_RPM=600` — общий тормоз, а не квота | С 0.40 лимит без токена считается по адресу клиента, а из Docker все клиенты хоста приходят с одного адреса шлюза: при умолчании 60 запросов/мин Claude Code с субагентами, консилиум и Continue делили бы одну корзину и упирались в неё. 10 запросов/с обычная работа не достигает, а зацикленный клиент — достигает за секунды. Квоты держат провайдеры, у консилиума — свои лимиты вызовов в коде |
| Таймаут запроса | `HEADROOM_REQUEST_TIMEOUT=600` | По умолчанию 300 с, а облачные роли консилиума ждут модель до 420 с (`[models.cloud] request_timeout_seconds`): дольше 300 с прокси отвечал `502 proxy_error` — 2026-10-15 так оборвались два ревью GLM-4.7 с рассуждениями (300,9 и 301,7 с) |
| Маяк | выключен (`HEADROOM_BEACON=off`) | Маяк по умолчанию шлёт счётчики (токены, модели, сбои) на `headroom-beacon.workers.dev`. Проверка обновлений на PyPI оставлена — по ней видно новые версии |
| Телеметрия | `--no-telemetry` | — |
| HTTP/2 | `--no-http2` | Обход `SSLV3_ALERT_BAD_RECORD_MAC` при отмене многих параллельных стримов |
| Словари tiktoken | `TIKTOKEN_CACHE_DIR=/tmp/headroom-home/.headroom/tiktoken-cache` — в смонтированном `~/.headroom` | По умолчанию лежат в `/tmp` контейнера (3,5 МБ) и пропадают при каждом пересоздании: на медленной сети первые два запроса после старта ждали по 10 с на словарь. Первый раз `headroom-apply` заполняет каталог из работающего контейнера. Путь привязан к `container_home` лаунчера 0.41 — сменится он, словари просто скачаются заново. Как и все `--env`, значение попадает и в управляемый блок `~/.zshrc`; на хосте это лишь место кэша словарей |

## Кто идёт через прокси

| Клиент | Через Headroom | Метка аккаунта | Как подключён |
|---|---|---|---|
| Claude Code (основная копия и worktree) | да | без метки | `ANTHROPIC_BASE_URL`; раскладку по проекту Headroom больше не ведёт (запись `HR_Helper-v2` застыла на 2026-08-07): трафик без метки — это Claude Code |
| Continue, облачные модели GLM | да | `continue-zai-coding`, `continue-zai-general` | `apiBase` + заголовки, см. ниже |
| ИИ-консилиум (Z.AI) | да | `ai-council` | `infra/ai-council/config.toml` → `[models.cloud.headroom]` |
| Хук DAMS (GLM-бриф) | нет | — | `.claude/scripts/glm_client.py` ходит в `api.z.ai` напрямую |
| Локальные модели консилиума (Ollama) | нет | — | Промпты — system + одно user-сообщение: в cache-режиме новейшее user-сообщение уходит как есть, выигрыша нет, а прокси добавил бы хоп и точку отказа |
| Gemini (консилиум) | нет | — | другой протокол, маршрут его не понимает |
| Kimi Code | да | `kimi-code` | `base_url` + `custom_headers` (два `x-headroom-*`) у провайдеров в `~/.kimi-code/config.toml`; аварийный обход — алиас `kimi-direct/*` через `/models` |
| Copilot Chat, Codex | нет | — | у расширений нет настройки адреса либо биллинг подпиской; Copilot возможен через `headroom wrap vscode` + `headroom copilot-auth login` (вход владельца) — не подключено |

Расход по меткам: `npm run ai-pipeline:status` (с последнего рестарта прокси) или `/stats` → `savings.per_project`.

### Контракт для OpenAI-совместимых клиентов (Z.AI и др.)

- **Метка аккаунта** — префикс пути: `http://127.0.0.1:8787/p/<метка>/…`. Одна метка на аккаунт или ключ, тогда
  расход разных аккаунтов виден раздельно.
- **Куда идти дальше** — два заголовка в каждом запросе: `x-headroom-base-url: https://api.z.ai/api/coding/paas/v4`
  (General API — `…/api/paas/v4`) и `x-headroom-original-path: /chat/completions`. Без них прокси клеит к
  `OPENAI_TARGET_API_URL` свой путь `/v1/chat/completions`, у Z.AI получается `/v4/v1/chat/completions` → 404.
  Проверено и на 0.41.0.
- Ключ провайдера уходит обычным `Authorization`: прокси его пересылает, а не подменяет. Тела ошибок провайдера
  (Z.AI `1310`, `1113`, `401`) 0.41.0 отдаёт клиенту без изменений — по ним консилиум различает квоту и ключ.

### Обновление и откат

1. CLI на хосте — первым: `uv tool install --force 'headroom-ai[all]==<версия>'`. Прокси ≥ 0.40 не слушает
   `0.0.0.0` без токена, пока лаунчер не передаст `HEADROOM_ALLOW_UNAUTHENTICATED_BIND=1`, а лаунчер старого CLI его
   не передаёт: новый образ со старым CLI не поднимется. `headroom-apply` сверяет версии и откажется работать при
   расхождении.
2. Пробный контейнер новой версии на свободном порту с отдельным рабочим каталогом (общий `~/.headroom` не трогать)
   и гейты: Claude Code насквозь (`ANTHROPIC_BASE_URL=http://127.0.0.1:<порт> claude -p --model haiku …` с одним
   вызовом инструмента), тела ошибок Z.AI напрямую и через прокси, `/v1/compress` и `/stats` с хоста, логи без
   обращений к HuggingFace.
3. `HEADROOM_IMAGE=ghcr.io/headroomlabs-ai/headroom:<версия> npm run ai-pipeline:headroom-apply` (или поднять
   значение по умолчанию в скрипте). Команда останавливает прокси, копирует `~/.headroom`, дописывает архив
   событий, применяет конфиг, пересоздаёт контейнер, ждёт `/readyz` и сверяет историю: пожизненные итоги не меньше
   копии, а все события копии за последние 29 дней (запас к окну Headroom) — в журнале, иначе выходит с ошибкой.
   Не снялась копия, упал `apply` или новый конфиг не ответил на `/readyz` за 90 с — команда возвращает прежний
   манифест из копии и поднимает прокси на нём. Копии не удаляются сами (~120 МБ каждая, в основном логи) —
   старые из `~/.headroom-backups/` можно удалить вручную. Пока контейнер
   пересоздаётся (20–40 с), клиенты получают отказ соединения — Claude Code и консилиум повторяют запрос сами.
   Процесс `headroom mcp serve` в MCP-хабе обновляется `bash infra/scripts/dev-ai/mcp-hub.sh restart hub`, в сессиях
   Claude Code — при следующем старте сессии или `/mcp`.

**Откат:** CLI прежней версии (`uv tool install --force 'headroom-ai[all]==0.39.1'`), затем
`HEADROOM_IMAGE=ghcr.io/headroomlabs-ai/headroom:0.39.1 npm run ai-pipeline:headroom-apply`. Образ остаётся
локально. Если новая версия переписала формат истории — остановить прокси и вернуть файлы из
`~/.headroom-backups/<время>/` до запуска старой версии.

## Для данных продукта не использовать

HR-данные в этот контур не отправляются ни в каком окружении, в том числе на локальном стеке с копией боевых
данных. Backend это проверяет сам: адреса `127.0.0.1`, `localhost`, `host.docker.internal`, `headroom-default` в
`HEADROOM_RUNTIME_URL` отклоняются при старте с ошибкой в логе, сжатие остаётся выключенным
(`apps/backend/src/modules/ai/config/ai-context-compression.config.ts`).

Продукту нужен `headroom-runtime` — runbook в `../runtime/README.md`.
