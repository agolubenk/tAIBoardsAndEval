# HR Helper Ops — консоль мониторинга, алертов и перезапуска контейнеров

Отдельная система наблюдения за продуктом. Она **не связана с продуктом** ни кодом, ни базой, ни
учётками (решение владельца 2026-10-06). Сейчас работает локально, потом без переделки
переезжает на бесплатный хостинг вроде Vercel. Оформление — в стиле главной страницы продукта:
стеклянные панели, капсулы, токены `--lg-*`. Структура разделов взята из прототипа
`prototipes/ops-atlas-console.html`, логика сборщиков — из `prototipes/local cloude monitoring service`.

| Раздел           | Что внутри                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------- |
| Обзор            | что горит, доступность сервисов за 30 дней, серверы, последние перезапуски и деплои      |
| Инфраструктура   | серверы (агенты), контейнеры, метрики CPU/RAM/диск/nginx, **перезапуск контейнера**      |
| Мониторинг       | внешние HTTP-проверки (health-JSON, ключевая строка), TLS-сертификаты                    |
| Алерты           | активные и история, правила, каналы (Telegram / email / webhook с HMAC), журнал доставки |
| Инциденты        | автоматические из критичных алертов и ручные, хронология, заметки                        |
| Деплои           | живой ход деплоя по событиям скрипта; GitHub Actions (`deploy-contabo.yml`), упавший — алерт |
| События          | единая лента: алерты, действия с причинами, настройки, входы                             |
| Отчёты ИИ-совету | `hrh.ops.report/v1`: предпросмотр, отправка по расписанию, история                       |
| Настройки        | общие, агенты, пользователи (своя администрация), GitHub, профиль                        |
| `/status`        | публичная страница статуса (выключена по умолчанию)                                      |

## Как устроено

```
 сервер (Contabo)                                консоль (локально или Vercel)
┌───────────────────────────┐   HTTPS, HMAC   ┌─────────────────────────────────────┐
│ hrh-ops-agent (python)    │ ──────────────► │ POST /api/agent/report               │
│  метрики хоста, docker,   │                 │  → состояние, метрики, правила,      │
│  nginx, бизнес-метрики    │ ◄────────────── │    алерты, инциденты, уведомления    │
│  docker restart <имя>     │  команды в      │  ← в ответе: команды перезапуска     │
└───────────────────────────┘  ответе         │                                      │
   входящих портов нет                        │ планировщик (тик): HTTP/TLS-проверки,│
                                              │ «агент молчит», GitHub, дайджест,    │
  домены продукта ◄──── внешние проверки ──── │ отчёт ИИ-совету                      │
                                              └──────┬──────────────┬────────────────┘
                                   Telegram / email / webhook    продукт: ИИ-совет
                                                                 (приёмник — следующий этап)
```

- **Агент сам приходит к консоли.** Консоль никогда не подключается к серверу. На сервере не
  открываются порты. Консоль может жить на Vercel, где фоновых процессов нет.
- **Перезапуск идёт через очередь команд.** Консоль ставит команду, агент забирает её в ответе на
  следующий отчёт (каждые 15 с), выполняет `docker restart -t 30 <имя>` и присылает результат.
- **Внешние проверки независимы от агента.** Если сервер лёг целиком, агент молчит, но
  проверки доменов (из консоли) и правило «агент молчит» это фиксируют.
- **База — libSQL.** Локально это файл SQLite `data/ops.db`, на Vercel — Turso (бесплатный тариф).
  Миграции и клиент одни и те же.

## Запуск локально

```bash
cd infra/ops-console
npm ci
cp .env.example .env        # впишите OPS_ADMIN_EMAIL, OPS_ADMIN_PASSWORD (≥ 10 символов)
npm run build && npm start  # http://localhost:8797 — API, интерфейс и планировщик в одном процессе
```

Режим разработки: `npm run dev`. API работает на `:8797`, Vite с HMR — на `http://localhost:5180`.
Проверки: `npm run typecheck`, `npm test` (сквозной сценарий на временной БД + чистая логика).

Консоль не входит в npm workspaces продукта: у неё свой `package-lock.json`, корневые `npm ci`,
turbo и CI продукта её не затрагивают.

## Подключение сервера (локальный контроллер)

**Одноразовым кодом** (нужен https-адрес консоли `OPS_PUBLIC_URL`). Команду установки выдаёт
**Настройки → Агенты → «Команда установки»**:

```bash
curl -fsSL https://<консоль>/agent/install.sh | sudo OPS_ENROLL_CODE=<код> bash
```

Код:

- 32 символа, действует 15 минут и только один раз;
- в базе хранится только его sha256;
- подбор ограничен: не больше 10 неудачных обменов с одного IP и 100 всего за 15 минут.

Что делает скрипт:

1. Скачивает файлы агента с этой же консоли и сверяет их sha256.
2. Обменивает код на новый секрет агента. Секрет не проходит через браузер, прежний перестаёт
   действовать.
3. Пишет `/etc/hrh-ops-agent.env` с правами 600 для root. Прежний файл сохраняется как
   `.bak.<время>`.
4. Запускает службу `hrh-ops-agent`.

Если https-адреса нет, команда не выдаётся. Тогда подключайте вручную:

1. В консоли: **Настройки → Агенты → «Агент»**. Секрет и готовые строки для env показываются
   **один раз**.
2. На сервере из каталога `agent/`:
   ```bash
   sudo ./install.sh                       # пользователь hrh-ops, /opt/hrh-ops, systemd-юнит
   sudo nano /etc/hrh-ops-agent.env        # вставить выданные строки (права 600)
   sudo -u hrh-ops python3 /opt/hrh-ops/hrh-ops-agent.py --dry-run   # что уйдёт, без отправки
   sudo systemctl enable --now hrh-ops-agent && journalctl -u hrh-ops-agent -f
   ```
3. Полезные переменные агента (`agent/hrh-ops-agent.env.example`):
   - `OPS_COMPOSE_PROJECT` — основной стек (у HR Helper — `backend`). Агент ≥ 1.5 показывает
     контейнеры всех compose-проектов хоста и без проекта; основной идёт первым, а остановленный
     контейнер соседнего стека — алерт, только если по restart policy он должен работать. Вывод
     healthcheck уходит только у основного стека (у чужого он может процитировать секрет).
     `OPS_CONTAINER_EXCLUDE` — маски имён, которые не показывать;
   - `OPS_RESTART_PROJECTS` — чьи контейнеры можно перезапускать (по умолчанию — только основной
     проект; пустой `OPS_COMPOSE_PROJECT` — все, как раньше). Перед `docker restart` агент заново
     читает проект контейнера и перезапускает по Id;
   - `OPS_RESTART_ALLOW` / `OPS_RESTART_DENY` — второй рубеж: какие контейнеры хост вообще
     разрешает перезапускать;
   - `OPS_DISK_MOUNTS`; трафик nginx за минуту — `NGINX_ACCESS_LOG` (nginx на сервере) или лог
     контейнера через `docker logs` (nginx в Docker: сервис compose `nginx` находится сам, иначе
     `NGINX_CONTAINER`); в консоль уходят счётчики и шаблоны путей (`/api/v1/candidates/:id`), не
     id и не имена файлов. `BUSINESS_CMDS` — числа из команд на хосте, раз в `BUSINESS_INTERVAL_SEC`
     (300 с; для HR Helper — 3600): `agent/hrh-business.sh companies|users|db_size_mb` (активные
     компании и пользователи, размер базы; только чтение, таймаут 5 с);
   - `OPS_NGINX_CONTAINERS` — откуда брать домены (агент ≥ 1.5, модуль `hrh_ops_edge.py`): раз в 10 мин
     `docker exec <nginx> nginx -T` → `server_name`/`listen`, раз в 6 ч — рукопожатие с SNI на адрес входа этого
     nginx на самом хосте (срок, издатель, ошибка проверки). Пусто — сервис compose `nginx` или образ nginx в любом
     проекте, маски — только эти, `-` — выключено. Уходят имя, контейнер, порт и итог проверки; конфигурация nginx
     и пути к ключам — нет. Список шлётся при изменении и раз в час (`domains`, не больше 100 имён — nginx
     основного стека первым: он же источник имени, если его отдают два nginx), отказ `nginx -T` и обрезка списка — в
     каждом отчёте (`domainsFailed`, `domainsTotal`). Срок недоверенного или выписанного на другое имя сертификата
     алерт не открывает и не закрывает. `docker exec` в соседний стек — тот же доступ, что у группы docker, но
     автоматический: на хосте нужен runc ≥ 1.1.12 (CVE-2024-21626); не нужно — маска только своих nginx. Тесты
     сборщиков: `python3 -m unittest discover -s agent`.
   - **VPN (WireGuard, агент ≥ 1.6)** — отдельный корневой сборщик `hrh-ops-vpnd.py` (юнит `hrh-ops-vpn.service`,
     установщик включает его сам, если на хосте есть интерфейс WireGuard): раз в 30 с `wg show all
     allowed-ips|latest-handshakes|transfer|endpoints` (ключи — только в памяти; `dump`, `private-key`,
     `preshared-keys` не вызываются) и прирост conntrack по адресам туннеля; раз в 5 мин — ping по туннелю
     активным пирам (RTT, потери). Пишет `/run/hrh-ops-vpn/vpn.json` (0640, группа `hrh-ops`), агент читает файл
     (`hrh_ops_vpn.py`, `OPS_VPN_FILE`, `-` — выключить). Все роли видят пиров: на связи, рукопожатие, скорость,
     трафик, RTT; **только владелец** — внешние адреса пиров и top-50 направлений за час и сутки (адрес, PTR-имя,
     протокол/порт, байты, соединения; таблица `agent_vpn`, `GET /infra/agents/:id/vpn`). `OPS_VPN_VIEWERS` —
     e-mail через запятую — сужает круг владельцев (по SSO владелец — любой суперадмин продукта, а при полном
     туннеле направления — это история посещений); пусто — все владельцы. Направления агент присылает не чаще раза
     в 5 мин, консоль хранит одну строку на агента и удаляет её через 25 ч без обновлений; в списках обзора и
     инфраструктуры блока `vpn` нет. Имена пиров — `OPS_VPN_PEERS=10.77.0.2=Mac,…`; PTR — в фоне с кэшем на сутки
     и только подтверждённый прямым запросом (FCrDNS: поддельный PTR не показывается), `OPS_VPN_PTR=0` — не
     спрашивать. Байты направлений — только с `net.netfilter.nf_conntrack_acct=1`, без него — число соединений.
     Корзины окон — `vpn-flows.json.gz` в каталоге состояния агента (каталог 0700, файл 0600), пишутся раз в 15 мин.
     Сборщик работает от root только с `CAP_NET_ADMIN`/`CAP_NET_RAW`; конфиги WireGuard, env агента, shadow, ssh,
     сертификаты, `/opt/hr-helper` и docker ему не видны (`InaccessiblePaths`). **Выключить на хосте:**
     `systemctl mask --now hrh-ops-vpn` — повторное подключение агента маску не снимает.

Агенту нужен только stdlib `python3` (≥ 3.8) и docker CLI. Входящих портов он не открывает.

Сбор docker и бизнес-метрик идёт в фоновом потоке. Отчёт уходит по расписанию, даже если docker
CLI тормозит или dockerd завис: снимок контейнеров годен 3 интервала, дальше в отчёте приходит
`dockerError`. Консоль тогда замораживает контейнерные алерты (состав неизвестен), а через 4 таких
отчёта поднимает «Docker не отвечает». Перезапуск выполняется в отдельном потоке и тоже не
задерживает отчёты.

### Сервер при локальной консоли

Пока консоль работает на ноутбуке, сервер не может достучаться до неё напрямую. Агент ходит в
`http://127.0.0.1:8797` на сервере, а обратный SSH-туннель пробрасывает этот порт на консоль:

```bash
scripts/connect-agent.sh install <ssh-цель> contabo-prod   # один раз: агент + /etc/hrh-ops-agent.env
scripts/connect-agent.sh tunnel  <ssh-цель>                # держать запущенным, пока консоль локальная
scripts/connect-agent.sh daemon  <ssh-цель>                # или в фоне с переподключением (нужен SSH-ключ)
```

Env агента (с секретом) консоль кладёт в `data/<agent-id>.agent.env`, права 600, в git не попадает.

### Прод (VPS): сервис ops-console в docker-compose.contabo.yml

На проде консоль — сервис `ops-console` стека (без профиля): наружу только через nginx
`https://<OPS_DOMAIN>`, агент на хосте ходит сам на `127.0.0.1:8797` — **тот же URL, что
использовался через туннель**, env агента не меняется. Туннель после переезда останавливаем
(`scripts/connect-agent.sh stop`), флаппинг «Агент сервера молчит» уходит вместе с ним.

Переезд с ноутбука (DNS → сертификат → `.env.contabo` → перенос SQLite-базы → деплой) —
по шагам в `docs/ops/deploy-contabo.md` → «Ops-консоль на проде». Ключевое:
`OPS_ENCRYPTION_KEY` на проде = ключ локальной консоли (иначе секреты каналов/агентов/GitHub
в перенесённой базе не расшифруются), а базу копируем только при остановленной консоли.

### Telegram-бот и личные подписки админов

**Бот консоли** (владелец, «Настройки → Интеграции → Telegram-бот»): токен от @BotFather. На проде
(явный `OPS_PUBLIC_URL` с https) консоль сама ставит вебхук `…/api/telegram/webhook` с
`secret_token` и `max_connections=1`. Вебхук ставится, только если у бота его нет или он уже наш:
иначе — «Забрать вебхук» явно, так локальная консоль на копии прод-базы не перехватит прод.
Без публичного https (локально) бот опрашивается `getUpdates` из процесса, и только пока у
бота нет вебхука. Затем владелец задаёт **пароль бота** (свой ≥ 12 символов или
сгенерированный, показывается один раз).

**Личная подписка** («Настройки → Профиль → Telegram», любая учётка, в том числе вход через
платформу):

1. «Подключить Telegram» — одноразовая ссылка `t.me/<бот>?start=…` на 10 минут (на телефоне
   кнопка, на компьютере ещё и QR).
2. Бот присылает код из 6 цифр, его вводят в профиле. Так консоль убеждается, что Telegram
   принадлежит вошедшему в учётку: подсмотренная ссылка без сессии жертвы ничего не даёт.
3. Пароль бота вводится кнопкой «Ввести пароль» (Mini App `/tg/password`, подпись `initData`).
   Пароль не становится сообщением в чате. Без https (локально) — сообщением, бот удаляет его
   до проверки.

Уведомления идут подписке, только пока: учётка активна, доступ из платформы подтверждён (SSO —
не старше суток), подтверждена **текущая** версия пароля бота. Смена пароля — всем подписчикам
просьба ввести новый, до ввода уведомлений нет. Отключение учётки, отзыв доступа в платформе
(сверка в тике каждые 15 минут, даже если человек не заходит в консоль), `/stop`, блокировка
бота — подписка приостанавливается и возобновляется только вручную, с вводом пароля.
Приостановленную владельцем (или за 5 неверных паролей за сутки) снимает только владелец.
20 неверных паролей за сутки по всем подпискам или вебхук бота на чужом адресе (проверка каждые
5 минут) — ввод пароля замораживается, владельцу уходит сообщение в каналы, кроме Telegram.

**Отчёты и кнопки в Telegram.** Суточный отчёт (каналам и подпискам с включённым суточным отчётом)
приходит одной карточкой: статус и главная причина, что горит сейчас, доступность, инциденты и
алерты, ресурсы, контейнеры, деплои, TLS (только если до срока < 21 дня или ошибка), «что сделать».
Под ней кнопки: «📋 Больше информации» — тот же отчёт, что получает ИИ-совет, по разделам;
«📈 Графики» — снимки за тот же период альбомом (CPU, память, диск по хостам, задержка проверок, 5xx
nginx; только графики с данными; PNG 900 px рисует сервер — resvg в пуле libuv, шрифт DejaVu в
образе; набор кэшируется на минуту); «⚡ Срочный отчёт» — свежий отчёт прямо сейчас. То же —
командами `/report` и `/charts`. Под карточкой алерта, пока он горит: «✋ Беру в работу» и
«🔕 Тишина 1 ч» (роль не ниже оператора; первый взявший остаётся ответственным, тишина с кнопки
только продлевает) и «🔗 Открыть в консоли»; после нажатия — из бота или из консоли — карточка
показывает «В работе: …» / «Тишина до …», нажатая кнопка уходит.

Кто может: в личке — подписчик с подтверждённым паролем бота. В группе это уже рассылка: роль не
ниже оператора и только группа, подключённая каналом консоли с тем же ботом и числовым chat id;
каждая такая отправка — в журнал. Отчёт и графики — не чаще раза в минуту на чат, не больше 5 за 5
минут на человека, тяжёлая работа — по одной на консоль (очередь до 3) и после ответа вебхуку.

**Меню бота.** `/menu` (и `/start` у подписчика) — сводка «что горит» и кнопки разделов со
счётчиками: алерты (горящие и закрытые за сутки), инциденты, серверы, проверки, деплои, TLS, отчёт
сейчас, графики. Переходы правят одно сообщение: список → карточка → «Назад» / «Обновить» / «Меню» —
лента в чате не растёт. Карточки: алерт (факты, подсказка, инцидент; «Беру в работу», «Тишина 1 ч»),
инцидент (затронуто, рядом по времени, хронология; «Взять себе»), сервер (CPU/RAM/диск/иноды/сеть,
проблемные контейнеры с перезапусками за 10 мин; «Контейнеры», «Графики хоста»), контейнер (состояние,
память, healthcheck, последний ручной перезапуск и его статус; «Перезапустить»), проверка (доступность,
p50/p95/p99, фазы запроса, ошибки по причинам; «Проверить сейчас» — не чаще раза в 15 с). «Больше
информации» под отчётом открывает подробный отчёт по разделам в одном сообщении (+ «Весь отчёт»).
Права — как у отчётов: подписчик с подтверждённым паролем; в группе — оператор и только в группе-канале
консоли; действия — роль не ниже оператора; перезапуск — оператор и только в личке; не больше 60 нажатий
в минуту на человека. Список команд у уже подключённого бота обновляется сам при плановой проверке вебхука.

**Перезапуск из бота** (решение владельца 2026-10-11) — тот же путь и те же проверки, что в консоли
(`server/containers/restart.ts`): «Перезапустить» в карточке контейнера → причина сообщением (3–300
символов) → у контейнера с данными — его точное имя → команда в той же очереди агента → ответ с номером
команды и кнопкой статуса. Одна кнопка — один контейнер, массового перезапуска нет. Диалог живёт 10 минут
(состояние — в `settings`, `tg-dialog:<Telegram id>`), роль и подписка проверяются заново на каждом шаге;
неверное имя — отказ и конец диалога; «Отменить» под вопросом. В ленте и хронологии инцидента запрос из
бота помечен «(из Telegram)».

**Групповые каналы** («Алерты → Каналы → Telegram-бот») работают как раньше и без пароля бота.
«Найти чат» показывает только группы и каналы: личные уведомления — через профиль. Если у канала
тот же бот, что у подписок, getUpdates занят вебхуком, и консоль показывает группы, которые
видел вебхук.

## Проверки, техработы и хранение

- **Типы проверок.**
  - **HTTP(S):** статус, ключевое слово и фазы запроса (DNS, соединение, TLS, первый байт). Каждая
    проверка открывает новое соединение: переиспользованный keep-alive сокет спрятал бы
    соединение и TLS.
  - **TCP** (`хост:порт`): только установка соединения.
  - **DNS:** имя резолвится записью нужного типа; «ожидаемое значение» — подстрока ответа.

  HTTP и TCP проходят через защиту исходящих запросов: частные адреса доступны только из
  «Внутренних адресов». DNS-проверка идёт через публичные резолверы (1.1.1.1, 8.8.8.8), а имена из «Внутренних
  адресов» — через резолвер сервера; ответ A/AAAA с внутренним адресом — сбой без самого адреса, пока имя или адрес
  не внесены во «Внутренние адреса». Ошибки проверок внутренние адреса не показывают.

- **Домены.** Вкладка «Домены» в инфраструктуре сводит в одну строку на имя внешнюю HTTPS-проверку
  (`/monitors/tls`) и домены nginx с хостов (`/infra/domains`, таблица `agent_domains`); состояние — худшее из двух.
  Правило `tls_expiry` по домену без внешнего монитора считает агентский срок (тот же отпечаток
  `rule:<id>:tls:<домен>` — появится монитор, алерт продолжится, а не задвоится); пока внешняя проверка свежее суток,
  агентский замер её алерт не трогает. Домен, пропавший из конфигурации nginx, закрывает свой алерт.
- **Статистика.** p50/p95/p99 задержки считаются по успешным проверкам, ошибки — отдельно. На
  графике сбои отмечены метками.
- **Техработы.** Окно задаётся на хост (вместе с его контейнерами), на внешнюю проверку или на
  всю консоль.
  - В окне алерты не поднимаются и не рассылаются, повторы тоже. Восстановления проходят как обычно.
  - Если после окна условие держится, алерт поднимается заново через обычные «N наблюдений
    подряд». Техработы не прячут незакрытую проблему.
- **Онбординг.** Чек-лист на главной.
  - Обязательные шаги: монитор, агент, канал доставки. Канал засчитывается только после реальной
    доставки теста.
  - Деплои и публичная страница необязательны: о них напоминают только в настройках.
- **Хранение** (Настройки → Общие). Чистит фоновый тик. Алерты и инциденты он не удаляет.

  | Данные                       | По умолчанию | Допустимо |
  | ---------------------------- | ------------ | --------- |
  | Результаты проверок, метрики | 30 дней      | 1–90      |
  | Журнал доставки              | 30 дней      | 7–180     |
  | События                      | 90 дней      | 7–365     |
  | Суточные агрегаты проверок   | 400 дней     | 90–730    |

  Карточки хода деплоя — 90 дней и не больше 200 последних, без настройки (см. «Ход деплоя»).

- **Публичная страница** `/status` (по умолчанию выключена). Показывает только мониторы с
  отметкой «публичный»:
  - статус и доступность за 90 дней по суточным агрегатам;
  - историю инцидентов, которые задели эти сервисы: важность, время и сервисы, без названий и
    заметок.

  Ответ кэшируется на 30 секунд.

## Перезапуск контейнеров — гарантии

- Перезапускать можно **любой** контейнер. Контейнеры, которые хранят данные (postgres,
  pgbouncer, redis, minio, clickhouse, kafka и т. п. по имени, образу или сервису compose, либо
  с меткой `ops.stateful=true`), перезапускаются **только после ввода точного имени** (решение
  владельца 2026-10-06). Ошибка эвристики в сторону «хранит данные» безопасна: просто
  понадобится ввести имя.
- **Причина обязательна.** Она попадает в ленту, в хронологию связанного инцидента и в отчёт
  ИИ-совету.
- **Защита от повторов:** у одного контейнера одновременно только одна команда в очереди. После
  успешного перезапуска действует пауза (по умолчанию 120 с, Настройки → Общие), и у агента на
  хосте есть свой cooldown. Команда, которую агент не забрал за 10 минут или забрал, но не
  прислал результат за 10 минут (ответ потерялся в сети), истекает и перестаёт блокировать
  новые перезапуски.
- **Перезапуск не поднимает ложных алертов:** пока команда выполняется, «контейнер остановлен» и
  «unhealthy» для этого контейнера не оцениваются. Ручной `docker restart` не увеличивает счётчик
  restart loop.
- **Права:** перезапускают оператор и владелец, наблюдатель только смотрит. Агент выполняет только
  `docker restart` над контейнером, который существует на хосте и проходит allow/deny-маски.
- **Один путь для консоли и бота:** все правила — в `requestRestart` (`server/containers/restart.ts`);
  роут консоли и Telegram-бот их не повторяют. Запрос из бота — только в личке, с причиной и (для
  контейнера с данными) именем; в журнале — «(из Telegram)».

## Алерты

Встроенные правила (пороги меняются, правило можно выключить, но не удалить):

| Правило                          | Важность            | Когда                                                              |
| -------------------------------- | ------------------- | ------------------------------------------------------------------ |
| CPU > 90 %, память > 90 %        | внимание            | 4 отчёта подряд                                                    |
| Диск > 85 % / > 95 %             | внимание / критично | 2 / 1 отчёт                                                        |
| nginx 5xx > 10 в минуту          | внимание            | 3 отчёта подряд                                                    |
| Контейнер остановлен / unhealthy | критично            | 2 отчёта подряд; одноразовые задачи с кодом 0 не считаются         |
| Restart loop                     | критично            | ≥ 3 перезапусков демоном за 10 мин                                 |
| Нехватка памяти в контейнере     | внимание            | ядро убило процесс в контейнере за 10 мин (агент ≥ 1.4)            |
| Агент молчит                     | критично            | нет отчётов дольше 4 интервалов                                    |
| Docker не отвечает               | критично            | 4 отчёта подряд с `dockerError` (зависший dockerd, нет docker CLI) |
| Сайт недоступен                  | критично            | 2 сбоя проверки подряд                                             |
| TLS истекает                     | внимание / критично | < 14 / < 3 дней                                                    |
| Деплой упал                      | критично            | итог скрипта деплоя с кодом ≠ 0; workflow `failure` / `timed_out`  |
| Деплой идёт долго                | внимание            | дольше 60 мин (порог — минуты)                                     |
| Нет rollback-prev                | внимание            | деплой сменил сервисам образ, а rollback-prev им не поставил       |

Алерты деплоя (OPS-DEPLOY-VIS, фаза 2) идут от событий `contabo-deploy.sh`. Провал — сразу по итоговому
событию, с упавшей фазой и проверками; долгий деплой — на каждом тике. Алерт из событий поднимает и закрывает
только агент, приславший их, — следующим своим деплоем. Опрос GitHub — отдельный алерт того же правила: события
его не подавляют и не закрывают. Поэтому при провале приходят два уведомления (событие сразу, опрос — после),
в консоли они в одном инциденте («Деплой · <workflow>»). К «Сайт недоступен» добавляется факт «Идёт деплой»
(при подъёме стека около 3 минут 502) или «После деплоя» — в первые 30 минут после зелёного деплоя, если сайт
лёг (false-green). Оба — только когда запуск GitHub это подтверждает; алерт они не глушат.

Плюс правила P0 продукта по бизнес-метрикам (`biz_*`, считаются в замерах раз в 5 минут) — таблица и включение в
[`docs/ops/p0-slo-alerts.md`](../../docs/ops/p0-slo-alerts.md).

**Нехватка памяти внутри контейнера.** Ядро убивает самый большой процесс контейнера, упёршегося в свой потолок
памяти (или любого контейнера, когда кончилась память всего сервера). Убит вспомогательный процесс — контейнер
работает дальше без него; убит главный — контейнер перезапускается с тем же id. Счётчик `oom_kill` в cgroup во втором
случае бесполезен: systemd пересоздаёт scope контейнера за 0–3 с, и счётчик снова 0. Поэтому агент ≥ 1.4 считает
случаи по журналу ядра (строки `oom-kill:`, группа `adm`): читает от курсора не чаще раза в минуту, жертву берёт из
`task_memcg`, итог по id контейнера только растёт и хранится в `/var/lib/hrh-ops/oom.json` (StateDirectory) —
переживает перезапуск контейнера и агента. У пересозданного контейнера (новый id) итог начинается заново. Кроме
итога агент шлёт имена убитых за 3 суток (`pluginsmanager ×4`; при нехватке памяти всего сервера — с пометкой
«память хоста») и пики памяти и swap с запуска из cgroup (`memory.peak`, `memory.swap.peak`).

Консоль показывает пики и итог на странице сервера. Каждый прирост итога пишется в ленту событий (пик, потолок, swap,
имена) и в историю как `oomnew:<контейнер>`; правило «Нехватка памяти в контейнере» суммирует приросты за 10 минут,
поэтому алерт совпадает с событием и не зависит от срока хранения истории. Подсказка различает потолок контейнера и
нехватку памяти всего сервера. Первое значение итога — точка отсчёта: случаи до установки агента 1.4 новыми не
считаются, итог меньше прошлого (пересоздание, потерянный учёт) — тоже новая точка отсчёта.

Алерт закрывается так же, как открывается, — после стольких же нормальных отчётов подряд:
метрика, которая гуляет у порога, не открывает и не закрывает его на каждом отчёте. Пока
healthcheck контейнера в состоянии `starting`, алерт «unhealthy» не меняется. После перезапуска
локальной консоли старая тишина агентов не оценивается, пока агент не успеет вернуться (окно
тишины + 60 с, пауза повтора агента ограничена 60 с).

Критичный алерт открывает инцидент. Если по тому же объекту уже есть открытый инцидент, алерт
присоединяется к нему. Инцидент закрывается, когда восстановились все его алерты. «В работу» и
«Тишина» останавливают повторные уведомления. Каналы: **Telegram-бот** (HTML, `parse_mode`
передаётся всегда), **email** (SMTP), **webhook** (только с подписью HMAC), а в самой консоли
алерты видны всегда.

В Telegram каждый алерт — ветка. Срабатывание (или «мигает») приходит карточкой. Повтор,
восстановление, ручное закрытие и «стабильно» приходят короткими ответами на неё. Сама
карточка переписывается на месте: пока алерт горит, в ней свежие значения и «обновлено ЧЧ:ММ:СС»,
после закрытия — итог (восстановлено или закрыт, сколько длилось). Пока алерт мигает,
восстановление не рассылается, но карточку всё равно переписывают в итог, без ответа в ветку.
Ссылка на карточку `chatId:message_id` хранится в журнале доставки (`deliveries.external_id`) и
действует только в том же чате. Если карточки нет (её удалили, она не дошла, отправлена до этой
версии, чат канала сменили или журнал старше 30 дней очищен), уведомление уходит полным отдельным
сообщением, как раньше. Если ответ в ветку не ушёл (например, 429 при шторме), карточку не правят.
Сбой правки канал не красит.

Уведомление о восстановлении показывает факты и ссылки наблюдения «в норме», а не последнего
сбоя. Строка алерта их не перезаписывает: в истории остаётся, что сломалось. Деплой-алерты
опрашивают только запуски из `main` (`?branch=main`): запуск с другой ветки — проверка, а не
выкладка. У ручного запуска (Run workflow, откат) GitHub отдаёт вершину ветки, а не выкаченный
коммит, поэтому вместо коммита пишется «ручной запуск», а сам коммит смотрите в логе запуска.

Подпись webhook и отчётов: `X-Ops-Timestamp: <unix ms>` и
`X-Ops-Signature: sha256=<hex HMAC-SHA256(ключ, "${timestamp}.${body}")>`. Приёмник сверяет подпись
через `timingSafeEqual` и отклоняет запросы старше 5 минут.

## Ход деплоя (события скрипта деплоя)

На странице «Деплои» — живая карточка текущего или последнего деплоя: фазы со статусом и длительностью
(идущая тикает), проверки по публичным адресам с кодом curl, rollback-prev, потерянные события и запуск
GitHub, если он сопоставлен (по sha; у ручного Run workflow — по времени: деплои идут строго по одному).

- **Откуда.** `infra/scripts/prod/contabo-deploy.sh` через `infra/scripts/prod/lib/ops-deploy-events.sh` зовёт
  помощник `infra/scripts/prod/ops-deploy-event.py` (stdlib python3): `POST /api/agent/deploy-events` под
  учёткой агента хоста из `/etc/hrh-ops-agent.env`. Заголовки, подпись и окно ±5 минут — как у отчёта, метка
  повтора — своя у карточки: с общей меткой отчёт агента, подписанный раньше, но пришедший позже события,
  получал бы 409. Контракт — `shared/deploy-events-contract.ts`, тело ≤ 16 КБ, Zod.
- **События** (не больше 8 на деплой): `deploy_start`, `prepare`, `build_start`, `build_done` (код),
  `rollback_prev`, `nginx_apply` (код 0/20/30/40), `health_checks`, `deploy_done` (код выхода скрипта — из
  `trap EXIT`, поэтому приходит и после упавшей проверки). Каждое несёт накопленную сводку, `deployId` (sha и
  время старта) и `seq`: консоль сама перезапускается на шаге `up`, потерянные события карточку не портят,
  повтор не дублирует. Миграции и подъём стека идут внутри `rebuild-prod-stack.sh` — для скрипта деплоя это
  одна фаза «сборка, миграции, подъём» с её кодом и длительностью.
- **Деплою не вредит.** Только во втором запуске скрипта (после `git reset` и `exec`). Нет учётки агента,
  python3 или консоли — деплой идёт как раньше: ни строки в его логе, тот же код выхода. Каждое событие
  ограничено `timeout 5` (если команда есть), дедлайном помощника 4 с и HTTP 3 с. Замер харнессом: консоль
  отвечает или закрыта — +0,7–0,8 с на деплой, зависла — +25 с; худший случай — ~40 с (8 событий × `timeout 5`).
- **Карточка** — `GET /api/events/deploys/live` (видит и наблюдатель); интерфейс опрашивает раз в 5 с, только
  пока деплой идёт, иначе раз в минуту. «Нет событий» — идёт, но событий нет 2,5 ч (сборка молчит до 90+ мин)
  или запуск GitHub завершился без итога от скрипта.
- **Хранение** — 90 дней и не больше 200 карточек (ежедневная чистка); новых карточек от агента — не больше 30
  в час.
- **Проверка пути деплоя** — `bash infra/scripts/prod/tests/contabo-deploy-sim.sh`: целый скрипт с фейками
  docker/git/curl, версия из `origin/main` против рабочей во всех контекстах запуска; `--self-test` —
  посадки дефектов; `--timing` — добавка ко времени.

## Отчёты ИИ-совету директоров

`shared/report-contract.ts`, схема `hrh.ops.report/v1`. В отчёт входят доступность (по часовым
агрегатам), инциденты, алерты, ручные перезапуски с причинами, ресурсы серверов, деплои, TLS и
рекомендации. Рекомендации строятся по правилам из фактов, без генерации. Персональные данные — только
email оператора в `restarts[].by`. Расписание — по умолчанию ежедневно в 06:00 UTC (или по понедельникам);
период собирается один раз.

**Куда уходит.** Свой приёмник владельца (адрес и ключ в «Отчётах») — туда. Иначе, если есть связка с
продуктом (вход через платформу: `OPS_SSO_API_URL` + `OPS_SSO_CLIENT_SECRET` ≥ 32 символов), — в продукт
автоматически, `POST /api/v1/platform/ops-reports`: ключ подписи выводится из секрета SSO и origin консоли
(формула — в контракте), внутренний адрес backend пропускается только для этого вызова. Без того и другого
отчёт хранится в консоли со статусом «приёмник не задан». Адрес без ключа — тоже «не задан»: молча в
продукт консоль не переключается.

**Доставка.** Отчёт сначала сохраняется (`pending`), потом отправляется; не дошедший повторяется раз в
15 минут тем же телом со свежей подписью — до 8 попыток в пределах суток (недельный — недели). История
отчётов в консоли — 180 дней.

**В продукте** хранится по одному последнему отчёту каждого вида — не сам отчёт, а сводка из чисел и имён
сервисов (≤ 1200 символов), которую backend строит сам. ИИ-совет получает её к первому ходу новой сессии
(полномочие `platform.metrics`); если отчёт старше 36 ч (недельный — 8 дн.), совет видит строку «не
приходил N дн.».

## Очередь владельца (`/queue`, `/api/oq/v1`)

Переехала 18.10.2026 из артефакта claude.ai (спека `docs/specs/owner-queue.md`). Сюда сводятся решения, мёржи,
команды на сервере, ручные проверки и «Ход работ». Агенты любых аккаунтов Claude и любые ИИ-клиенты пишут через API
или MCP (`infra/owner-queue-mcp`), владелец отвечает здесь и в Telegram-боте очереди (`infra/owner-queue-bot`).

- **Данные** — `oq_docs`: коллекции `checks` (ответы владельца, статусы агентов), `items` (пункты), `work`
  (задачи «Хода работ»), в формате базы артефакта. Есть журнал `oq_events` и токены `oq_tokens` (только sha256).
- **Страница `/queue`** — страница артефакта как есть (`server/queue/page.html`). Её хранилище подменено опросом
  API с ETag (`server/queue/page-scripts.ts`), на пунктах мёржа есть кнопки «Влить» и «Перезапустить деплой».
  Скрипты подключаются только с одноразовым nonce (CSP). Доступ — владелец консоли или токен очереди.
- **Права проверяет сервер:**
  - ответ владельца (`done`, `choice`, `note`, `at`) агент поменять не может, получит 403;
  - сдвиг `planEnd` без `basePlanEnd` — 409;
  - запись с устаревшей `ifVersion` — 409;
  - не больше 120 записей в минуту на токен.
- **Мёрж** (`POST /api/oq/v1/merge/:itemId {sha}`, только владелец):
  - вливается ровно показанный SHA;
  - `[skip ci]` берётся из пункта;
  - мёрж с деплоем закрыт, пока идёт деплой;
  - не чаще раза в 30 секунд.
  Токен GitHub для этого отдельный от токена опроса деплоев. Перезапуск деплоя — `POST /api/oq/v1/redeploy`.
- **Вложения входящих** (`/api/oq/v1/files`, таблица `oq_files`, файлы — на диске консоли):
  - загружает только владелец (сессия с `X-Ops-Csrf` или токен `owner`): `POST /files?item=<id>`, тело — сам файл,
    имя — заголовок `X-File-Name` (URL-кодирование), `Content-Length` обязателен;
  - тип — по содержимому: картинки (PNG, JPEG, GIF, WebP), PDF, docx и xlsx без макросов, текст UTF-8 (не разметка);
    SVG, HTML и всё прочее — 415. Имя чистится от путей и bidi-символов, расширение берётся по содержимому;
  - список `GET /files?item=<id>` и сводка `GET /files/summary` (с ETag) — `read`/`agent`; содержимое `GET /files/:id` —
    `agent`/`owner`, всегда `attachment` + `nosniff` + `CSP: sandbox`; удалить — `DELETE /files/:id`, владелец;
  - лимиты и потолок проверяются одним SQL-оператором (параллельные загрузки не проскочат); тот же файл в пункте — та же
    запись. Удаление пункта удаляет его файлы; через `OQ_FILES_RETENTION_DAYS` после закрытия файлы удаляются, строка
    остаётся надгробием. Срок считается от последней правки закрытого пункта или ответа на него: правка продлевает
    хранение (осознанно — лучше дольше, чем раньше времени). Уборка (`oq-files`, `oq-files-tmp`) — в планировщике;
  - сводка для страницы несёт строки файлов только у 300 новых, но число файлов — у всех пунктов: карточка старого
    пункта показывает «Вложений: N — показать» и догружает список; обрезка пишется в журнал (не чаще раза в час).

Настройки вложений (env, перезапуск без релиза):

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `OQ_FILES_DIR` | рядом с SQLite: `<папка базы>/oq-files` (на проде — `/app/data/oq-files`, том `hr_helper_v2_ops_data`) | каталог файлов; без файловой базы (Turso, Vercel) — не задан, вложения выключены, «📎» скрыт |

## Бесплатное размещение: Render + Turso (рекомендуется)

Vercel Hobby разрешён только для некоммерческого личного использования, а HR Helper —
коммерческий продукт. Поэтому основной вариант другой: **Render Free** (веб-сервис Node) и
**Turso Free** (база libSQL). Консоль работает там тем же процессом, что и локально, со
встроенным планировщиком, и внешний cron не нужен.

1. Turso: `turso db create hrh-ops` → URL `libsql://…` и токен (`turso db tokens create hrh-ops`).
   Бесплатно: 5 ГБ и 500 млн прочитанных строк в месяц, консоли этого хватает с запасом.
2. Render: «New → Blueprint» → этот репозиторий → `infra/ops-console/render.yaml`. Впишите
   `OPS_DATABASE_URL`, `OPS_DATABASE_AUTH_TOKEN`, `OPS_ADMIN_EMAIL`, `OPS_ADMIN_PASSWORD`. Ключ
   шифрования и секрет cron Render сгенерирует сам. Публичный адрес консоль возьмёт из
   `RENDER_EXTERNAL_URL`.
3. Агенту на сервере: `OPS_CONSOLE_URL=https://<сервис>.onrender.com`. Туннель больше не нужен.
4. Free-сервис засыпает через 15 минут без входящих запросов. Пока сервер жив, его будит агент
   (отчёт каждые 15 с). Чтобы падение сервера целиком тоже было видно, настройте внешний пингер
   (cron-job.org, бесплатно) раз в 5 минут: `GET https://<сервис>.onrender.com/api/health`.
   750 бесплатных часов в месяц хватает на один сервис круглосуточно.

Ограничения Free: 0,1 CPU и 512 МБ RAM (консоли хватает), диск стирается при деплое (поэтому
база в Turso), холодный старт после сна — около минуты.

## Альтернатива: Vercel (Pro или некоммерческий проект)

1. База: [Turso](https://turso.tech) (free) → `turso db create hrh-ops` → URL `libsql://…` и токен.
2. Проект Vercel с **Root Directory = `infra/ops-console`**. `vercel.json` уже задаёт сборку:
   миграции на Turso, затем `.vercel/output` (Build Output API v3). Это статика SPA, одна
   функция `/api/*` (бандл esbuild, libSQL через web-клиент без нативных модулей) и Vercel Cron.
3. Environment Variables: `OPS_DATABASE_URL`, `OPS_DATABASE_AUTH_TOKEN`, `OPS_ENCRYPTION_KEY`,
   `OPS_ADMIN_EMAIL`, `OPS_ADMIN_PASSWORD`, `OPS_PUBLIC_URL`, `CRON_SECRET`.
4. Первый владелец создаётся на шаге сборки (`npm run db:migrate`), если пользователей ещё нет.
5. Агенту — новый `OPS_CONSOLE_URL`.

**Частота проверок на Vercel.** На тарифе Hobby Vercel Cron срабатывает раз в сутки, этого хватает
на дайджест и отчёт. Минутные проверки выполняются двумя путями:

- **попутно с отчётами агента** (каждые 15 с, пока сервер жив). Это лёгкий тик: только
  HTTP-проверки, «агент молчит» и срок жизни команд. GitHub, TLS, ретенция, дайджест и отчёт
  выполняются в полном тике, чтобы ответ агенту не ждал медленных внешних API;
- **внешним пингером** (cron-job.org, бесплатно, раз в минуту): `POST https://<консоль>/api/cron/tick`
  с заголовком `Authorization: Bearer $CRON_SECRET`. Это полный тик. Он нужен, чтобы падение
  сервера целиком тоже было замечено, а деплои и сертификаты проверялись вовремя.

Аренда в БД гарантирует, что одновременные тики не выполняются дважды.

> Деплой на Vercel не выполнялся. Проверено локально: сборка `.vercel/output`, запуск бандла
> функции под Node (`/api/health`, 401 без сессии, 503 у cron без секрета). Работа с Turso
> на живой базе не проверялась.

## Вход через платформу (SSO)

Продукт — поставщик входа (IdP), консоль — клиент; поток authorization code.

- **Кто входит.** Суперадмин платформы — всегда, ролью «владелец». Остальным админам платформы
  доступ выдаёт суперадмин в продукте: «Платформа и надёжность → Ops-консоль: доступы»
  (`/admin/platform/ops-console`), роль — «оператор». Отключение оператора платформы отзывает и
  доступ к консоли: повторное включение его не возвращает, нужна новая выдача суперадмином.
- **Поток.** «Войти через платформу» → консоль кладёт `state` в httpOnly-cookie и уводит браузер
  на страницу-посредник продукта `/admin/ops-console-sso` (не залогинен — сначала вход в админку
  продукта, включая его 2FA) → SPA продукта вызывает `POST /api/v1/platform/ops-sso/authorize`
  своим Bearer-токеном → одноразовый код (Redis, 120 с) уходит на
  `https://<консоль>/api/auth/sso/callback` → консоль сверяет `state` и обменивает код
  server-side (`/token`, секрет `OPS_SSO_CLIENT_SECRET`) → своя сессия на 12 часов.
- **Учётка консоли** создаётся при первом входе и привязана к id админа платформы, а не к email:
  если email уже занят локальной учёткой, вход отклоняется («conflict») — владелец консоли
  меняет email локальной учётки (Настройки → Пользователи) или админ — свой email в профиле
  продукта. Неудачные входы через платформу ограничены: 10 с одного IP за 15 минут. Пароля у SSO-учётки нет; роль и доступ меняются только
  в продукте (в «Настройки → Пользователи» — только имя и локальная блокировка).
- **Отзыв.** Консоль сверяет доступ с платформой (`/introspect`) раз в 5 минут на запросе:
  отозван доступ, отключён оператор, передан пост суперадмина — сессии закрываются, роль
  обновляется без перелогина. Продукт не отвечает (сеть, 5xx) — сессия живёт с прежней ролью
  и проверяется снова через минуту: консоль нужнее всего именно во время аварии. Ответ 4xx
  (неверный секрет) — ошибка конфигурации: SSO-сессии закрываются.
- **Break-glass.** Локальная учётка владельца остаётся: если продукт лежит, новый вход через
  платформу невозможен, а локальный — работает. Последнего активного локального владельца нельзя
  понизить или заблокировать.
- **Настройка.** `OPS_SSO_PRODUCT_URL` (адрес SPA продукта), `OPS_SSO_API_URL` (куда консоль
  ходит server-side; по умолчанию тот же адрес, на проде — `http://backend:3001` во внутренней
  сети), `OPS_SSO_CLIENT_SECRET` — тот же, что у backend продукта; у backend ещё
  `OPS_CONSOLE_CALLBACK_URL=https://<консоль>/api/auth/sso/callback` (сверяется точно; от его
  origin выводится и ключ отчётов) и `OPS_CONSOLE_EXTRA_HOSTS` — хосты, на которых тот же callback
  тоже разрешён (короткий адрес очереди: сессия host-only, вход возвращается на свой хост). Код
  входа привязан к redirect_uri, с которым выдан. Без секрета кнопки входа через платформу нет.
  На проде всё раздаёт `docker-compose.contabo.yml` из `.env.contabo`.

## Безопасность

- **Своя администрация.** Роли «владелец / оператор / наблюдатель». Пароли хранятся как scrypt.
  Сессия — httpOnly-cookie `SameSite=Strict`, в БД лежит только sha256 токена. Изменяющие
  запросы требуют заголовок `X-Ops-Csrf`. После 5 неудачных входов вход по учётке блокируется на
  15 минут. Последнего владельца нельзя понизить или заблокировать.
- **Хосты.** Консоль отвечает только по именам из `OPS_ALLOWED_HOSTS` и по loopback, остальным — 421. Имя из
  списка, которое не совпадает с хостом `OPS_PUBLIC_URL` (короткий адрес очереди), получает только очередь и вход
  (`QUEUE_ALIAS_PATH_RE` в `server/http-types.ts`), остальное — 404. Тот же список держит nginx (`queue-alias.sh`),
  но Node разбирает путь иначе («\» = «/»), поэтому список nginx — не единственная защита.
- **Секреты** (токены ботов, SMTP, ключи подписи, секреты агентов, GitHub) шифруются
  AES-256-GCM ключом `OPS_ENCRYPTION_KEY`. Наружу отдаётся только маска.
- **Агент:** HMAC по `ts.METHOD.path.sha256(body)`, сравнение `timingSafeEqual`, окно ±5 минут.
  Метка времени строго возрастает, поэтому повтор запроса отклоняется. Отчёт не больше 512 КБ,
  схема проверяется Zod. События деплоя — та же подпись (путь входит в неё — запрос одного маршрута не
  принимается другим), повтор отсекает метка карточки, тело ≤ 16 КБ; секрет читает только помощник на хосте.
- **Исходящие запросы** — только http(s) без учётных данных в URL, с таймаутом и ограничением
  размера ответа.
- Конфигурация каналов (chat id, адреса, URL webhook) видна только оператору и владельцу, полный
  адрес приёмника отчётов — только владельцу.
- **Telegram-бот:** вебхук принимается только с верным `secret_token` (иначе 401) и, на проде, из
  сетей Telegram (nginx); повтор `update_id` не обрабатывается. Telegram-аккаунты админов видит
  только владелец; в журнале доставки подписка — «личная подписка #id». Тексты сообщений
  не журналируются.

## Ограничения и что дальше

- Приёмник отчётов в админке ИИ-совета не сделан (затрагивает auth-контур продукта — нужен
  отдельный ОК владельца). Вход через учётку продукта — см. «Вход через платформу (SSO)».
- Логи контейнеров в консоль не передаются намеренно: в логах backend могут быть персональные
  данные, а консоль может жить у стороннего хостинга.
- 2FA у локальных учёток консоли нет; вход через платформу проходит 2FA продукта.
- Графики читают сырые сэмплы (раз в минуту на метрику). На 7 днях это ~10 тыс. строк на
  график — для Turso free допустимо, но при росте числа серверов понадобятся агрегаты, как у
  проверок.
- Ход деплоя: миграции и подъём не выделены в отдельные фазы (они внутри `rebuild-prod-stack.sh`, который
  харнесс подменяет фейком); `/ideas` и `/api/v1/public/ideas/captcha` скрипт деплоя не проверяет — добавить их
  значит изменить поведение деплоя (новые строки лога, красный деплой), а пока их ловят мониторы консоли.
  Алерты по ходу деплоя (дольше 35 мин, красная проверка после зелёного деплоя, rollback-prev не поставлен) —
  следующая фаза: данные для них в карточке уже есть.
