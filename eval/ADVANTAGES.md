## 0. Цель и отправная точка

Владелец: **команда ИИ-сессий тратит меньше токенов и контекста, не теряя скорости и качества, и не простаивает
на лимите.** Повод — 23–24.10 четырнадцать сессий сожгли недельную квоту подписки за 42 часа, команда стояла
5 дней. Отсюда два подпроекта с разделением труда:

- **supertick-eval** — *как* команда работает дёшево: пайплайн экономии П1–П11.
- **t-boards** — *где* живёт работа: своя замена Notion, control plane задач для агентов.

Инвариант 1: снаружи ничего не меняется — PR, карточки, очередь, бот, «мёрж = деплой» и прод как были.

## 1. supertick-eval — преимущества пайплайна

Разобран внешний плагин supertick (тже: тик супервизора вне модели, файловая почта, приёмка по диффу).
Вывод `EVALUATION.md`: **не брать** — он под «одну фичу за прогон» с эфемерной командой, а у нас непрерывный
бэклог и долгоживущие роли; busy-детект только на Linux; тик срезал бы максимум 6–8 % расхода Т2 ($100 из
$1 298 ходов без действия; переписку $84 он не срезает вообще). Из него взяты рычаги, а не модель — и это
тоже преимущество: чужой процесс не тащим, платим только за проверенные механизмы.

| # | Механизм | Преимущество | Цифра / факт |
|---|---|---|---|
| П1 | **Геном роли** — запуск `claude --settings pipeline/genome/<роль>.json`: отрезаны плагины, скиллы и MCP-инструменты вне роли | каждый вызов роли дешевле; меньше поверхность ошибок (лишний инструмент физически недоступен) | база 83K → расчёт 50–55K, живая проба **42K**; скилл-листинг 8.7K → 1.3K |
| П6 | **Капсула** — контекст-пакет роли/карточки (цель, приёмка, решения, «не делать», следующий шаг) | передача дел без пересказа истории; наследник стартует с ~2K символов, а не с чтения всего | пишет и `contextPack` (≤ 2000 симв.) в карточку t-boards |
| П7/П8/П10 | **Нерв** — демон без модели, будит только ту роль, которой нужно действовать | экономия не столько токенов, сколько **времени команды**: лимит, кворум PR и ответ владельца больше не ждут, пока кто-то проснётся сам | 26.10 пять сессий встали на общем 5-часовом лимите — заметили через часы; теперь: пауза тапов при отказе, «лимит снят» по сбросу/смене аккаунта, пункт владельцу при недельном лимите; квота окна 5 ч калибруется сама ($17.2 на 28.10) |
| П9 | **Рой** — рутина (выжимка логов, поиск) на Haiku-субагентах и бесплатных моделях | дорогие хвосты Т2 уходят с Opus; PII и секреты наружу не уходят | хвосты Т2: «результат:Bash» $93.5 и «Read» $20.7; egress-фильтр + маскирование; битые ссылки → «ПРОВЕРЬ ВЫЖИМКУ» |
| П5/П2 | **TOON/дешёвый формат MCP-ответа, tool-scope по роли, бюджет на вызов** | ответ сервера и набор инструментов подогнаны под токены, а не наоборот | 3835 токенов против 4329 (TOON) и 3952 (JSON): −11 % к чистому TOON; не больше 3 поисков инструментов за вызов |

Отдельные преимущества **как методологии**:

- **Замеры вместо догадок.** `context_audit.py`, `wake_anatomy.py`, аудиты Т2/Т3 — каждое решение пайплайна
  привязано к цифре; «первым — самое дешёвое: суточный замер, до него идеи в процесс не вводить».
- **Всё отключается одним действием.** Геном — запуск без `--settings`; Нерв — `launchctl bootout`; рой —
  перестать вызывать; этап 0 в t-boards — перестать писать в лес. У каждого механизма записан откат.
- **Решения владельца d1–d5** зафиксированы до изменений живых конфигов (инвариант 6).

## 2. t-boards — преимущества

Боль (владелец, Q-052): Notion для агентов — «кладбище багов и задач», отваливающийся MCP, рассинхрон
очередей/идей/ревью. t-boards — форк kaneo, «фабрика для ИИ»: сначала для агентов, потом для владельца.

### 2.1 Токены и контекст

- **Задача живёт вне контекстного окна.** Контекст-пакет компилируется под запуск: цель + приёмка + состояние +
  ссылки, ≤ 2500 входящих токенов на задачу. Полная история в пакет не входит — сжатие не меняет истину, сырые
  данные хранятся отдельно от сводок.
- **Статус читают, а не спрашивают**: `forest_list_work_state` вместо сообщений «какой статус?»; сводки
  Координатора строятся из леса. Конец копий одного факта по 4–7 местам (главная жалоба отчётов Т3).
- **Цель владельца**: «прочитать задачу и начать» на **55–75 % дешевле Notion** (Q-050); порог перехода — минимум
  вдвое на 10 реальных карточках (AC-001; бенчмарк ещё не прогнан — §4).

### 2.2 Надёжность и корректность

- **Аренда + fencing-токен**: правка без токена отклоняется; связанные сессии делят аренду через `groupKey`;
  истечение по TTL. Гонки «кто первый записал» и потерянные правки исключены конструктивно, а не договором.
- **Корректность не зависит от LLM**: транзакции, идемпотентность, ожидаемые ревизии (`expectedRevision`),
  «не изменилось» с etag — детерминированные гарантии; модели только оптимизируют.
- **История карточки** — триггеры БД, откат одной правки одним действием (откат — только люди).
- **RPO ≤ 2 ч** (Q-051): свой VPS, бэкап поднимается на чистой машине; доступ только через WireGuard-туннель.

### 2.3 Права и контроль владельца

- Матрица прав вместо доверия: агент доводит карточку максимум до «на ревью»; закрыть, переоткрыть, сменить
  приоритет, свалить дерево/сектор — только через «да» владельца (`forest_request_approval` → `approvalId`).
- `half-baked` («сырая идея») меняет только владелец; такую карточку **нельзя арендовать** — защита на уровне API.
- Граница продукта: ключ продукта A не видит продукт B (404/403, fail-closed) — многопродуктовость с первого дня.

### 2.4 Память и передача дел

- **Наследник** получает ярлык роли `t3-<ключ>` — с арендами и журналом предшественника; смена сессии для
  карточки невидима.
- **claude-mem привязан к карточкам**: наблюдения и рабочее состояние читаются рядом с задачей, а не валяются
  в общем пуле; `contextPack` на карточке — всё, что нужно, чтобы продолжить.
- **Зеркало Notion**: обновление по `last_edited_time`, поля агента (ветка, PR, файлы, контекст-пакет) на
  зеркальных карточках сохраняются. Переход без большой миграции: канон меняется, когда зеркало неделю чистое.

### 2.5 Структура против «кладбища»

- Модель леса: деревья (эволюционирующие задачи), секторы по смыслу (Canopy View), **вырубка** — завершённое
  дерево превращается в «бревно», ветки сжимаются в «семена». Архив — операция системы, а не ручная чистка.
- Ошибка — вид карточки (`kind: bug`, серьёзность) на той же доске и в тех же колонках владельца: один процесс,
  восемь колонок (Новая → … → Готово/Закрыта) для всех продуктов.
- Телеметрия на карточке: `tokens`, `costUsd` — сколько стоила работа, видно сразу.

## 3. Синергия: почему два подпроекта, а не один

| Связка | Что даёт |
|---|---|
| Капсула пишет `contextPack` в карточку t-boards | экономия пайплайна материализуется в структуре данных t-boards, а не в переписке |
| Журнал событий и капсулы спроектированы сразу как сущности t-boards | один источник на факт вместо 4–7 копий (R4 Ф-1) |
| Нерв знает роли, включая `tboards` | события доски будят только роль 6, остальные спят |
| R-037: хук переносит `work_state` из claude-mem в лес и аренды | двойная запись этапа 0 становится автоматической — состояние пишется само |
| Этап 0 (с 30.10): 6 ролей Т3 работают в лесу с геномами | команда разработки — пилот обоих подпроектов одновременно, критерии успеха измеримы |

Проверяемые критерии этапа 0 (свёрка через 24 ч): у каждой роли последний шаг не старше 2 ч; у карточек в работе
есть `branch`/`pullRequests` и `contextPack`; 0 правок поверх чужой аренды; 0 вопросов «какой статус?»;
первый вызов роли ≤ 45K токенов.

## 4. Что честно не доказано (или ещё не измерено)

- **≈ $20 на PR и −35…45 %** — модель из `PIPELINE.md`, проверят ворота фаз на живом дне; Т3 мерили 5 ч почти
  без нагрузки; «Т3 под нагрузкой ≈ $714» — модель для ранжирования рычагов.
- **«Вдвое дешевле Notion» (AC-001)** — бенчмарк на 10 реальных карточках ещё не прогнан (после импорта).
  55–75 % — ожидание владельца (Q-050), не замер.
- У автора supertick всего два живых прогона — мало для выводов о стоимости; у нас сам supertick не ставится.
- Kimi выбыл 29.10: вторая линза другого вендора не отработала; у GLM на 14.10 ~треть находок были неверными —
  внешним выжимкам нужна выборочная сверка.
- До писателя R-037 этап 0 живёт с двойной записью (claude-mem + лес) — это осознанная плата за пилот.
- Форк kaneo — локальный, наружу не пушится: сопровождение и обновления апстрима — наша ноша.
