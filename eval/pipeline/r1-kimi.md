## 0. Главный тезис

**Деньги сидят не в холостых пробуждениях (8–10%), а в структуре контекста.** Цифры из базовой линии:

- Т2 (19 ч, $1 298): чтение кэша 54.2% ($703.5), из него учтённый хвост повторно перечитанных вставок — $265.1
  (data/audit-t2-2310.txt п.2). Повторы nested_memory внутри того же контекста — 644 381 т за окно (п.4).
- Т3 (5 ч, $40.1): запись кэша 61.8% ($24.8) — каждая нестабильная вставка ломает префикс и заставляет переписывать
  кэш; базовый контекст первого вызова 83–84 K при среднем 141 K (п.6, п.1).
- Холостые ходы Т2 — $99.9 (7.7%), переписка — $84.5 (6.5%). Supertick бьёт именно в это: честный потолок ~7.5%
  (../reports/lens-3-kimi.md). Это мало и не решает проблему недельной квоты (Т2 сгорел за ~42 ч).

Следствие: главный резерв — **контекст как продукт**: меньше постоянной базы, стабильный префикс, пакет по задаче
вместо истории, рутина на бесплатных моделях. Оценка реализуемого потолка: **25–35% окна Т3** против 6–8% у
supertick — при неизменном внешнем виде (инвариант 1).

## 2. Где спорю с Dev4dev-документом

1. **Очередность.** Документ ставит экономию контекста после надёжности (этап 1), качества (этап 2) и доказательного
   ревью (этап 3), а «короткие runs» — этапом 6. Но дефицит — недельная квота, а сторож её не экономит, он сокращает
   простой. Конфиг-экономия (мои P1/P2/P6/P9) стоит дни, не требует новых сервисов и даёт больший процент раньше.
   Предлагаю параллельный трек: этап 1 (сторож) и «этап 0.5» (конфиг-пакет) идут одновременно; этапы 2–6 — по
   документу.
2. **Принцип 7 требует дополнения.** «Модель не планирует пробуждение» — верно, но supertick показал вторую
   половину проблемы: детерминированный будильник с файловой почтой теряет сообщения. Диспетчер обязан писать
   каждое событие в append-only журнал с idempotency key — иначе получим экономию ценой потери работы.
3. **Пакет 2–8 K токенов — цель, не норма.** Для code-задач реалистично 8–20 K (символы + правила + diff-контекст).
   Предлагаю зафиксировать измерение (медиана пакета, доля retrieval), а не число; иначе компилятор начнут
   «оптимизировать» выбрасыванием нужного.
4. **Бесплатные модели не рассмотрены.** Документ перебирает React Doctor/Checkov/Ducktective/ECC, но не роутинг
   рутины на free-tier (Groq, OpenRouter free, GLM-flash). Между тем 83% вызовов Т3 — ровно один инструмент
   (data/purpose-t3-2610.txt): заметная доля — рутина, которую Opus делает не лучше llama-3.3-70b. Это P5 ниже;
   требует d-решения по инварианту 5.

## 3. Предложения (формат PROTOCOL)

### P1. Сокращение постоянной базы контекста (правила, память, листинги)
Механизм: в `.claude/settings.local.json` — `claudeMdExcludes` по глобам для ролей, которым файл не нужен
(path-based); `skillOverrides: {"<имя>": "name-only"}` для 10 плагинов, дающих только листинг (используются 3 из 13 —
data/claude-code-controls.md §1); `permissions.deny` для MCP, чуждых роли (playwright в backend-роли и т.п.);
обновление Claude Code ≥ 2.1.304 ради `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH`.
Экономия: 8–12% окна Т3. Основание: базовый контекст 83–84 K (audit-t3 п.6); срезание ~30 K × 377 вызовов ≈ 11.3 Mт
чтения кэша; nested_memory-повторы 60 272 т за 5 ч Т3 и 644 381 т за 19 ч Т2 (п.4 обоих аудитов); skill_listing
87.4 Kт и хвост 3.3 Mт за Т3 (п.2). На масштабе Т2 та же мера ≈ $60–90/19 ч.
Измерение: первый вызов сессии 83 K → ≤ 45 K; средний контекст 141 K → ≤ 120 K; повторы nested_memory → ~0.
Риск: роль теряет нужное правило → регресс качества (стоп-критерий протокола). Митигация: excludes только по путям,
где роль не работает; security-правила не трогаем.
Откат: удалить ключи из settings.local.json.
d-решение: **нужно** (инвариант 6 — живой конфиг). Вопрос: «Включить конфиг-пакет экономии №1 (excludes,
skillOverrides, deny лишних MCP) после замера на тени?»

### P2. Дедупликация и щадящие хуки (стабильный префикс)
Механизм: хук UserPromptSubmit/dams-context вставляется только при смене темы (fingerprint последней вставки в
state-файле; совпадение — пропуск). grill-task-auto — только для реальных grill-задач. context_window_protection на
SessionStart (24.4 Kт × 11 за Т3) ужимается до ссылки на канон.
Экономия: 2–4% окна Т3 через снижение записи кэша (запись 61.8% = $24.8/5 ч; каждая вставка в середину префикса —
перезапись). Прямой хвост UserPromptSubmit в Т2 — $16.8/19 ч.
Измерение: «источники вставок хуков» (токены), доля записи кэша 61.8% → ≤ 50%.
Риск: пропуск релевантного dams-контекста → митигация: вставка при смене cwd/ветки/темы всегда.
Откат: вернуть хук из git.
d-решение: нужно (тот же пакет, что P1 — одним пунктом).

### P3. Диспетчер-конвейер: спящие роли + append-only журнал событий
Механизм: роли спят в bash-ожидании (ноль токенов, как supervisor-wait.sh supertick); диспетчер на коде следит за
источниками (очередь владельца, GH-события, watchdog, cron) и будит роль только на реальную работу, записывая
событие в append-only журнал с idempotency key и приоритетом P0–P4. Отличие от supertick: журнал в SQLite/PG, не
файловая почта (урок потери сообщений); диспетчер вне модели (принцип 7 Dev4dev).
Экономия: 8–12% окна Т2 (холостые $99.9 + переписка $84.5 = $184/19 ч = 14.2%; честный потолок после вычета
полезной координации ~8–12%). На Т3 эффект меньше: координация уже 15.8% вызовов при 10% холостых.
Измерение: wake_anatomy — доля no-action wakes 10% → ≤ 3%; $ холостых → ≤ $15/19 ч в пересчёте.
Риск: задержка реакции (polling 60 с), потеря сообщений — закрывается журналом; двойное пробуждение — fencing по
workspace-блокировке.
Откат: роли возвращаются на SendMessage; диспетчер гасится одним процессом.
d-решение: для тени — не нужно; для включения — нужно («роли спят до события, будит диспетчер»).

### P4. Компилятор контекстных пакетов (пакет вместо истории)
Механизм: shadow-сервис: на вход wake-событие из P3, на выход пакет — цель, acceptance criteria, правила по ссылкам
(принцип → правила → исключения), затронутые символы, snapshot, provenance (source/revision/freshness). Security-
инварианты и exact AC не сжимаются — хранится оригинал + hash, в пакете ссылка (Dev4dev §Контекст).
Экономия: 8–10% окна Т3. Основание: средний рабочий контекст 147 K (purpose-t3); цель 60–80 K на рабочих вызовах ≈
−45% чтения кэша на 74% вызовов ≈ $3.3/5 ч; плюс снижение записи кэша (короче префикс-дифф).
Измерение: средний контекст 141 K → ≤ 90 K; медиана пакета; доля контекста из retrieval (метрика Dev4dev).
Риск: потеря контекста (инвариант 4) → обязателен provenance и ссылка на оригинал; регресс = стоп-критерий.
Откат: роль читает историю, как сейчас; компилятор остаётся тенью.
d-решение: для пилота на одной роли (фаза 3).

### P5. Рефлексы на бесплатные моделях (роутинг рутины)
Механизм: meta-правила (развитие T3 PROPOSALS №11): правило с единственным файлом и локальной операцией выполняет
free-tier (Groq llama-3.3-70b, OpenRouter free, GLM-4.5-flash) через egress-фильтр диспетчера (P3), который пропускает
наружу только тексты задач/правил и режет код, секреты, PII. Неоднозначное — Claude. Наблюдатель claude-mem уже на
haiku ($0.3/5 ч) — не трогаем.
Экономия: 8–11% окна Т3. Основание: 83% вызовов с ровно одним инструментом (purpose-t3); консервативно 10–15%
рабочих вызовов — уводимая рутина ≈ $3–4.5/5 ч. На масштабе Т2 ≈ $100+/19 ч.
Измерение: доля вызовов на free-моделях; $/PR; качество рутины по возвратам PR.
Риск: утечка (инвариант 5) → фильтр обязателен и тестируется на синтетике до d-решения; деградация рутины →
advisory-период с человеческой выборочной проверкой.
Откат: флаг роутера в off — весь трафик снова на Claude.
d-решение: **нужно обязательно**. Вопрос: «Разрешить отправку текстов задач и правил (без кода, секретов, PII) на
бесплатные OpenRouter/Groq/GLM-flash через egress-фильтр?»

### P6. Кэш-дисциплина: обновление CLI + TTL
Механизм: обновить Claude Code 2.1.237 → ≥ 2.1.242 (лучше ≥ 2.1.304); `promptCacheTtl: "1h"` для основного
разговора; проверить `idleCompaction` (v2.1.290+); субагентам — осознанный `experimental.cacheTtl`.
Экономия: 5–8% окна Т3. Основание: холодные вызовы «сон > 60 мин» — $6.7/5 ч (16.8%, audit-t3 п.1); TTL 1 ч снимает
перезапись кэша после часового сна; в связке с P3 (сон до события, не по таймеру) причина «сон» убывает.
Измерение: холодные вызовы по причине «сон» → ≤ 5%; запись кэша 61.8% → ≤ 50% (совместно с P2).
Риск: регрессии новой версии CLI → сначала на одной роли; 1h-запись дороже 5m при коротких сессиях — замерить.
Откат: откат версии/ключа.
d-решение: нужно (среда команды). Можно одним пунктом с P1: «обновить CLI и включить пакет кэш-дисциплины».

### P7. Сторож с авто-действиями (развитие watchdog)
Механизм: `../shadow/watchdog.py` уже ловит каскады лимитов, потерю auth, staleness (6 переигровок, сигнал ≤ 60 с).
Добавить: предиктор сессионных лимитов (всплески 502 → лимит через 2–4 ч), авто-пауза ролей перед каскадом,
предиктивный пункт владельцу «через ~N ч упираемся в лимит, план: …». Состояния аккаунта — автомат из Dev4dev
(available → degraded → rate_limited → awaiting_reset → probing).
Экономия: не токены, а простой: утренний каскад 26.10 дал 4 ч 15 мин незамеченного простоя — при недельной квоте
простой = потерянная квота. Косвенно защищает $/PR.
Измерение: время обнаружения остановки (метрика Dev4dev): часы → ≤ 2 мин; ложные STALE ≤ заданного порога.
Риск: ложная пауза останавливает работу → авто-пауза только по каскадной сигнатуре (≥ 2 роли), одиночная — пункт
владельцу.
Откат: watchdog в режим «только сигналы».
d-решение: нужно («сторожу разрешены авто-пауза ролей и предиктивные пункты»).
