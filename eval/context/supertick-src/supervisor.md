# Супервизор: как ведущий спит и что его будит

Это про деньги ведущего. Каждый его ход стоит столько, сколько весит его контекст, а в
живом прогоне контекст ведущего к середине работы — сотни тысяч токенов: пересылка
одного письма стоила $0,38 (замер 121-218). Холостой ход «проверить, нет ли чего» при
таком контексте — самое дорогое действие в команде, а нужен он был потому, что
ведущего будило только письмо участника, и молчание он не отличал от смерти.

Супервизор убирает холостые ходы. Это два скрипта без единого обращения к модели:

- `scripts/supervisor-tick.py <run-dir>` — один проход по файлам прогона: что участники
  сообщили, что отметил ведущий, живы ли движки. На выходе список действий с
  приоритетами P0–P4 и снимок `state/supervisor.json`.
- `scripts/supervisor-wait.sh <run-dir>` — цикл тиков со `sleep` между ними. Завершается,
  когда есть действие уровня P1 и выше (или истёк максимум), и **этим будит ведущего**:
  ведущий запустил его фоновым Bash и закончил ход, а возврат фонового вызова — это
  его пробуждение.

Пока цикл крутится, ведущий не тратит ничего. Проснувшись, он читает вывод цикла
(десяток строк) и делает ровно то, что там названо. Полные отчёты, диффы и переписка в
его контекст не попадают — только пути.

Порядок принят 24.09.2026 (карточка 121-299). Идеи — из porch (pragmatic-orchestration):
проверка в первую минуту, надзор с интервалом 5–15 минут, контракт задачи, приёмка
родителем по диффу, «не ретраить вслепую». Рантайм porch не используется.

## Файлы прогона, которые читает тик

Все — в `.claude/teams/{team-name}/` (в командах — абсолютным путём `<RUN DIR>`). Ничего нового ведущий не ведёт руками: карточки
участников и письма пишут сами участники, тик их только читает.

| Файл | Кто пишет | Что даёт тику |
|------|-----------|---------------|
| `PLAN.md` | ведущий | статусы задач: DONE участника без DONE в плане = приёмка не сделана |
| `state.md` | ведущий | фаза; путь к запускалке движков |
| `pending.log` | ведущий | строки `\| OPEN` — недоставленные копии |
| `runs/<name>.json` | ведущий создаёт при спавне (`run-state.py new`), дальше **сам участник** (`run-state.py set` или Write) | статус, время последнего события, файлы задачи, интервал надзора |
| `mail/lead/*.md` | участники — копия каждого письма ведущему (`team-mail.sh` или Write) | DONE, STUCK, QUESTION, ESCALATION, SENSITIVE, ENGINE_DOWN, QUEUED — что ждёт ведущего |
| `mail/<name>/*.md` | кодер — копия REVIEW в `mail/unified-reviewer/`; рецензент — VERDICT в `mail/<кодер>/` (до сообщения); ANSWER в `mail/<кодер>/` (до сообщения) — ведущий на QUESTION / ESCALATION / STUCK, на MEDIUM техлид на ESCALATION / REVIEW_LOOP | письмо, которое адресат не взял за 2 минуты, — `undelivered_mail` |
| `mail/<name>/.seen` | адресат (`team-wait.sh`) | какие письма он уже получил |
| `ledger.jsonl`, `engine/<role>/*` | `run-engine.sh` | жив ли процесс движка, забран ли результат |
| `state/supervisor.json` | тик | снимок и память тика (первая минута, контрольные точки) |
| `state/acked.log` | ведущий (`supervisor-tick.py ack`) | письма, на которые ведущий уже ответил |
| `reports/accept-task<id>.md` | ведущий — одной записью ответ проверяющего приёмки (всегда на Claude) | статус `ACCEPTING` в PLAN.md + этот файл = `accept_result` |
| `reports/deviations-<роль>-task<id>.md` | прокси внешнего движка | ожидание против факта — читает проверяющий приёмки и фаза 3 |

**Почта — это каталог, а не файл.** Одно письмо — один файл `mail/<кому>/<время>_<от кого>_<KIND>[_task<id>].md`
с заголовком `from:/kind:/task:/ts:` и телом. Так писать могут и роли без Bash (рецензент — только
Write), и никто не портит чужие строки. Почта не заменяет SendMessage: письмо по-прежнему
уходит участнику напрямую, а файл — долговечная копия для тика и для восстановления.

**Ответ, которого участник ждёт, — файл, а не только сообщение** (с 0.16.0). Рецензент пишет
вердикт файлом в `mail/coder-N/` и только потом шлёт сообщение: сообщение, вернувшееся `queued`,
пропадает, файл — нет (121-374: ~12 ручных пересылок; fix-391-388 с ожиданием файла — ни одной).
Кодер после REVIEW ждёт файл в переднем плане: `team-wait.sh <run-dir> coder-N --task <id> --max 540`
с `timeout` Bash 570000, вызов за вызовом, пока письмо не ляжет; между вызовами —
`run-state.py set … status=in_review note="VERDICT WAIT"`, чтобы не сработал `silent_too_long`.
Любое письмо по задаче кончает ожидание: VERDICT — к коммиту, другое — ответить и ждать снова.
Фоном ждёт только ведущий: конец фоновой задачи простаивающего участника не будит (22.10.2026,
feature-trial-fixes, reports/wake-test.md). Пока участник ждёт, сообщения к нему приходят только в
конце вызова, до 9 минут: нужен ждущий (`STATUS?`, просьба, ответ) — сначала файл
`team-mail.sh … <KIND> task <id>`, потом сообщение; молчание на `STATUS?` до 9 минут — не повод
для замены. Письмо считается взятым, если оно есть в `mail/<имя>/.seen` (это пишет `team-wait.sh`)
или адресат обновил карточку позже письма (рецензент без Bash пишет `reviewing` в момент получения
REVIEW). `.seen`, записанный фоновым `team-wait.sh`, не доказывает, что письмо взято: процесс
отметил его, пока участник спал, и тик теряет `undelivered_mail`. Время карточки — позднее из
`lastEventAt` и mtime файла карточки: рецензент без Bash время берёт взаймы из письма REVIEW, но
если всё же выдумает его (121-393: `12:06+03:00` при реальных `13:48+02:00`, дважды ложный P0),
тик поверит файловой системе.

**Ответ ведущего — тоже файл** (с 0.17.0). На QUESTION / ESCALATION / STUCK ведущий сначала кладёт
`team-mail.sh <run-dir> coder-N lead ANSWER task <id> -- "<ответ>"`, потом шлёт сообщение; кодер,
чей вопрос вернулся `queued`, ждёт ответ той же командой в переднем плане, что и вердикт. Так `queued`
ответ не требует от ведущего RESEND (121-393: две ручные пересылки, обе лишние).

**Как читаются шапка письма и отчёт приёмки** (с 0.18.1; правила шапки ниже у тика и
`team-wait.sh` общие, кроме границы шапки):
- ключи `from:/kind:/task:/ts:` — без учёта регистра, пробелы вокруг ключа и значения и `\r`
  снимаются; ключ повторён — побеждает последний;
- граница шапки разная: тик кончает её на первой строке без одного из этих ключей (`to:`, строка
  без `:`, строка из пробелов), `team-wait.sh` такие строки пропускает и читает до первой пустой;
  `team-mail.sh` таких строк в шапку не пишет;
- id задачи — первое слово значения `task:` без одного ведущего `#`: `#3` и `3 (rework)` — задача
  3, `33` — нет; сравнение с учётом регистра (`2A` ≠ `2a`), с заголовком `## Task <id>:` в
  PLAN.md — как есть, поэтому `## Task #3:` с письмом `task: #3` больше не сходится;
- вердикт приёмки — только первая непустая строка `reports/accept-task<id>.md`, проверяется как
  есть: PASS, если она начинается с `ACCEPT:` и в ней есть слово PASS; отступ перед `ACCEPT:`,
  заголовок выше неё или пустой отчёт — `FAIL/?`.

Это терпимость чтения, а не разрешение писать иначе: шапка — строчные ключи и голый id, как ставит
`team-mail.sh`; `ACCEPT:` в отчёте одна и первая.

**Карточка участника** `runs/<name>.json`:

```json
{"name": "coder-3", "role": "coder", "task": "3",
 "spawnedAt": "2026-09-24T10:00:00+02:00", "lastEventAt": "2026-09-24T10:12:40+02:00",
 "status": "in_review", "files": ["src/a.py"], "acceptance": ["…"], "nonGoals": [],
 "checkAfterSec": 900, "note": "ждёт вердикта r1"}
```

Статусы: `running` → `in_review` → `fixing` → `done`; `reviewing` / `idle` у рецензента;
`stuck`, `stopped`. `stopped` ставит только ведущий — участнику, которого он остановил или заменил.
Каждый `set` ставит `lastEventAt` — это и есть «признак жизни».
`checkAfterSec` — интервал надзора: 900 по умолчанию, 300 для задач с риском или
пометкой SENSITIVE (ведущий ставит при спавне).

## Что тик считает действием

| Приоритет | kind | Когда | Что делает ведущий |
|-----------|------|-------|--------------------|
| P0 | `deliver_pending` | строка `OPEN` в pending.log старше 2 минут | доставить копию (team-runtime.md, «Правила ведущего: QUEUED и RESEND») |
| P0 | `undelivered_mail` | письмо в `mail/<имя>/` лежит 2 минуты, его нет в `.seen`, карточка адресата старше письма, адресат не `done`/`stopped` | `SendMessage(to=<имя>, "RESEND: from <от кого>\n<текст файла>")`, затем `ack` по имени файла |
| P0 | `stuck` / `engine_down` | письмо STUCK или ENGINE_DOWN, статус `stuck` в карточке | разобрать по phase2-monitoring.md, «Таблица событий»; после ответа — `ack` |
| P0 | `engine_dead` | у движка нет процесса и нет `.done` | «мёртвый прокси» из phase2-monitoring.md, «Тихий участник и мёртвый прокси» |
| P0 | `engine_failed_unread` | `.done` со `status=failed`, никто не забрал | как ENGINE_DOWN |
| P0 | `engine_result_unread` | результат движка лежит без `.taken` 15 минут, у прокси 3: прокси — роль с карточкой `runs/<роль>.json` не `done`/`stopped`; 3 минуты действуют, пока карточка (позднее из `lastEventAt` и mtime) не новее `.done` — прочитав result.md, прокси сразу ставит `note="ENGINE READ"` (feature-trial-medium: прокси, не разбуженный фоновым ожиданием, трижды терял по 15 минут) | переслать результат адресату самому (23.09 так вернули находки Grok) |
| P0 | `silent_too_long` | участник без событий два интервала и без правок в файлах задачи (mtime внутри окна, не `git status`) | `STATUS?` — он же будит участника, уснувшего на своей фоновой работе (24.09.2026: кодер ждал зависший jest 45 мин); нет ответа — `TaskStop` и свежий участник |
| P1 | `accept_needed` | DONE в почте, а в PLAN.md задача не DONE / ACCEPTING / REOPENED | поставить `ACCEPTING(coder-N)` и поднять проверяющего приёмки (phase2-monitoring.md, «Приёмка DONE»); задача только из документов — DONE сразу, кроме документов-продукта (`agents/`, `skills/`, `.conventions/` плагина): они идут на приёмку |
| P1 | `accept_result` | задача `ACCEPTING`, а `reports/accept-task<id>.md` уже лежит | первая непустая строка `ACCEPT: … PASS` → DONE в PLAN.md и спавн следующих; `FAIL` → `REOPENED(coder-M)` и свежий кодер с невыполненными критериями (один раз) |
| P1 | `answer_needed` | QUESTION / ESCALATION / SENSITIVE / REVIEW_LOOP / QUEUED без ответа | ответить, затем `ack` |
| P1 | `first_minute_silent` | 3 минуты после спавна — участник не поставил даже `startedAt` (первый `set status=running`), ни письма, ни правок, ни движка; звучит один раз. Поставивший `startedAt` уже работает и первой минуты не имеет | `STATUS?` участнику; молчит — уточнить задачу и перезапустить. Дальше он под обычным надзором: P0 через два интервала |
| P2 | `first_minute_silent` | 60 секунд без признаков жизни; один раз | ничего; станет P1 через 3 минуты |
| P3 | `checkpoint` | прошёл интервал надзора | ничего; информация при следующем пробуждении |
| P3 | `busy` | условие `silent_too_long`, но под `--root` (cwd процесса из /proc) идёт pytest / jest / yarn / npm / craco, начатый внутри окна молчания; в выводе `busy: <команда>`. Процесс старше окна не спасает — зависший jest остаётся P0. Без /proc правило не действует | ничего: участник гоняет тесты (121-393: денежный pytest 5–6 мин — дважды ложный P0); при следующем пробуждении сверить, что команда сменилась |
| P4 | `ok` | тихо | спать дальше |

Первая минута считается от `startedAt` — участник ставит его сам первым `run-state.py
set … status=running` (карточку ведущий заводит до спавна, между ними бывают минуты:
24.09.2026 — девять). Роль без задачи (рецензент, техлид) рождается `idle` и первой
минуты не имеет: она ждёт первый запрос, а не молчит. Каждая тревога первой минуты
подаётся один раз — в первом прогоне 0.14.0 она повторялась на каждом тике и будила
ведущего впустую восемь раз.

Цикл по умолчанию будит на P1 и выше (`--wake-on P1`). P2–P3 ведущий видит в выводе, когда
проснётся по другой причине или по максимуму ожидания (`--max`, по умолчанию час:
плановая проверка на случай, о котором тик не знает).

**Приёмка (`accept_needed` → `accept_result`).** DONE участника — кандидат, а не результат.
Ведущий код не читает: он пишет дифф коммитов задачи в файл, ставит `ACCEPTING` и поднимает
одноразового проверяющего (`acceptance-checker`, всегда на Claude: `supertick:spec-verifier`), который сверяет
дифф с критериями задачи из PLAN.md и гоняет её тестовую команду. Отчёт ложится в
`reports/accept-task<id>.md`, тик будит ведущего по нему. Критерии в PLAN.md поэтому
проверяемые — команда с ожидаемым выводом или факт о файле (`phase1-planning.md`, «Шаг 3: сложность и план»).

**Чего тик не видит.** Смерть Claude-участника: у него нет процесса и маркера. Тик
покажет только `silent_too_long`. Поэтому при каждом пробуждении по P0 ведущий сверяет
роли с `ListAgents` — единственный способ узнать, что участника снят лимитом API (23.09
так умерли четыре кодера разом).

## Ход ведущего с супервизором

1. **После спавна команды** (phase1-planning.md, «Шаг 5: спавн команды») и после каждого обработанного
   пробуждения:
   ```
   Bash(run_in_background=true):
     bash {plugin}/scripts/supervisor-wait.sh <RUN DIR> --root {корень репозитория}
   ```
   `<RUN DIR>` здесь и ниже — абсолютный путь каталога прогона: с относительным цикл не находит
   файлов. Затем **закончить ход**. Никаких «подожду и проверю»: ждёт скрипт.
2. **Пробуждение** — возврат этого фонового вызова (или письмо участника, или уведомление о
   завершении субагента: они никуда не делись). Прочитать вывод цикла — он уже содержит
   действия тика. Если разбудило письмо, а не цикл: сначала `python3 {plugin}/scripts/supervisor-tick.py <RUN DIR>`,
   потом действовать — тик покажет всё, что накопилось, а не одно письмо. Idle-уведомления
   участников (пересказ на каждый конец хода) не разбирать, кроме тех, где участник сообщает о
   своём нарушении.
3. Обработать действия **по порядку приоритетов**, каждое — по таблице выше. На письма,
   которые ведущий закрыл ответом, поставить `ack`: `python3 {plugin}/scripts/supervisor-tick.py ack <RUN DIR> <файл письма>`
   (имя файла или путь — всё равно, тик хранит basename).
   DONE закрывается не `ack`, а статусом DONE в PLAN.md.
4. Снова запустить цикл и закончить ход. Цикл — единственное «кто-то работает» для
   проверки простоя из team-runtime.md, «Проверка простоя»: пока он крутится, простоя нет.
5. **После compaction**: `state.md`, `PLAN.md`, `pending.log` как раньше, плюс один тик —
   он восстанавливает «кто где» из карточек и почты без переписки.

Правило «никогда не опрашивать по таймеру» из phase2-monitoring.md, «Тихий участник и мёртвый прокси», остаётся в силе для
**модели**: ход ведущего по таймеру — холостой и дорогой. Цикл тиков не ход модели, он
стоит `sleep`.

## Что пишут участники

Каждый участник получает в промпте блок `SUPERVISOR` с путями. Правила — в файле роли
(`agents/coder.md`, `agents/unified-reviewer.md`, `agents/proxy-teammate.md`); коротко:

- **Кодер** (есть Bash): первым делом `run-state.py set … status=running` — это старт его
  часов и первый признак жизни; `status=in_review` перед REVIEW, `status=fixing` по
  вердикту, `status=done` после коммита; самопроверки и полный прогон тестов — в переднем
  плане с таймаутом, а не фоновой задачей, на которой кончается ход: уснувшего так
  участника тик не видит; копия каждого письма ведущему — `team-mail.sh … lead …`
  тем же текстом, что ушёл в SendMessage. STUCK — и письмо, и `status=stuck`;
  после ответа ведущего — снова `status=running`.
- **Рецензент** (только Write): карточку ведущий заводит `idle` (роль без задачи);
  `runs/unified-reviewer.json` рецензент переписывает целиком — `reviewing`
  с номером задачи в начале, `idle` после вердиктов; письмо SENSITIVE ведущему дублирует файлом
  в `mail/lead/`. Его Write расширен на эти два места; на исходники — по-прежнему нет.
- **Прокси**: то же, что кодер, плюс `note` с путём к маркеру движка; ENGINE_DOWN — письмо и
  `status=stuck`.
- Ведущий после спавна пишет в `runs/` только одно — `run-state.py set … status=stopped` участнику,
  которого он остановил (`TaskStop`) или заменил; это единственное исключение. В `mail/` — только ANSWER.
