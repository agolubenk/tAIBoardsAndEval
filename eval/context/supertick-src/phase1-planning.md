# Фаза 1: от задачи до команды

От первой строки пользователя до собранной команды и запущенного супервизора. Шаги идут по номерам;
SIMPLE просто пропускает те, что ему не положены. Корень плагина `{plugin}` уже найден на шаге 0
SKILL.md; во все промпты подставляй его абсолютное значение из строки `Plugin root:`. `<RUN DIR>` —
абсолютный путь `.claude/teams/feature-<имя>` в рабочем дереве.

Сквозное правило фазы: любой ответ исследователя, риск-тестера или архитектора ты сначала сохраняешь
в `reports/` и только потом действуешь по нему. Ответ субагента не переживёт compaction, файл —
переживёт.

## Карта маршрута

Первое, что видит пользователь, — карта всего пути одним блоком, пока сложность ещё не известна:

```
🚀 Запускаю команду: <фича одной строкой>
   разведка → оценка сложности → план → проверка плана и риски → реализация → проверка
   Перебивайте в любой момент, если что-то идёт не туда.
```

Тут же — строка шага 0 (корень плагина и номер способа). Если каталог прогона с выбранным именем уже
существует, остановись и спроси пользователя (SKILL.md, «Главные правила»): чужой прогон не
перетирается.

## Шаг 0b: движки

Один раз за прогон реши, кто стоит за каждой ролью: Claude или внешний CLI из
`~/.claude/agent-teams.json`. Процедура целиком — `engines.md, «Шаг 0b: разрешение движков»`.
Коротко:
- нет конфига — все роли на Claude, ничего не печатаешь и лишних вызовов не делаешь;
- `--engines=off` или `"enabled": false` — то же;
- иначе одной командой `command -v` проверяешь бинари только тех движков, что названы в `roles`,
  строишь таблицу роль → движок и пишешь её в state.md (`## Engines`, со строкой `- launcher:`);
- одна строка ⚙️ в ленту — только если хоть одна роль ушла не на Claude.

Перед каждым спавном ниже сверяйся с таблицей:

| Роль на движке | Как спавнить |
|---|---|
| одноразовая (исследователь, риск-тестер) | без субагента: промпт в файл и `run-engine.sh` (механика A, `engines.md`) |
| участник (техлид, архитектор, рецензент, кодер) | `supertick:proxy-teammate` под тем же именем, шапка прокси — `engines.md, «Механика B: прокси»` |
| на Claude | тип `supertick:<роль>` из SKILL.md |

Три спавна идут встроенными типами Claude Code (`Explore`, `general-purpose`) — им это разрешено,
потому что плагин называет их сам; другие чужие типы не спавнятся. В таблице ищутся: веб-исследователь
(`general-purpose`) — роль `web-researcher`, скан наследия фазы 3 (`Explore`) — `legacy-scanner`.
Межзадачная сверка фазы 3 (`Explore`) — не роль конфига, всегда на Claude.
Внешний движок получает тот же промпт, что получил бы Claude, плюс выходной контракт: короче писать
нельзя.

## Шаг 1: ориентация

Ты один и быстро:
1. Прочитай `CLAUDE.md` проекта и посмотри верхний уровень дерева (Glob).
2. Есть `.conventions/` — прочитай все `gold-standards/*`: это образцы, их ты вложишь кодерам сам
   (20–30 строк каждый — единственное исключение из «ведущий не читает код»).
3. `package.json` и исходники не открывай — это работа исследователей.

## Шаг 2: исследователи

Цель — две вещи: (а) контекст кода — стек, структура, слои, команды сборки и тестов; (б) образцы —
настоящие файлы, по которым будут писать кодеры.

| Ситуация | Что делать |
|---|---|
| `--no-research` | никого не звать, планировать по тому, что есть |
| аргумент — бриф интервью `.briefs/<имя>.md` | прочитать его: `## Project Context` закрывает (а) |
| (а) не закрыто | `codebase-researcher` |
| нет `gold-standards/` под эту фичу | `reference-researcher` |
| незнакомая библиотека или шаблон | веб-исследователь (`general-purpose`, WebSearch или Context7) |

- Бриф интервью позволяет пропустить `codebase-researcher`, но это решение ты принимаешь явно и
  пишешь строкой в ленту: однажды разведку так пропускали каждый раз, и места вне брифа никто не
  искал.
- Разделы брифа читаются по именам: `## Intent`, `## Audience`, `## Success Criteria`,
  `## Exclusions`, `## Additional Context`, `## Project Context`. Критерии успеха уйдут в
  `## Business Criteria` плана проверки, исключения — в Out of scope задач.
- Все исследователи — параллельно, в одном ходу. В ленту — одна строка 🔍 до (сколько и зачем) и 3–4
  строки после: стек, сколько слоёв затронуто, где образцы, что удивило.
- Веб-исследователь отвечает в 10–20 строк: подход и почему, ключевая библиотека, 2–3 ловушки,
  псевдокод.
- Посреди прогона исследователя зовут только тогда, когда ответа нет в уже собранном, и не на каждый
  STUCK.

## Шаг 3: сложность и план

### Классификация

Механическая, без торга. Шаг A — шесть признаков MEDIUM:
1. затронуто два слоя и больше (БД, API, интерфейс);
2. меняется существующий ход логики (новая ручка в существующем роутере не считается);
3. рядом с чувствительным: файлы импортируют или вызывают модули входа, оплаты, прав;
4. после нарезки три кодовые задачи и больше (задача конвенций не считается);
5. хотя бы одна задача блокирует другую;
6. создаётся или правится пять файлов кода и больше (сливать задачи, чтобы уйти от признака, нельзя).

0–1 признак — SIMPLE. 4 и больше — сразу COMPLEX, шаг B не нужен. 2–3 — предварительно MEDIUM, и
тогда шаг B — семь признаков COMPLEX:
1. все три слоя сразу;
2. меняется поведение, на котором стоят другие фичи (общие утилиты, middleware, файл импортируют
   три модуля и больше);
3. правится сам код входа, оплат или биллинга, а не соседний;
4. пять задач и больше;
5. цепочка из трёх зависимых задач (A → B → C);
6. для такого кода в проекте нет образца;
7. десять файлов кода и больше.

В признаках A6 и B7 тексты, которые лишь описывают правку кода той же фичи, входят в работу, но не
в счёт. Где тексты и есть продукт (роли и справки плагина), они — код. Причина: 22.10.2026,
feature-trial-medium — два скрипта на 36 строк потянули 12 текстов, и подсчёт дал COMPLEX.

Ни одного B — MEDIUM, хотя бы один — COMPLEX. Итог печатается фиксированным блоком:

```
⚖️ Сложность
   A: <n>/6 — <какие сработали и чем доказано>
   итог A: <SIMPLE | MEDIUM?, считаю B | COMPLEX, B не считаю>
   B: <n>/7 — <какие> | пропущено
   FINAL: <SIMPLE | MEDIUM | COMPLEX> — <что это значит для команды>
```

С аргументом `--complexity=<уровень>` блок печатается так же, но FINAL берётся из аргумента:
`FINAL: MEDIUM — задано пользователем (подсчёт дал COMPLEX)`. В state.md пишется та же строка.

Доработка после релиза (замечание, сломанная мелочь, пропущенный пункт макета) — отдельный прогон:
PLAN.md и DECISIONS.md родителя идут как контекст, признаки считаются по самой доработке.

### Имя и файлы

- Имя прогона — `feature-<короткое-имя>`, каталог `.claude/teams/feature-<короткое-имя>/`.
- VERIFICATION_PLAN.md для SIMPLE и MEDIUM пишешь сейчас; для COMPLEX — после дебата, из проверок
  архитекторов. Шаблон и правила разделов — ниже, «Шаблоны».
- Блок образцов для кодеров: 3–5 примеров на 100–150 строк вместе — у каждого слой, путь, содержимое
  и на что смотреть, плюс главные правила конвенций. Источник — `gold-standards/` или ответ
  `reference-researcher`.
- PLAN.md пишешь только ты, по шаблону ниже; статусы и правила выдачи задач — `team-runtime.md, «План в PLAN.md»`.

### Правила нарезки задач

- Критерий приёмки — то, что можно проверить: команда с ожидаемым выводом или факт о файле.
  «Работает правильно» критерием не является: по этим строкам задачу примет одноразовый проверяющий,
  видящий лишь дифф (`phase2-monitoring.md, «Приёмка DONE»`).
- `Sensitive: yes — <почему>` ставь по списку файлов, если задача трогает одно из: деньги, начисление
  баланса или токенов, вход и права, миграция БД, общая инфраструктура (то, что лежит под каждым
  запуском, — как в SKILL.md, «Ревью: одни ворота на задачу»). В одном прогоне задача про оплату без этой строки прошла
  молча, а второе мнение потом нашло в ней три настоящих дефекта.
- Один файл — одна задача. Если общего файла не избежать, он закрепляется за одной задачей, другие
  получают его в `Blocked by:`: `git commit -- <файл>` берёт файл целиком, вместе с чужой
  незаконченной правкой.
- Последняя задача плана — всегда обновление `.conventions/`. Она не кодовая: в фазе 2 не спавнится,
  в «все кодовые DONE» не входит, `Blocked by:` у неё — фаза 3. Ссылаться ей на стабильные якоря
  (экспортируемое имя, `data-testid`), а не на номера строк: параллельная правка сдвигает их.
- Если у проекта есть правило коммита (пользователь, подпись, стиль сообщения), впиши его строкой
  `Commit:` в шапку плана — она главнее общих правил роли кодера.

## Шаг 4: проверка плана

**SIMPLE** — пропуск.

**MEDIUM.** Строка в ленту, спавн `tech-lead` (шаблон ниже), жди `READY`. Затем:

```
VALIDATE PLAN: <RUN DIR>/PLAN.md
DoD: <RUN DIR>/VERIFICATION_PLAN.md, раздел Definition of Done
Проверь объём задач, списки файлов, зависимости и подход.
```

Ответ — `PLAN OK` или список правок. Правки вносишь в PLAN.md сам и отправляешь `VALIDATE PLAN` ещё раз.

**COMPLEX — дебат архитекторов.**
1. Спавн трёх архитекторов параллельно (шаблон ниже) — `architect-frontend` (компоненты, состояние,
   шаблоны интерфейса, скорость на клиенте, доступность, дизайн-система), `architect-backend` (API,
   схема БД, целостность данных, скорость на сервере, масштаб, миграции), `architect-systems`
   (стратегия тестов, CI/CD, конвенции, удобство разработчика, деплой, мониторинг). В проекте без
   интерфейса frontend отвечает за тексты, которые читают люди и роли. Каждый отвечает `READY`.
2. После трёх `READY` — каждому `DEBATE PLAN: <RUN DIR>/PLAN.md` с фичей, DoD, контекстом кода,
   образцами и составом. Это раунд 1.
3. Архитекторы друг другу не пишут. Каждый кладёт `reports/debate-r<N>-<имя>.md` и отвечает тебе
   `ROUND <N> from <persona>: AGREE` или `ROUND <N> from <persona>: CONTEST` с путём файла. Файл
   раунда 2 и дальше начинается блоком «снято / держу»: что из своего снял, что держит и почему.
4. Жди все три ответа раунда. Кто молчит — `STATUS?`; ответа нет — повтори ему раунд.
5. Все `AGREE` или это был раунд 3 — всем `FINAL: SPEC APPROVED or FINAL POSITION`. Иначе —
   `ROUND <N+1>. <пути трёх файлов раунда N>`. Больше трёх раундов не бывает. После раунда 2 спорным
   остался один пункт — `FINAL` можно дать досрочно: пункт решаешь ты и пишешь в DECISIONS.md, как
   при `FINAL POSITION`. Причина: 22.10.2026, feature-trial-medium — раунд 3 решал один пункт и
   кончился перекрёстом позиций.
6. Ты переносишь раунды, но не аргументы: пересказывать одному архитектору файл другого нельзя.
7. В ленту — по строке ⚔️ на персону после каждого раунда и строка о том, чем кончился спор.

После `FINAL` жди три ответа.
- Все `SPEC APPROVED from …` — собери рекомендации в PLAN.md и назначь главного: фича в основном про
  интерфейс — frontend, про API и БД — backend, сквозная или инфраструктурная — systems. Прокси
  (архитектор на внешнем движке) главным не назначается, если есть архитектор на Claude: в
  feature-trial-medium (22.10.2026) прокси systems трижды терял по 15 минут.
- Есть `FINAL POSITION from …` — решаешь ты, записываешь разногласие в DECISIONS.md и тоже
  назначаешь главного.
- Главному — `PRIMARY ARCHITECT`: он создаёт DECISIONS.md с итогом дебата и ведёт риски шага 4b.
  После его ухода DECISIONS.md и эскалации переходят к тебе.
- VERIFICATION_PLAN.md собираешь из проверок: Build & Types и Tests — от systems, Browser Checks — от
  frontend, Spec Checks — от backend (конфиг и конвенции — от systems), Human Checks — всё, что не
  автоматизируется.

## Шаг 4c-4: бриф плана

Обязательная точка с пользователем на MEDIUM и COMPLEX (SIMPLE её пропускает). Пишешь прямо в чат,
не в `AskUserQuestion`.

COMPLEX — полный блок: фича; сложность (сколько архитекторов, сколько раундов); задачи по строке
смысла на каждую; ключевые решения дебата с персоной-автором; что изменится в коде; что вне объёма;
открытые вопросы. Сразу за ним — шаг 4a.

MEDIUM — короткая версия на 5–8 строк, после ответа техлида.

## Шаг 4a: развилки дизайна

Просмотри все задачи на развилки, которые человек увидит: компоновка экрана, путь пользователя,
архитектурный выбор, модель данных, влияющая на то, что видно, интеграции. Пропуск разрешён только
для чистого бэкенда, рефакторинга, багфиксов и брифа, где всё уже решено. Ничего не нашёл — строка
в журнал: «просмотрено <N> задач, развилок нет».

На каждую развилку — один `AskUserQuestion` с 2–3 конкретными вариантами:
- для экрана — грубый ASCII-макет на 3–5 строк в описании варианта; длинную схему сначала покажи в
  чате, а в кнопках оставь короткие метки;
- объясняй цену выбора, а не устройство реализации; чисто техническое — вариант «на ваше усмотрение»;
- один разумный вариант — не спрашивай; больше трёх развилок на фичу — не бывает;
- выбор пользователя запиши в PLAN.md (затронутые задачи) и в DECISIONS.md.

## Шаг 4b: риски

Только MEDIUM и COMPLEX.
1. `IDENTIFY RISKS` техлиду (MEDIUM) или главному архитектору (COMPLEX): что сломается — целостность
   данных, безопасность, поломка существующего, стыки задач, крайние случаи, скорость, внешние API.
   Ответ — не меньше трёх рисков: серьёзность CRITICAL / MAJOR / MINOR, задачи, что проверить.
   Строка ⚠️ в ленту со списком.
2. Риск-тестеры: по одному на каждый CRITICAL и не больше трёх на MAJOR; MINOR не проверяются. Все
   параллельно, шаблон ниже. Каждому — свой `<RUN DIR>/tmp/risk-<n>/` для скриптов.
3. Риск-тестер на внешнем движке: промпт в `engine/risk-tester-<n>/draft.prompt.md` плюс выходной
   контракт, `run-engine.sh` в режиме записи, `--timeout 3600`, `--report risk-<n>.md`. Отчёт без
   скрипта и его вывода — не вердикт: возобнови сессию и потребуй доказательства.
4. По вердикту каждого — строка 🧪. Отчёты лежат в `reports/risk-<n>.md`.
5. `RISK ANALYSIS RESULTS:` с находками — техлиду или главному. Он вносит подтверждённые риски в
   DECISIONS.md со смягчением и новыми критериями, объясняет, почему отклонены теоретические, и
   предлагает новые задачи и порядок.
6. Ты: новые задачи — в PLAN.md перед задачей конвенций; новые критерии и блокеры — в задачи;
   смягчения — в `## Risk Mitigation Checks` строками `RISK-<n> (<серьёзность>): что проверить`;
   риск, требующий решения человека, — пользователю. Строка 📝 с итогом изменений плана.

Спор риск-тестера и техлида о серьёзности решает техлид и пишет решение в DECISIONS.md.

## Шаг 5: спавн команды

Порядок важен: сначала рецензент, потом кодеры, в конце state.md и цикл.

**5a. Архитекторы уходят (COMPLEX)** — только после завершённого шага 4b. Всем трём — `DEBATE COMPLETE — HAND OVER AND STAND DOWN.` и
путь `reports/review-brief-<имя>.md`: бриф для рецензента не длиннее 25 строк — что проверить в своём
домене на этой фиче, ловушки, всплывшие в дебате, подозрительные файлы и границы. Затем они пишут
`DONE: review brief <путь>` и останавливаются. Главный уходит тоже: после дебата его звали дважды
(две эскалации, ни одного арбитража), а держать его живым дорого. Эскалации и арбитраж кругов ревью
теперь твои, сверка задач между собой — одноразовый проверяющий в фазе 3. Подтверждённый риск,
меняющий решение, — повод переписать бриф: 22.10.2026 бриф ушёл до риск-тестеров, и образец в нём
через 10 минут заменил RISK-3.

**5b. Рецензент.** Карточка без задачи (родится `idle`), затем спавн `unified-reviewer` по шаблону:

```bash
mkdir -p <RUN DIR>/mail/lead && python3 {plugin}/scripts/run-state.py new <RUN DIR> unified-reviewer role=reviewer
```

Так же заводятся карточки техлида на шаге 4 (`tech-lead role=tech-lead`) и архитекторов перед
их спавном (`architect-<persona> role=architect`). Промпт кончается просьбой ответить `READY` и закончить ход; его `READY`
в ленту не идёт. Строка `SECOND REVIEWER AVAILABLE: <engine>` — только если в `## Engines` у
`second-reviewer` стоит движок; при `none` или без конфига строки нет совсем — ни заглушки, ни
`none`: выдуманное значение включит второе мнение там, где его нет. То же правило — при каждом
следующем спавне рецензента (ротация, ENGINE_DOWN). На COMPLEX в промпт идут все три брифа
архитекторов, целиком или путями; рецензент стартует около 90k токенов и таким остаётся.

**5c. Перед кодерами.**
- `git rev-parse HEAD` — это значение пойдёт в `## Base Commit:` state.md (шаг 5e).
- `git status --short`: чужие правки (другая команда, работа пользователя) идут в каждый промпт
  кодера блоком `--- FOREIGN CHANGES ---` — не трогать, не индексировать, не чистить. Если файл
  задачи в этом списке — кодер коммитит его, собрав содержимое из закоммиченной версии плюс свою
  правку, и пишет об этом в DONE.
- Пустые `pending.log` и `LEGACY_REPORT.md` (шаблон ниже).

**5d. Кодеры.** На каждую доступную задачу, пока кодеров не больше `--coders`:
1. `Status: IN_PROGRESS(coder-<N>)` в PLAN.md.
2. Одной командой, прямо перед вызовом — потому что `spawnedAt` карточки запускает часы:
   ```bash
   mkdir -p <RUN DIR>/mail/lead && python3 {plugin}/scripts/run-state.py new <RUN DIR> coder-<N> role=coder task=<id> files=<a,b> checkAfterSec=<300|900> nonGoals=<Out of scope>
   ```
   `checkAfterSec=300` — для задачи с `Sensitive:` или подтверждённым риском, иначе 900.
3. Спавн по шаблону кодера. Каждому кодеру — свой `<RUN DIR>/tmp/coder-<N>/` для временных файлов:
   общий scratchpad сессии кодеры однажды затёрли друг другу, и один прогнал тест в чужом дереве.

**5e. state.md** — по шаблону ниже. После спавна ты не пишешь в `mail/` (кроме ответов `ANSWER`), а в
`runs/` — только одно: `python3 {plugin}/scripts/run-state.py set <RUN DIR> <имя> status=stopped`
участнику, которого остановил (`TaskStop`) или заменил (новое имя, мёртвый прокси,
`second-reviewer-<id>` после отмены или когда его находки пересылал ты; отправив находки сам, он
ставит себе `done`).

**5f. Цикл.** Запусти супервизор фоном и закончи ход — `supervisor.md, «Ход ведущего с супервизором»`:

```
Bash(run_in_background=true):
  bash {plugin}/scripts/supervisor-wait.sh <RUN DIR> --root <абсолютный корень рабочего дерева>
```

Путь каталога прогона — только абсолютный: с относительным цикл в фоне терял каталог. Последняя
строка фазы в ленте — 👥 «команда собрана: <кто>, задач <n>, работают <k>».

### VERIFICATION_PLAN.md

Имена разделов — ключи разбора в фазе 3; пустой раздел опускается. В фазе 3 берутся только пункты
`- [ ]`.

```
# Verification Plan
## Feature: <фича>

## Definition of Done
- <планка качества из CLAUDE.md и проекта>

## Business Criteria
- [ ] <каждый критерий успеха брифа — как проверка>
- [ ] Исключения соблюдены: <что не тронуто>

## Risk Mitigation Checks
- [ ] RISK-1 (CRITICAL): <что проверить>

## Build & Types
- [ ] `<команда сборки>` — без ошибок

## Tests
- [ ] `<команда тестов>` — <ожидаемый итог>

## Browser Checks
- [ ] <URL>: <что видно и что нажимается>

## Spec Checks
- [ ] <критерий приёмки или факт о файле>

## Visual Checks
- [ ] <страница>: макет <файл>, URL <адрес>, ширина компьютера и телефона

## Human Checks
- [ ] <что проверить>
  → команда `<…>`, сигнал успеха `<…>`, окно `<сколько ждать>`, образец отказа `<…>`
```

- Сборка и тесты — от исследователей, браузер — из критериев интерфейса, спецификация — из критериев
  приёмки, ручное — всё, что требует суждения.
- Ручная проверка без расплывчатости: точная команда, точный сигнал, окно времени и образец отказа,
  особенно для деплоя, биллинга, очередей, миграций, middleware входа. «Задеплой и посмотри» нельзя.
- Фича с живым соединением получает браузерный сценарий в DoD: модульные тесты такую регрессию не
  ловили, браузерный прогон — поймал.
- Фича по макету всегда получает `## Visual Checks` (сейчас или в фазе 3).

### state.md

```
# Team State — feature-<имя>

Восстановление после compaction: один тик; затем этот файл, PLAN.md, pending.log (доставить все OPEN);
проверить `test -x <Plugin root>/scripts/supervisor-tick.py`; исполнять инструкции текущей фазы.

## Phase: EXECUTION
## Team Name: feature-<имя>
## Complexity: <SIMPLE | MEDIUM | COMPLEX>
## Base Commit: <sha из git rev-parse HEAD>

## Инструкции фазы 2
1. Спать на цикле; проснувшись — действия тика по приоритетам (phase2-monitoring.md).
2. DONE → ACCEPTING и приёмщик по диффу; PASS → DONE и новые кодеры; FAIL → один раз REOPENED.
3. Ответы на QUESTION / ESCALATION / STUCK — файлом ANSWER, потом сообщением; затем ack.
4. Ротация рецензента каждые 3 принятые задачи.
5. Все кодовые задачи DONE → `## Phase: VERIFICATION`.

## Инструкции фазы 3
1. Задача конвенций → сверка задач между собой → проверяющие по VERIFICATION_PLAN.md.
2. Доработки (до 3 итераций) → наследие → сводка → завершение → ручные проверки.

## Supervisor
- loop: bash <Plugin root>/scripts/supervisor-wait.sh <RUN DIR> --root <рабочее дерево>
- tick: python3 <Plugin root>/scripts/supervisor-tick.py <RUN DIR>
- last wake: <HH:MM> <причина>

## Engines
- launcher: <Plugin root>/scripts/run-engine.sh
- fallback: claude
- <роль>: <движок>[, запасной ход: claude — бинарь не найден]
- <роль>: <движок> — назначено при запуске

## Team Roster
- unified-reviewer: active (supertick:unified-reviewer), задач с последней ротации: 0
- tech-lead: active (supertick:tech-lead)
- coder-1: task 1 (supertick:coder)

## Second opinions
```

- `## Phase:` — `EXECUTION` до конца фазы 2, затем `VERIFICATION`; тик читает это слово.
- `## Engines` пишется только при конфиге движков; нет раздела — всё на Claude. Роль, которую ты
  отдал движку сам при запуске (политика владельца, `engines.md`), — строкой «назначено при запуске».
- Архитекторы, если были, — в `## Team Roster` со статусом `STOOD_DOWN`.
- `## Second opinions` — по строке `- second-reviewer-<id>: task #<id>, spawned <HH:MM>` на живой

- Статусы задач сюда не копируются — они только в PLAN.md.
