# Движки: кто стоит за ролью

Роль команды можно отдать внешнему CLI-агенту (Codex, Kimi, Grok, Cursor): другая модель —
другое слепое пятно. Без конфига всё на Claude, и шаг 0b ничего не стоит.

В этой справке `{plugin}` — корень плагина из строки `Plugin root:` в state.md (у ролей — из
строки `PLUGIN:` шапки промпта). Внешний движок плейсхолдеров не раскрывает, поэтому в его
бриф попадают только абсолютные пути: ни `{plugin}`, ни переменных окружения.

## Конфиг и совместимость

Один файл на пользователя: `~/.claude/agent-teams.json`. Проектного конфига нет, путь тот же,
что был у предыдущей линии плагина, и существующий файл работает без единой правки.

- Нет файла, не читается, битый JSON — все роли на Claude. На битом JSON одна строка
  предупреждения в ленту, в остальных случаях тишина.
- Самая короткая форма: `{"roles": {"<id>": "<engine>"}}`. Роль, не названная в `roles`, идёт
  на Claude. Исключение — `second-reviewer`: не назван — выключен, а не на Claude. Новая роль
  не должна включаться молча оттого, что её нет в конфиге.

| Ключ | Что значит |
|---|---|
| `enabled` | общий выключатель, по умолчанию `true`; `false` — всё на Claude |
| `fallback` | что делать, если движок недоступен: `"claude"` (по умолчанию, тихо перейти на Claude) или `"fail"` (остановить прогон); `second-reviewer` от обоих свободен — его просто пропускают |
| `roles.<id>` | строка-движок или объект `{engine, model?, effort?, sandbox?}`; `sandbox` — `read-only` или `workspace-write`, у cursor превращается в `mode_flags` |
| `engines.<name>` | переопределение пресета: `model`, `effort`, шаблоны `cmd` и `resume`, `mode_flags`, `session`, `result` |

Аргумент запуска `--engines=off` действует как `enabled: false` на один прогон.

**Правила совместимости с боевым конфигом:**
- Ключ, который начинается с `_`, игнорируется на любом уровне вложенности (`_readme`, `_why`,
  `_policy`, `_note`, `_mode_flags`, `_session`, `_result`, `_path`, `_trust`, `_models*`,
  `_retired_*` и любые другие). Это комментарии владельца.
- В `roles` бывают роли других плагинов (`research-challenger`, `research-critic`,
  `rollback-critic`). Это не ошибка: в таблицу движков и в ленту они не попадают.
- `engines.<name>` переопределяет пресет поле за полем: заданное поле — из конфига, остальные —
  из пресета. Целиком пресет не заменяется. Итоговый argv всё равно проверить: однажды блок
  `cmd`/`resume` в конфиге был без `--` перед промптом, и оба исследователя умерли на старте.
- `roles.<id>` — строка или объект, оба вида читаются одинаково.
- `mode_flags` — объект `{"read": "...", "write": "..."}`.
- `session` у cursor — регулярка для id сессии, `result` — имя поля ответа. Скрипту запуска
  первая не нужна: JSON cursor он разбирает сам.
- Снятые id `security-reviewer`, `logic-reviewer`, `quality-reviewer` — одно предупреждение и
  игнор. Их движок на `unified-reviewer` молча не переносится.

Пример конфига — `agent-teams.example.json`: все его ключи без `_` есть и в боевом файле.

## Реестр ролей

Вид роли определяет механику: одноразовая на Claude — субагент `Task()`, на внешнем движке —
механика A; участник на Claude — обычный участник команды, на внешнем движке —
`supertick:proxy-teammate` под тем же именем, механика B.

| id роли | вид | движки | когда |
|---|---|---|---|
| `lead` | оркестратор | только Claude | вызов навыка |
| `codebase-researcher` | одноразовая | claude, codex, kimi, grok, cursor | фаза 1, шаг 2 |
| `reference-researcher` | одноразовая | claude, codex, kimi, grok, cursor | фаза 1, шаг 2 |
| `web-researcher` | одноразовая (`general-purpose`) | claude, grok (живой поиск) | фаза 1, шаг 2 |
| `risk-tester` | одноразовая | claude, codex, cursor | фаза 1, шаг 4b |
| `acceptance-checker` | одноразовая, на каждую задачу | только Claude (`supertick:spec-verifier`) | фаза 2, каждый DONE |
| `ci-verifier` | одноразовая | claude, codex, cursor | фаза 3 |
| `spec-verifier` | одноразовая | claude, codex, cursor | фаза 3 |
| `browser-verifier` | одноразовая | только Claude (Chrome MCP) | фаза 3 |
| `legacy-scanner` | одноразовая (Explore) | claude, codex, cursor | фаза 3, наследие |
| — (межзадачная сверка) | одноразовая, встроенный тип `Explore`, не роль конфига | только Claude | фаза 3, SIMPLE и COMPLEX |
| `tech-lead` | участник | claude, codex, kimi, grok, cursor | фаза 1, MEDIUM |
| `architect` | участник | claude, codex, kimi, grok, cursor | фаза 1, COMPLEX |
| `architect-frontend`, `architect-backend`, `architect-systems` | участник | переопределяют `architect` для своей персоны | фаза 1, COMPLEX |
| `unified-reviewer` | участник | claude, codex, kimi, cursor | шаг 5, любой уровень |
| `second-reviewer` | участник на одну задачу, имя `second-reviewer-{id}` | claude, codex, kimi, cursor; нет ключа — выключено | фаза 2, по SENSITIVE |
| `coder` | участник | claude, codex (экспериментально) | шаг 5 и фаза 2 |

- `lead`, `browser-verifier` и `acceptance-checker` любое назначение, кроме Claude, игнорируют
  с одним предупреждением: приёмщик на Cursor `--mode ask` дал ложный FAIL, не запустив тесты.
- Cursor `--mode ask` shell не пускает: 22.10.2026 `spec-verifier` пропустил 2 из 10 пунктов-
  команд. Роль с командами на cursor берёт `.write` и контракт «файлы не менять» — или Claude.
- Колонка «движки» — совет, а не запрет: конфиг может назначить любое из реестра.
- Лучше всего переносятся роли «прочитать и выдать список»: рецензенты, исследователи,
  проверяющие, риск-тестер; `second-reviewer` — в первую очередь, его смысл и есть в другой
  модели. `tech-lead`, `architect` и `coder` лучше держать на Claude.
- Боевой конфиг владельца назначает этому плагину: `risk-tester`, `codebase-researcher`,
  `reference-researcher`, `spec-verifier`, `legacy-scanner` (cursor, `composer-2.5`) и
  `second-reviewer` (cursor, `gpt-5.6-sol-high`).
- Политика владельца: второй и следующие кодеры могут идти через Cursor, но только на
  механических задачах; это решает ведущий при запуске, а не ключ `roles`.

## Шаг 0b: разрешение движков

Один раз за прогон, сразу после шага 0. Таблица остаётся до конца прогона.

1. Прочитать конфиг. Нет — всё Claude, шаг закончен, в ленту ничего. Битый JSON — то же плюс
   строка предупреждения.
2. `--engines=off` или `enabled: false` — всё Claude, конец.
3. Одной командой `command -v` проверить бинари только тех движков, что упомянуты в `roles`.
   У cursor бинарь — `cursor-agent`, никогда `agent`. Бинаря нет — такие роли по `fallback`;
   у `second-reviewer` — `none`.
4. Собрать таблицу роль → движок и записать в state.md разделом `## Engines` со строкой
   `- launcher: <абсолютный путь {plugin}/scripts/run-engine.sh>`. Роли чужих плагинов не
   включать.
5. `second-reviewer` решается здесь же и записывается как любая роль. Он `none`, если ключа
   нет, бинаря нет или его разрешённый движок совпал с движком `unified-reviewer`: то же
   мнение от той же модели ничего не добавит. Совпадение — одно предупреждение в ленту.
   Значение `none` нигде не печатается и само по себе строку ленты не вызывает.
6. Сравнение движков делается только здесь, по разрешённым значениям. Посреди прогона оно не
   пересматривается; единственное исключение — `ENGINE_DOWN` рецензента
   (`phase2-monitoring.md`, «Таблица событий»).
7. Строка ⚙️ в ленту — только если хоть одна роль не на Claude: какие роли на каких движках,
   остальные на Claude. Роль ушла на запасной ход — строка «движок не найден, роль на Claude».

По `## Engines` фаза 1 решает, получит ли рецензент строку `SECOND REVIEWER AVAILABLE: <engine>`:
только при движке у `second-reviewer`. При `none` и без конфига строки нет вовсе.

Перед каждым спавном в фазах 1–3 ведущий смотрит движок роли в этой таблице. Встроенные типы
Claude Code — только у названных в реестре: `general-purpose` у `web-researcher`, `Explore` у
`legacy-scanner` и у межзадачной сверки; она в `roles` не назначается.

## Запуск через run-engine.sh

Любой вызов внешнего движка — и одноразовой роли от ведущего, и каждый ход прокси — идёт
через `{plugin}/scripts/run-engine.sh`. CLI напрямую из Bash не вызывается ни в переднем
плане, ни фоном, и `&` в конце команды не ставится.

Почему: большой `timeout` (600000) у вызова CLI в переднем плане Claude Code уводит в фон
(23.09.2026, 5 из 5). Прокси ждал файл вывода фоновой задачи (одно `EXIT:0`), затёр им ответ и
запустил промпт заново: ~24 минуты впустую. `&` под `run_in_background` осиротил `cursor-agent`.

**Что делает скрипт.**
- Отцепляет рабочий процесс (`setsid nohup`) и за секунду возвращается, напечатав `pid=`,
  `out=`, `done=`, `result=`, при `--report` ещё `report=`, и строку `wait:` с командой ожидания.
- Рабочий процесс запускает команду движка со stdin из `/dev/null` под `timeout` (`--timeout`,
  по умолчанию 3600 с), пишет вывод в `<out>.part`, по выходу движка атомарно — в `<out>`.
- Достаёт id сессии в `session.txt` (cursor — поле `session_id` JSON, codex и kimi — регулярка
  пресета, grok — `--session`) и ответ в `<out>.result.md` (поле `result` JSON или весь вывод).
- `--report <имя>` копирует ответ в `reports/<имя>`, только если вызов успешен. Занятое имя
  отчёта не затирается: появится `<имя>-<метка>.md`, затем `-2`, `-3`.
- Последним пишет маркер `<out>.done`: строки `status=` (`done` или `failed`), `exit=`,
  `reason=`, `started=`, `ended=`, `wall_s=`, `session=`, `out=`, `result=`, `report=`. Есть
  маркер — значит, на диске уже всё.
- Причины провала в `reason`: `timeout <N>s`, `exit <N>`, `engine reported is_error`,
  `no reply in output`, `no JSON reply (no session_id)`.
- Метки никогда не переиспользуются: занятая `004` даст `005`, занятая `r2` — `r2-2`. Промпт
  копируется рядом с выводом как `<метка>.prompt.md`.
- Ledger: `launch` сразу, с pid; `done` или `failed` по выходу, со временем `date -Is`.
- Отказ до запуска, код 2: нет `--role`, `--run-dir` или `--prompt`, нет команды после `--`,
  пустой промпт, нет бинаря (у `cursor-agent` с подсказкой про PATH), `--timeout` не число, нет python3.

**Файлы роли** — `<RUN DIR>/engine/<имя участника>/`: `NNN.prompt.md`, `NNN.out.part`,
`NNN.out`, `NNN.out.pid`, `NNN.out.result.md`, `NNN.out.done`, `session.txt`; вызывающий сам
пишет `draft.prompt.md` и `NNN.out.taken`. Каталог — по имени участника, а не по голой роли:
у второго мнения это `engine/second-reviewer-{id}/`, иначе два экземпляра делили бы одну
сессию. Файлы `engine/` не удаляются, не переписываются и ничем не перекрываются.

**Команда движка** — argv после `--`, а не строка: никакого `eval` и вложенных кавычек.
Плейсхолдеры `{prompt}` и `{prompt_file}` подставляет рабочий процесс. Промпт приходит одним
аргументом, а ядро ограничивает аргумент 128 KiB: промпт больше — exit 126 и `failed`.

**Потолок** — только `--timeout`: около 1800 для рецензентов, `second-reviewer` и архитекторов,
3600 и больше для `coder` и `risk-tester`. Меньше 1200 не ставить: grok-xhigh тратит 3–6 минут
на раунд архитектора и 7–16 минут на второе мнение.

**Ожидание** — отдельный вызов, только по маркеру. Ведущий ждёт фоном (`run_in_background:
true`): его будит конец фоновой задачи. Участник — в переднем плане, Bash `timeout` 570000, до
9 минут за вызов, повтор до маркера; между повторами `run-state.py set … note="ENGINE WAIT"`:

```
until [ -f <out>.done ]; do sleep 5; done; cat <out>.done                      # ведущий, фоном
timeout 540 sh -c 'until [ -f <out>.done ]; do sleep 5; done'; cat <out>.done  # участник
```

Почему: участника конец фоновой задачи не будит (22.10.2026: прокси-архитектор ждал `.done`
фоном и трижды терял по 15 минут до P0). Не ждать файл вывода фоновой задачи и `<out>` (он чуть
раньше ответа), не ждать по таймеру вместо маркера. Ответ — из `<out>.result.md`, итог — из
маркера; прокси сразу после чтения — `run-state.py set <RUN DIR> <имя> status=running
note="ENGINE READ"`, после пересылки — `touch <out>.taken`. Без `.taken` P0 `engine_result_unread`:
у прокси (у `engine/<имя>/` есть карточка `runs/<имя>.json`, не `stopped`/`done`) через 3 минуты,
пока карточка не новее `.done`, иначе через 15; у одноразовой роли ведущего — через 15 минут.

**Перед любым запуском** проверить состояние роли:

```
{plugin}/scripts/run-engine.sh --status <RUN DIR> <имя участника>
```

По строке на вызов: `RUNNING <base> pid=…`, `DONE-UNREAD <base> <поля .done>`, `taken <base> …`,
`DEAD <base> pid=… (no .done, process gone)`; вызовов нет — `no calls for <имя>`. При `RUNNING`
или `DONE-UNREAD` новый вызов не запускается: ждать или прочитать. Так ответ переживает и
рестарт сессии, и лимит API, уронивший участника.

## Пример: боевой cursor → argv

Исходник в конфиге:

    cmd:    cursor-agent -p --trust --output-format json --model {model} {mode_flags} -- "$(cat {prompt_file})"
    resume: cursor-agent -p --trust --output-format json --model {model} {mode_flags} --resume {session} -- "$(cat {prompt_file})"

Как из строки конфига получить аргументы скрипта:
1. Первый вызов роли берёт `cmd`, следующие — `resume` из `engines.cursor`; поля нет — из
   пресета.
2. `{model}`: сначала `roles.<id>.model`, потом `engines.cursor.model`, потом модель пресета.
3. `{mode_flags}`: роли чтения берут `engines.cursor.mode_flags.read`, `coder`, `risk-tester` и
   роли с командами («Реестр ролей») — `.write`. Строка режется по пробелам на отдельные
   аргументы (`--sandbox`, `enabled`, `-f`), а не идёт одним словом в кавычках.
4. `"$(cat {prompt_file})"` (и `"{prompt}"` у других пресетов) превращается в `'{prompt}'` в
   одинарных кавычках: оболочка вызывающего его не трогает, текст вставит рабочий процесс.
5. `{session}` — содержимое `engine/<имя>/session.txt`, только для `resume`.
6. `< /dev/null` выбрасывается: скрипт и так не даёт движку stdin.
7. `--` перед `'{prompt}'` остаётся; перед вызовом скрипта — `PATH="$HOME/.local/bin:$PATH"`.

`<RUN DIR>` — абсолютный путь из шапки промпта: относительный у фонового вызова теряется.
`{plugin}` прокси или ведущий подставляют сами из `PLUGIN:` / `LAUNCHER:` до запуска.

Режим чтения, архитектор-прокси `architect-backend`, раунд 1. Роль без `model` в `roles` (например,
`"architect-backend": "cursor"`) берёт модель движка по умолчанию, `engines.cursor.model`;
хвост после первого `--` совпадает с примером в шапке `run-engine.sh`:

    PATH="$HOME/.local/bin:$PATH" {plugin}/scripts/run-engine.sh --role architect-backend \
      --run-dir <RUN DIR> --prompt <RUN DIR>/engine/architect-backend/draft.prompt.md \
      --engine cursor --report debate-r1-architect-backend.md --timeout 1800 \
      -- cursor-agent -p --trust --output-format json --model grok-4.7-xhigh-fast --mode ask -- '{prompt}'

Тот же режим чтения, второе мнение по задаче 3. В боевом конфиге `roles.second-reviewer.model`
— `gpt-5.6-sol-high`, и правило 2 берёт его раньше модели движка:

    PATH="$HOME/.local/bin:$PATH" {plugin}/scripts/run-engine.sh --role second-reviewer-3 \
      --run-dir <RUN DIR> --prompt <RUN DIR>/engine/second-reviewer-3/draft.prompt.md \
      --engine cursor --task 3 --report review-task3-second-r1.md --timeout 1800 \
      -- cursor-agent -p --trust --output-format json --model gpt-5.6-sol-high --mode ask -- '{prompt}'

Режим записи, риск-тестер (боевой `roles.risk-tester` — cursor, `composer-2.5`):

    PATH="$HOME/.local/bin:$PATH" {plugin}/scripts/run-engine.sh --role risk-tester-1 \
      --run-dir <RUN DIR> --prompt <RUN DIR>/engine/risk-tester-1/draft.prompt.md \
      --engine cursor --task 3 --report risk-1.md --timeout 3600 \
      -- cursor-agent -p --trust --output-format json --model composer-2.5 --sandbox enabled -f -- '{prompt}'

Resume того же риск-тестера (id из `<RUN DIR>/engine/risk-tester-1/session.txt`, новая метка выберется сама):

    PATH="$HOME/.local/bin:$PATH" {plugin}/scripts/run-engine.sh --role risk-tester-1 \
      --run-dir <RUN DIR> --prompt <RUN DIR>/engine/risk-tester-1/draft.prompt.md \
      --engine cursor --task 3 --timeout 3600 \
      -- cursor-agent -p --trust --output-format json --model composer-2.5 --sandbox enabled -f --resume <session> -- '{prompt}'

Остальные пресеты — так же: `"{prompt}"` → `'{prompt}'`, без `< /dev/null`. Grok вдобавок получает
`--session <uuid>` у скрипта и тот же uuid в `--session-id`; свой формат вывода — `--session-regex`.

## Пресеты

Плейсхолдеры: `{prompt}` — текст файла промпта; `{prompt_file}` — путь к нему (для тех, кто
читает файл сам, — cursor); `{sandbox}` — `read-only` или `workspace-write` по нужде роли
(пишут `coder` и `risk-tester`, остальные читают); `{mode_flags}` — строка режима для той же
нужды; `{model}`, `{effort}` — роль или умолчание пресета; `{session}` — сохранённый id сессии.

Успех — по коду выхода и ответу модели, не по stderr. Все четыре проверены живыми вызовами
(kimi-code/k3, Cursor Agent CLI 2026.09.02 и 2026.09.10, codex-cli 0.146.0, grok-4.6): ответили
и после resume вспомнили сказанное. После обновления CLI — перепроверить.

**codex**
- cmd: `codex exec --skip-git-repo-check --sandbox {sandbox} -m {model} -c model_reasoning_effort="{effort}" "{prompt}" < /dev/null`
- resume: `codex exec resume {session} "{prompt}" < /dev/null`
- умолчания: model `gpt-5.6-sol`, effort `xhigh`; чтение — `read-only`, запись — `workspace-write`.
- Сессия — из строки вывода `session id: <uuid>`.
- В строковой форме `< /dev/null` обязателен: без него `codex exec` может повиснуть на stdin.
  На подписке ChatGPT работает только `gpt-5.6-sol`; просто `gpt-5.6` требует платного ключа API.
- Строка `failed to load models cache` в stderr бывает и на полном успехе — это не ошибка.

**kimi**
- cmd: `kimi -m {model} -p "{prompt}"` · resume: `kimi -r {session} -p "{prompt}"` · model `kimi-code/k3`.
- Сессия — из хвостовой строки вида `kimi -r session_…`.
- Флага песочницы нет, а `--auto` / `--yolo` с `-p` несовместимы: ролям с записью (`coder`,
  `risk-tester`) kimi не назначать. `-S` — синоним `-r`, но сам kimi печатает `-r`.

**grok**
- cmd: `grok --sandbox {sandbox} --always-approve -m {model} --effort {effort} --session-id {session} -p "{prompt}"`
- resume: `grok --sandbox {sandbox} --always-approve --effort {effort} -r {session} -p "{prompt}"`
- умолчания: model `grok-4.6`, effort `high`; песочница как у codex.
- Без `--always-approve` grok в пакетном режиме молча выходит, ожидая одобрения.
- Id сессии grok не печатает. Вызывающий создаёт его сам (`uuidgen`) до первого вызова роли,
  сразу кладёт в `session.txt` и передаёт скрипту `--session`. Голый `grok -r` берёт последнюю
  сессию каталога, и две роли молча делят один разговор. Id — настоящий UUID: читаемые имена
  grok отвергает.

**cursor**
- cmd: `cursor-agent -p --trust --output-format json --model {model} {mode_flags} -- "$(cat {prompt_file})"`
- resume: `cursor-agent -p --trust --output-format json --model {model} {mode_flags} --resume {session} -- "$(cat {prompt_file})"`
- умолчания пресета: model `cursor-grok-4.6-xhigh`; чтение — `--mode ask`, запись —
  `--sandbox enabled -f`. В боевом конфиге модель переопределена на `grok-4.7-xhigh-fast`.
- Сессия — поле `session_id` JSON-ответа, приходит в конце вместе с ответом в поле `result`.
- Бинарь — только `cursor-agent`. Алиас `agent` установщик grok делает ссылкой на свой бинарь,
  и прогон запускает grok с флагами cursor, падая на `--trust`.
- Без `--trust` CLI в неинтерактивном режиме встаёт на вопросе о доверии к каталогу.
- `--` перед промптом обязателен: бриф начинается с `---` и без него читается как ключ
  (17.09.2026 оба исследователя умерли сразу: неизвестный ключ, exit 1, пустая сессия).
- Промпт — только через файл: в брифах кавычки, обратные апострофы и переводы строк.
- `--mode ask` — настоящий режим чтения: на просьбу создать файл отказывается, файлы окружения
  вроде `backend/.env` не даёт прочитать, а на CLI 22.10.2026 отклоняет и любую команду
  оболочки («Shell отклонён в Ask mode»); на `--sandbox enabled -f` команды выполняются.
- Режим чтения файлов не пишет — их пишет вызывающий. В брифе сказать: вернуть полный текст в
  ответе, прокси или ведущий сохранит его, куда записала бы роль; иначе ход уйдёт на отказ.
- Бинарь лежит в `~/.local/bin` (ссылка в `~/.local/share/cursor-agent/versions/`); не
  находится — префикс `PATH="$HOME/.local/bin:$PATH"`.
- Модели — `cursor-agent --list-models`. Модели Claude через Cursor не гонять: смысл в другом
  слепом пятне. Модель вне тарифа Cursor молча подменяет другой — сверять `model` в ответе.
  Ориентиры: grok-xhigh — состязательное чтение, codex-xhigh — роли со скриптами, sol-xhigh —
  длинные диффы, flash — дешёвый обход дерева. На критическом пути (второе мнение, архитектор)
  — `grok-4.7-xhigh-fast`: короткое задание за 10,4 с против 16 с у обычного xhigh при том же
  ответе, а обычный xhigh на ревью думает 7–16 минут.
- Resume проверен: второй вызов вспомнил слово из первого, 354 новых входных токена и 17 536 из кэша.

## Механика A: одноразовая роль

Одноразовая роль на внешнем движке — без субагента: CLI запускает ведущий (или кто бы спавнил).

1. Промпт — в `<RUN DIR>/engine/<роль>/draft.prompt.md` до запуска; скрипт сам заведёт
   `001.prompt.md` и дальше. Содержимое — тот же промпт, что получил бы Claude-агент из справки
   фазы, плюс раздел «Выходной контракт» ниже. Файл промпта — единственное, что переживает
   зависание.
2. Пути, а не содержимое: движок работает в каталоге проекта и читает сам. Исключение —
   образцы вне репозитория: путь, если он доступен, иначе текст.
3. Запуск через `run-engine.sh` с `--report research-<role>.md`, `risk-<n>.md` или
   `verify-<role>.md`.
4. Ожидание `.done` — по абзацу «Ожидание»: ведущий фоном, участник в переднем плане; ledger
   пишет скрипт.
5. Прочитать `<out>.result.md`, затем `touch <out>.taken` — дальше это как ответ субагента.
6. Провал (`status=failed`, ошибка входа, нет CLI) — по `fallback`: `claude` — обычный
   Claude-агент и строка ⚙️ «не ответил, переключаю на Claude»; `fail` — стоп и доклад.

Ответ кончается строкой `ВОПРОС ОРКЕСТРАТОРУ: <вопрос>` — ответить из своего контекста и
продолжить ту же сессию через `resume` (скриптом, метка новая), а не начинать заново.

Режимы: `risk-tester` — запись, временные скрипты только в `<RUN DIR>/tmp/`; `ci-verifier` —
запись, потому что сборка пишет артефакты; `spec-verifier`, исследователи и `legacy-scanner` —
чтение (`spec-verifier` с пунктами-командами на cursor — запись, файлы не менять). Отчёт
риск-тестера без скрипта и его вывода — не вердикт: возобновить сессию и потребовать
доказательства. `ci-verifier` владелец держит на Claude: песочница чтения не пускает к файлу
окружения, тесты падают на импорте, а снять песочницу — показать ключи.

## Механика B: прокси

Участник на внешнем движке — это `supertick:proxy-teammate` с тем же `name`, что был бы у
Claude-участника. Для остальных состав не меняется: кодер шлёт REVIEW `unified-reviewer`, как
всегда. Как прокси работает изнутри — `agents/proxy-teammate.md`.

Шапка его промпта перед обычным промптом роли:

    ROLE: <id роли>
    ENGINE: <имя движка>; cmd: <разрешённый шаблон>; resume: <шаблон>; session: <как извлекается>
    LAUNCHER: <абсолютный путь {plugin}/scripts/run-engine.sh>
    SANDBOX: read-only   (coder: workspace-write + явный список разрешённых файлов)
    --- ROLE BRIEF ---
    <бриф роли по разделу «Бриф роли», только абсолютные пути>
    --- END ROLE BRIEF ---

Вместо блока — строка `ROLE BRIEF FILE: <абсолютный путь>`: бриф лежит файлом, прокси вставляет
его в `draft.prompt.md` как есть. Блок стоит ведущему 250+ строк контекста (22.10.2026).

Дальше — тот же блок контекста, что получил бы Claude-участник: общая шапка `PLUGIN:` /
`RUN DIR:` / `NAME:`, фича, DoD, образцы, подтверждённые риски, состав.

- Одна внешняя сессия на роль; каждое следующее сообщение — `resume`, поэтому второй круг
  ревью помнит первый.
- Каждый вызов, и resume тоже, — через скрипт и с ожиданием `.done` в переднем плане. Ответ на
  диске с момента выхода движка, поэтому умерший прокси теряет только пересылку.
- Движки говорят больше, чем знают. Прокси сверяет каждую находку с указанными строками и
  пересылает только подтверждённое.
- Сразу после запуска прокси шлёт ведущему `ENGINE RUNNING: <роль> on <engine>, started <HH:MM>`
  со строками `process:`, `output:`, `done marker:`.
- Прокси не может стартовать — `ENGINE_DOWN: <роль>. <причина>` ведущему, ведущий действует по
  `phase2-monitoring.md`, «Таблица событий».
- Прокси-кодер ведёт цикл ревью как обычный кодер: коммит только после вердикта без
  CRITICAL и MAJOR, вердикт ждёт в переднем плане (`team-wait.sh <RUN DIR> <имя> --task <id>
  --max 540`, повтор); значимая правка после ревью — новый круг.
- Внешнему кодеру — механические задачи. Правки его работы — через resume той же сессии, а не
  руками прокси.

## Бриф роли

Движок получает те же инструкции, что Claude-агент, — никогда не пересказ и не «короткую
версию».

- Бриф — тело `agents/<role>.md` без frontmatter (`name`, `description`, `model`, `tools`): у
  движка свои инструменты, а границу задаёт флаг песочницы.
- В начале брифа — пара фраз своими словами: прямой связи с командой у тебя нет; всё, что роль
  «отправляет», ты возвращаешь в ответе, оркестратор доставит.
- Текст меняется только в таких местах:
  - «отправь находки кодеру» → «верни находки в ответе, оркестратор передаст»;
  - «напиши техлиду, ведущему или участнику» → «закончи ответ строкой
    `ESCALATE TO <имя>: <сообщение>`»;
  - «ты только читаешь, никаких Write/Edit» → оставить и закрепить флагом песочницы чтения;
  - механика сообщений (`SendMessage`, `QUEUED:` / `RESEND:`, «закончи ход и жди») → «верни в
    ответе»;
  - статусы PLAN.md и механика состава → выбросить.
- Первый промпт прокси по порядку: строка «ты — <роль>, ниже роль целиком, следуй буквально»;
  бриф дословно; блок контекста; запрос — пути и что проверить, а не содержимое файлов;
  раздел «Выходной контракт».
- Одноразовая роль получает тот же промпт из справки фазы плюс выходной контракт.
- Только абсолютные пути.

## Второе мнение без файла агента

Файла `agents/second-reviewer.md` нет и не будет, и типа `supertick:second-reviewer` тоже нет.
Бриф собирается одинаково на любом движке из двух частей.

**Часть 1** — тело `agents/unified-reviewer.md` с заменами из `engines.md, «Бриф роли»`: та же
работа, глубина, приоритеты и шкала серьёзности и уверенности, чтобы находки двух рецензентов
можно было сравнить.

**Часть 2** — контракт «только находки». Он заменяет разделы вердикта и сообщений рецензента,
его раздел о втором мнении (там описана сторона первого рецензента) и каждое место, где
сказано, что рецензент единственный и последний, — в теле роли и в её `description`. В
контракте, своими словами:
- это второе мнение по задаче #<id>, вердикта нет; где контракт и файл роли расходятся,
  прав контракт;
- исходники только читать; единственный файл, который пишется, — файл находок;
- на выходе только находки с `file:line`; ничего похожего на одобрение или «править нечего»;
- ничто из отправленного не окончательно: `unified-reviewer` откроет каждую строку и решит сам;
  неуверенность называть прямо;
- сначала файл `reports/review-task{id}-second-r{round}.md`, потом рецензенту
  `SECOND OPINION: task #<id>` со строкой `Findings: <путь>` этого файла; адресат один —
  `unified-reviewer`, кодеру никогда;
- каталог `.claude/teams/*/reports/` не открывать вовсе: там уже лежит отзыв первого
  рецензента, а мнение, увидевшее чужую рамку, с ней соглашается. Читать только изменённые
  файлы и файл диффа в `engine/`; `git` для диффа не запускать, `sudo` никогда; уже открыл
  отчёт — сказать об этом;
- после одной задачи работа кончена.

Бриф несёт задачу, список изменённых файлов, диапазон диффа и путь файла диффа — и ничего, что
сделал первый рецензент. Песочница чтения этот запрет не обеспечивает, поэтому он записан в
самом контракте. Файл находок — часть контракта: фаза 3 считает такие файлы.

**Спавн.**
- Внешний движок — `supertick:proxy-teammate` с именем `second-reviewer-{id}`, механика B; в
  шапке `ROLE: second-reviewer`, собранный бриф — как `ROLE BRIEF`; файл находок прокси пишет
  через `--report`.
- `claude` — `supertick:unified-reviewer` с именем `second-reviewer-{id}`; блок
  `--- SECOND OPINION CONTRACT ---` первым, с явным списком отменяемых мест файла рецензента,
  затем общая шапка, `TASK: #<id>`, `FILES: <список>`, `DIFF RANGE: git diff <base> -- <файлы>`,
  `DIFF FILE: <RUN DIR>/engine/second-reviewer-<id>-1.diff`.
- Дифф пишет ведущий при спавне на обоих движках: у Claude-экземпляра, сделанного из
  `unified-reviewer`, нет Bash. Прокси, найдя файл пустым или не найдя его, пишет сам по
  диапазону из брифа.
- Потолок: на внешнем движке — `--timeout 1800` скрипта; на `claude` своего таймера нет,
  граница — ход субагента. Ход не кончается — ведущий отменяет экземпляр
  (`phase2-monitoring.md`, «Второе мнение»).

## Дифф в файле

Роль, которая читает изменение (`unified-reviewer`, `second-reviewer`, проверяющий), получает
дифф готовым файлом. Пишет его до запуска тот, кто запускает движок: ведущий для одноразовой
роли и второго мнения, прокси для участника. В промпт — строкой «Дифф задачи: <путь>»; сам
движок дифф не строит. Зачем: 23.09.2026 из-за `sudo -u admin git …` в брифе песочница
`--mode ask` не дала построить дифф, движок через 483 с сказал «находок нет», а повтор с
готовым диффом нашёл настоящие.

```
D=<RUN DIR>/engine/<имя>-<n>.diff
git diff <base> -- <файлы> > "$D"
for new in $(git ls-files -o --exclude-standard -- <файлы>); do
  git diff --no-index -- /dev/null "$new" >> "$D"    # код 1 у --no-index — это успех
done
```

- Пути: `engine/<role>-<n>.diff`; второе мнение — `engine/second-reviewer-{id}-1.diff`
  (пишет ведущий); приёмка — `engine/accept-task{id}.diff` через `git show <sha…> -- <файлы>`.
- Ничего, что пишет в индекс: никакого `git add -N` — индекс делят параллельные кодеры.
- `dubious ownership` → `git -c safe.directory="$PWD" …`.
- `sudo` — никогда, ни в своей команде, ни в промпте. Запрос со словом `sudo` — слово
  выбросить, команду оставить.
- Тот, кто пишет файл диффа, его не читает.

## Выходной контракт

Дописывается в конец каждого промпта внешнего движка. Формулировки свои, но каждый пункт
обязателен:
- ты модуль конвейера: ответ — данные для оркестратора, а не письмо человеку;
- файлы не менять; исключение — `coder` и `risk-tester`, и только явно разрешённые файлы;
  временные скрипты риск-тестера — только в `.claude/teams/<team>/tmp/`;
- строго формат роли, без вступлений и заключений;
- у каждого утверждения — ссылка `файл:строка`; без ссылки — пометить как предположение (прокси
  находку без ссылки отбрасывает);
- прежде чем сообщить о проблеме, проверить, нет ли уже защиты (middleware, обёртка,
  валидация); теоретическое без кода не сообщать;
- не хватает контекста — не выдумывать, последней строкой `ВОПРОС ОРКЕСТРАТОРУ: <вопрос>`;
- никакого `sudo` и прав выше песочницы; дифф уже лежит по указанному пути, `git` для него не
  запускать.

## Ledger

Каждый движок сам хранит свои разговоры, но не знает, какой разговор — какой роли, задачи и
круга. Ledger хранит только этот адрес.

Где лежат сами разговоры:
- codex — `~/.codex/sessions/YYYY/MM/DD/rollout-<время>-<id>.jsonl`;
- kimi — `~/.kimi-code/sessions/`, индекс `session_index.jsonl`;
- grok — `~/.grok/sessions/<cwd в url-кодировке>/<uuid>/`;
- cursor — `~/.cursor/chats/<md5 от cwd>/<uuid>/` (в `meta.json` есть `cwd`), читаемая запись —
  `~/.cursor/projects/<cwd, слэши заменены дефисами>/agent-transcripts/<uuid>/`.

`<RUN DIR>/ledger.jsonl` — один файл на прогон, один объект JSON на строку, только
дописывание `>>`, никогда не переписывается.

| event | кто пишет | поля |
|---|---|---|
| `launch` | скрипт, сразу | `ts`, `role`, `engine`, `task`, `label`, `pid` (для `kill -0`), `session`, `prompt`, `out` |
| `done` / `failed` | скрипт, по выходу | плюс `exit`, `wall_s` (измерен), `reason`, `result`, `report`; пустые поля опускаются |
| `relayed` | прокси, переслал ответ (и поставил `.taken`) | `ts`, `role`, `task` |
| `checks_done` | прокси кодера | `result`: `pass` или `fail: …` |
| `committed` | прокси кодера | `commit` |

Пример строк:

```
{"ts":"2026-10-21T14:02:11+02:00","event":"launch","role":"risk-tester-1","engine":"cursor","task":"3","label":"001","pid":41200,"prompt":"/abs/engine/risk-tester-1/001.prompt.md","out":"/abs/engine/risk-tester-1/001.out"}
{"ts":"2026-10-21T14:06:40+02:00","event":"done","role":"risk-tester-1","engine":"cursor","task":"3","label":"001","pid":41200,"exit":0,"wall_s":269,"session":"<uuid>","out":"/abs/…/001.out","result":"/abs/…/001.out.result.md","report":"/abs/reports/risk-1.md"}
{"ts":"2026-10-21T14:07:02+02:00","event":"relayed","role":"risk-tester-1","task":"3"}
```

- Вызывающий пишет только свои события, время — `date -Is` с поясом, не руками (22.09.2026
  вписанные руками разошлись с реальностью на 17 и 26 минут). Старое `engine_done` = `done`.
- Файлы `engine/<имя>/*` остаются механизмом (промпт, ответ, маркер); ledger их не заменяет.
- Ledger нет или он неполон — запасной путь:

  ```
  python3 {plugin}/scripts/engine-sessions.py <каталог проекта> [--since HH:MM] [--json]
  ```

  Скрипт обходит хранилища четырёх движков, оставляет сессии этого каталога и печатает id,
  время старта, путь записи и готовую команду resume. Ничего не нашёл —
  `No engine sessions found for <project>` и код 0.

## Правила

- Решения наружу не отдаются: отклонения, арбитраж ревью, дизайн, удаление наследия — за
  Claude-ролями. `DECISION:` внешнего техлида прокси сверяет с DECISIONS.md до записи.
- Роль с записью — только движку с песочницей записи (не kimi). Иначе предупредить и вернуть
  роль на Claude. Пишущий движок получает явный список файлов, после него — `git status`.
- Голос движка не решающий: не сверено — не проверено. Отчёт риск-тестера («API держит
