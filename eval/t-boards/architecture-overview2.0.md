## 0. Вердикт одним абзацем

Ядро Claude 2.0 (durable core, 12 инвариантов, fencing, context compiler, логическая компрессия,
canopy вместо fuse) — принять полностью: это сильнейшая часть, и она напрямую бьёт по измеренным
болям Т2/Т3 (см. §5). Споров два: (1) стек MVP — владелец уже решил «форк kaneo целиком» (Q-002),
значит TypeScript, а не Python-монолит из §16.1 документа Claude; контракты при этом языко-нейтральны
и переносятся 1:1; (2) документ Claude покрывает только control plane задач, а по приоритетам
самого владельца (Q-049) пятёрки получили «доски + MCP-экономия + память claude-mem» — память и
ещё пять планов в архитектуре отсутствуют. Закрываю их здесь блоками P1–P10.

## 1. Что принимается из Claude 2.0 без правок

- Инварианты I1–I12 и модель Task/Run/Edge/Event/Capsule (§3, §5 у Claude) — как есть.
- Разделение command / domain event / notification / query и запрет будить модель ради статуса (§7).
  Измеренное обоснование: в Т2 переписка и «ожидание» стоили 87 ходов · $84,5 и 164 хода · $99,9
  без единого действия (8% бюджета $1 298); в Т3 это уже 10 ходов · $3,8 — контракт Claude легализует
  именно это улучшение на уровне системы.
- Логическая компрессия с commitment register и coverage check (§10.2) — единственный допустимый
  способ сжатия, потому что единственный с проверкой «ничего не потеряли».
- Sticker → Board → Work Packet как адаптивная проекция по интенту и бюджету (§9) — прямое
  попадание в ответы Q-016/Q-017 (режимы выдачи, потолок 150–2500 токенов на задачу).
- Отказ от обещания «экономия 40–60%» без benchmark (§19) — совпадает с моим выводом линзы-3:
  честный потолок supertick был ~7,5%, а не 6–8% «на бумаге». Здесь закладываем измерение сразу (§5).

## 2. Главный спор: стек MVP — kaneo/TypeScript, не Python

**Факты.** Q-002: «Форк kaneo целиком; из crm переносим отдельные экраны». Kaneo — полностью
TypeScript-монорепо: Hono API + PostgreSQL через Drizzle ORM + React-фронтенд, pnpm + Turborepo,
Docker Compose, MIT; у него уже есть MCP-сервер и GitHub-интеграция
([kaneo.app](https://kaneo.app/), [openapps.pro](https://www.repocloud.io/details/Kaneo/)).
Наш монорепо — тоже Turborepo. В §16.1 Claude предложен Python + PostgreSQL — это противоречит
решению владельца и добавляет второй языковый стек туда, где UI уже написан.

**Решение (предложение):** контракты Claude 2.0 (Task/Run/Event/Capsule, state machine, API §12.4)
языко-нейтральны — реализуем их в форке kaneo как `apps/t-boards` (Q-001: своё приложение, своя БД,
свой деплой, продуктовая сегментация). Канонический core — отдельным модулем поверх той же
PostgreSQL; UI kaneo общается с ним через адаптер, а не напрямую в свои таблицы. Python остаётся
только для существующих tools (`tools/context_audit.py`, `tools/wake_anatomy.py`, `shadow/watchdog.py`).

**Риск:** внутренняя модель kaneo (карточки/метки/комментарии) покрывает ~60% канонической модели;
leases, fencing, capsules, события придётся дописывать — это и есть основной объём работ.
**Откат:** форк остаётся форком; core-модуль выносится без потери данных (JSON-экспорт canonical
сущностей — часть контракта). **d-решение:** не нужно — уже принято в Q-001/Q-002.

## 4. Недостающие планы (P1–P10)

Формат блока — по `pipeline/PROTOCOL.md`: механизм / экономия / измерение / риск / откат / d-решение.

### 4.0. Сущности продукта поверх canonical core (мост Q-009..013)

**Механизм:** Task расширяется extension-полями (механизм core+extensions у Claude, §12.2):
агент-исполнитель, ветка/PR/MR, затронутые файлы, токены и стоимость (факт), ссылка на
контекст-пакет (→ P2), mcp-рекомендации, типы связей «файл:строка» и «граф зависимостей по запросу»
(через graphify/Serena-адаптер, lazy). Отдельные сущности: `Comment` (треды, закрепление — Q-013),
`Attachment` (artifact со ссылкой), `Doc` (wiki-страница, markdown + изображения/ссылки),
`Base` (произвольные поля, как в Notion) — все как versioned capsules над тем же event log.
Статусы = как в Notion + переходы с проверками DoD (Q-010), матрица прав агента из Q-011 —
дефолтная политика, редактируемая per продукт/пользователь (note Q-011).
**Риск:** раздувание схемы. **Откат:** extensions отключаются флагом, core не затрагивается.
**d-решение:** не нужно (переиспользует принятые ответы).

### P1. Knowledge Plane: мост claude-mem (Q-023..027, приоритет 5/5)

**Механизм:** t-boards читает базу claude-mem через её воркер — один инстанс на Mac, один на сервере
(Q-024). Наблюдения автопривязываются к карточкам по ветке и ID задачи (Q-026); work_state сессий
проецируется на доску как read-only вид «рабочее состояние» (Q-023); наблюдения старше 92 дней
сжимаются в сводки (Q-027) — в терминах Claude это capsules kind=memory с provenance в claude-mem.
Отдавать владельцу и агентам: всё (Q-025) — включая будущим «агентам над агентами».
**Экономия:** устраняет повторное чтение истории между сессиями — базовый контекст первого вызова
сейчас 83–96K (pipeline/data, обе команды); память как внешний слой — главный рычаг его снижения.
**Измерение:** «базовый контекст первого вызова» из `context_audit.py`; доля запросов памяти,
решённых без обращения к модели. **Риск:** рассинхрон двух инстансов claude-mem (Mac/сервер) —
сверка digest раз в час, расхождение = алерт сторожа (P5). **Откат:** мост read-only, отключение
ничего не ломает. **d-решение:** не нужно.

### P2. Контекст-пакет и «bio/about» вместо повторного вливания (Q-013, Q-016)

**Механизм:** каждая карточка хранит скомпилированный контекст-пакет (V3 Work Packet у Claude)
с digest. Сессия стартует не с полной истории, а с bio ≤300 токенов: кто я (роль, ключ, веха),
текущая задача, 3–5 ссылок на capsules; догрузка — по ссылкам через MCP-режимы Q-016 (выбор полей,
«только изменения с T», «не изменилось» по хэшу, бюджет токенов параметром). Это прямая реализация
требования владельца «не повторять одно и то же между сессиями, а ссылаться на единый источник
с коротким bio/about».
**Экономия:** цель Q-050 — минус 55–75% токенов на «прочитать задачу и начать работу» против Notion MCP.
**Измерение:** benchmark на 10 реальных карточках (условие перехода №2, Q-044); счётчик
`prompt_tokens_total{view}` у Claude, §15.1. **Риск:** устаревший packet → обязательный digest
и пересборка при смене ревизии. **Откат:** fallback на полную выгрузку карточки.
**d-решение:** не нужно.

### P3. Free-tier роутер моделей (Q-030, Q-031, Q-022)

**Механизм:** классификатор тяжести запроса (детерминированный, по типу операции) направляет:
рутину (пересказ блокнота, кандидаты дедупа, классификация inbox, адверсариальная проверка правил
Q-038, «управление параметрами налету» Q-022) — на бесплатные модели OpenRouter (включая NVIDIA),
Groq free; среднее — GLM Coding Plan; сложное — Claude/Kimi. Лимиты бесплатных провайдеров
считываются из заголовков/ошибок и обходятся очередью с задержками и ротацией ключей (note Q-031),
а не параллельным оглушением. Код и PII к внешним моделям — только после d-решения (инвариант 5):
до него free-tier видит только тексты задач/правил без секретов и PII.
**Экономия:** выводит рутину из платного контекста; основание — Т3 PROPOSALS (даунгрейд модели
claude-mem, дедупликация) и моя линза-3 (до 8% бюджета — холостые/сервисные вызовы).
**Измерение:** доля вызовов по ярусам, $/PR (главная мера протокола), доля эскалаций «бесплатное
не справилось». **Риск:** нестабильное качество free-моделей → эскалация по порогу уверенности,
золотой набор регрессионных промптов. **Откат:** флаг роутера → всё на текущий провайдер.
**d-решение:** НУЖНО — «Разрешить отправку текстов задач и правил (без кода, секретов и PII)
на бесплатные модели OpenRouter/Groq для рутинных операций t-boards?»

### P4. Headroom как стандартный прокси + токеновый учёт на карточке (Q-013, Q-050)

**Механизм:** все вызовы worker→provider идут через headroom (уже работает для Kimi: prefix cache
hit 94.7%, экономия префикса $941 против $5 на сжатии); t-boards записывает фактические
токены/стоимость каждого run в карточку (поле Q-013) из provider-ответов и headroom-статистики.
**Экономия:** кэш префикса — самый дешёвый токен; наблюдаемость делает экономию доказуемой.
**Измерение:** `team-cost.sh`, `context_audit.py`, дашборд headroom; ворота — benchmark Q-050.
**Риск:** headroom как точка отказа → fail-open на прямой провайдер с алертом. **Откат:** переменная
окружения worker. **d-решение:** не нужно (уже в эксплуатации).

### P5. Жизненный цикл сессий и наследники (Q-007)

**Механизм:** ключ на сессию, выдача автоматически; идентичность агента = роль + ключ + имя +
id сессии + номер сессии по роли (веха). Долгие сессии запрещены политикой: watchdog
(`supertick-eval/shadow/watchdog.py`, уже проверен переигровками каскадов 26.10) детектирует
лимиты/застой/потерю auth → открывается наследник с handoff-capsule; приём считается состоявшимся,
только когда наследник воспроизвёл state без уточняющих вопросов (acceptance на передачу, не на код).
Стыкуется с lease/fencing Claude: старая сессия теряет fencing token автоматически.
**Экономия:** устранение незамеченных простоев (26.10 утренний каскад: 4ч15м молчания пяти ролей).
**Измерение:** время от сбоя до подхвата наследником; доля handoff без потери commitments (coverage check).
**Риск:** ложные срабатывания ротации → пороги watchdog калибруются по телеметрии, STALE по
определению шумный. **Откат:** ручное открытие наследника, как сейчас. **d-решение:** не нужно
для тени; нужно для авто-ротации — «Разрешить автоматическое открытие сессии-наследника по
сигналу сторожа?»

### P6. Диалоги в карточке с архивацией консенсуса (Q-020)

**Механизм:** комментарии-треды v1; совместная работа нескольких сессий над одной карточкой —
lease на правки + CAS по версии, общение — явно в треде карточки. При достижении консенсуса
тред «архивируется» в capsule kind=decision с ссылками на ветку диалога: остаётся и готовая основа
(«как продолжать / как не стоит делать»), и полная история. Это же решает канал Claude↔Kimi:
до запуска t-boards — временный файловый диалог `pipeline/dialog/`, после — треды карточек.
**Экономия:** конец переписке в контексте модели (Т2: 87 ходов · $84,5 — переговоры сессий).
**Измерение:** число model-wake на межсессионное сообщение → цель 0 (ответ из проекции).
**Риск:** гонки co-work → fencing уже в ядре. **Откат:** треды read-only. **d-решение:** не нужно.

### P7. Библиотека скиллов, правил и агентов (Q-032, Q-033)

**Механизм:** t-boards — источник истины для скиллов/правил/шаблонов; git — история через
экспорт (Q-032: «мой гит уже мусорная свалка»). На каждый артефакт — статистика: срабатывания,
токены, ошибки (Q-033, инфраструктура для «агентов, улучшающих агентов»). Переходный период —
dual-write t-boards↔git с метрикой рассинхрона; если вариант себя плохо проявит, откат к
«git — источник» по ноте владельца в Q-032.
**Экономия:** сессии перестают таскать в контекст все скиллы/правила — выдача по роли и задаче
(Q-019: +5 ближайших по вектору запроса вместо повторного влития всех).
**Измерение:** доля неиспользованных инъекций (хвост инъекций из мер протокола); рассинхрон
dual-write = 0. **Риск:** расхождение источника и экспорта. **Откат:** флаг «git — источник».
**d-решение:** не нужно (решение Q-032 принято, откат предусмотрен самим ответом).

### P8. Ревью-конвейер и контрольная среда (Q-034..039)

**Механизм:** на каждый PR (VPS, статические): lint/type/test → react-doctor (антипаттерны React)
→ abide (правила проекта; первые 7 — из Q-038) → checkov (только при правках infra). По кнопке:
ducktective (LLM-ревью диффа, на Mac — LLM и тяжёлое на Mac по Q-035), hetty (локально).
Infection Monkey не берём (Q-039). Каждая находка → карточка «Ошибки» (Q-037); прогрессия ошибок
балансирует багфикс/фичи с порогом от главного админа per продукт. Новые правила — локальные per
продукт, с адверсариальной проверкой GLM/openrouter и тумблером у пользователя (note Q-038).
**Измерение:** находки до/после на одинаковом типе PR; доля ложных срабатываний правил.
**Риск:** лицензии/зрелость сторонних инструментов (react-doctor — без разрешения, решение Q-036).
**Откат:** каждый инструмент отключается отдельно. **d-решение:** не нужно (набор утверждён Q-034..039).

### P9. Миграция Notion, блокнот и очередь владельца (Q-040..044, Q-052, Q-053, Q-028..029)

**Механизм:** фаза 1 — Notion главный, t-boards зеркало read-only (Q-041): импорт открытых и
закрытых карточек сразу после готовности БД, остальное догружается по ходу (note Q-040).
Переход — только при всех пяти условиях Q-044 (сверка количеств; −50%+ стоимости чтения задачи на
10 реальных карточках; неделя зеркала без расхождений; бэкап восстанавливается на чистой машине;
правила и скиллы переписаны) в окне 06–20.11.2026 (Q-042). Очередь владельца (ops-console /queue +
Telegram-бот) переносится последней, после стабилизации (Q-043). Блокнот (Q-028..031): чат с
источниками как NotebookLM поверх capsules + docs/ + PR + карточек; эмбеддинги локально, пересказ —
free-tier роутер (P3). Анти-цель Q-053 («не кладбище задач»): регламент полей обязателен,
метрика рассинхрона с другими сервисами — на сводной панели (Q-045).
**Измерение:** расхождения зеркала в сутки = 0 за 7 дней; чек-лист Q-044. **Риск:** двойная запись
в переходный период — главный источник рассинхрона; минимизируем окно, сверка ежедневно.
**Откат:** зеркало выключается, Notion остаётся главным. **d-решение:** нужно на сам переход —
по факту выполнения 5 условий (владелец подтверждает, Q-044).

### P10. Деплой, сеть и сохранность (Q-004..008, Q-051)

**Механизм:** VPS Contabo рядом с продом, отдельный контейнер (Q-004); доступ только через
WireGuard с Mac, предусмотреть добавление устройств; admin/admin допустим лишь внутри закрытой
сети, далее собственная auth (Q-005); адрес d4dev.admin.hrhelper.space — владелец готовит сам,
напомнить за 3 шага (Q-006). Туннель для локальных сессий Mac↔VPS. RPO 2ч (Q-051): снапшот БД
каждые 2ч + еженедельный restore-drill на чистой машине (он же условие перехода №4). Vault —
в перспективе на все сервисы (note Q-005).
**Конфликт, который надо замерить, а не угадывать:** лимит контейнера 320–1024MB (Q-008) против
рекомендованных kaneo 2GB RAM. Смягчение: «БД полностью на серверах» (note Q-001) — если
PostgreSQL живёт на существующем сервере, app-контейнер может уложиться в 1024MB; нижняя вилка
320MB реалистична только для MCP-gateway без UI. План: деплой → замер RSS под нагрузкой зеркала →
корректировка лимита фактом.
**Риск:** единая точка отказа VPS → RPO 2ч покрывает, RTO не регламентирован (принять для v1).
**Откат:** контейнер выключается, данные на серверных БД. **d-решение:** нужно на открытие адреса
и DNS (владелец делает сам, Q-006) и на WireGuard-доступ с новых устройств.

## 6. Самоопровержение (адверсариальная проверка моих же блоков)

1. **TOON как default (Q-018).** Владелец предпочтит TOON всегда, если доказана обратимость.
   Claude прав: сначала round-trip `decode(encode(x))==x` на Unicode/вложенности/null и benchmark
   реальными токенизаторами, потом default. До доказательства — JSON default, TOON по параметру.
2. **Free-tier роутер.** Качество free-моделей нестабильно, лимиты агрессивны; без golden-набора
   и эскалации это переносит экономию в потерю качества. Поэтому P3 стартует только на пересказах
   и классификациях, где ошибка обратима.
3. **Форк kaneo.** Риск «переизобретения Linear внутри форка»: канонический core надо держать
   тонким слоем, не переписывая kaneo UI под каждый инвариант; граница — адаптер §2.
4. **Dual-write Notion↔t-boards** — исторически главный источник рассинхронов (Q-052: Notion уже
   «кладбище багов и рассинхрон»). Ответ: зеркало строго read-only, запись только в Notion до
   перехода, сверка ежедневная автоматическая.
5. **Лимит 320MB.** Нереален для полного стека; честный ответ — замер после деплоя (P10), а не
   обещание «влезет».
6. **Статистика скиллов (P7)** бесполезна без идентификации вызова скилла в логах провайдеров —
   сначала инструментируем вызовы, потом обещаем аналитику.
7. **Моя же линза-3 против supertick** учит: свежий контекст ценнее экономии на тиках. Поэтому
   ни один блок выше не вводит модельный polling: вся асинхронность — события и сон-петли вне модели.
