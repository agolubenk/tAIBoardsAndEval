## Хард-стопы (кратко; полный текст ниже + `.claude/rules/17-notion-board.md`)

- **`Half-baked idea = true` → не брать в работу** без явного ОК владельца в текущем диалоге.
- **«Ошибки» приоритетнее «Задач»** — бэклог берётся в работу, когда в «Ошибках» нет ничего приоритетнее.
- **Закрытие — два шага, оба обязательны:** запись в `docs/plans/done/<модуль>.md` (оглавление и формат — `docs/plans/DONE.md`) И статус карточки.
- **Удаления страниц нет** — дубликаты помечаются `[Дубликат]` в заголовке и закрываются статусом.
- **Постановка — в карточке.** `docs/plans/BACKLOG.md`/`docs/plans/archive/FIX.md` не читать для скоупа открытого пункта — они заморожены.
- **Финальный статус — только после апрува пользователя.** Агент сам доводит карточку максимум до
  `на ревью`; `выполненные`/`завершённые` (Задачи) и `закрыто` (Ошибки) — только по явному
  подтверждению в текущем диалоге. См. «Пайплайн завершения» ниже.

## Маппинг полей

**Задачи**: `Name` = заголовок · `Backlog ID` = ID из миграции (если есть) · `Priority` = P0–P3 (P2-LT нормализуется в P2 — в Notion такого статуса нет) · `Source` = `Notion` (для новых, заведённых после 2026-08-12) / `BACKLOG.md` (для мигрированных) · `Report` = ссылка на файл/раздел кода, если применимо · `Status` = живой статус карточки.

**Ошибки**: `Name` = заголовок находки · `Backlog ID` = связанный BACKLOG ID (`INT-JB-1.x`, `WIKI-8.x`...) или свободное описание, если пункт не заведён в бэклоге · `Severity` = critical/high/medium/low · `Report` = ссылка на файл/раздел кода, если применимо · `Status` = открыто (по умолчанию), в работе — если код-фикс сделан, но не подтверждён вживую (пример: `withSessionOpSlot`-регрессия) · `Half-baked idea` = `__YES__` для нерасписанных идей/спайков (пример: agent-reach).

**Обе базы — «Очередь»** (текст, с 2026-10-20) = `<id строки плана> · <заголовок строки>`: карточка уже в плане-очереди
(«Ход работ» ops-консоли, https://ops.admin.hrhelper.space/queue). Фильтр «Очередь не пусто» — всё, что в плане;
пусто у не-half-baked карточки — новая, ещё не разложена. Пишет агент при сверке с Notion: строка плана хранит
список своих карточек (`cards`), а поле в Notion — обратная ссылка. Перекладка карточки в другую строку меняет оба
места. Поле не входит в отпечаток карточки у консилиума — запись его не запускает перепроработку.

## Пайплайн завершения — статусы и апрув пользователя

**Задачи** (6 статусов): `задача от пользователя` → `прожаренные явные задачи` → `в работе` →
`на ревью` → `выполненные` → `завершённые`.

**Ошибки** (4 статуса, приведены к той же форме 2026-08-11): `открыто` → `в работе` →
`на ревью` → `закрыто`.

Единое правило для обеих баз: агент двигает карточку сам вплоть до `в работе` → `на ревью`
(реализация закончена + отчёт по Definition of Done — изменённые файлы, прогнанный узкий
`turbo run lint|typecheck|test:run --filter=<pkg>`, риски). `на ревью` — потолок того, что агент
выставляет без спроса. Переход в финальный статус (`выполненные`/`завершённые` для Задач,
`закрыто` для Ошибки) требует явного подтверждения пользователя в этом же диалоге в ответ на
отчёт — без этого карточка остаётся в `на ревью`, даже если код уже смёржен.

Для Задач `выполненные` vs `завершённые`: `выполненные` — пользователь подтвердил, но шаг 1
закрытия (запись в `done/<модуль>.md`) ещё не сделан в этом ходе; `завершённые` — оба шага закрытия
выполнены. Обычно это один ход сразу после апрува; `выполненные` как отдельная остановка нужна,
если git-запись сознательно откладывается.

Исключение без прохождения через `на ревью`/апрув — точечные механические правки без
пользовательского видимого эффекта и с однозначной верификацией (typo, форматирование, lint-fix
при зелёном CI), и только по прямому запросу «закрой это» в этом же ходе, не по умолчанию.

## Порядок работы

1. **Сначала Ошибки, затем Задачи.** Бэклог берётся в работу только когда открытых пунктов в Ошибки с приоритетом выше текущего нет — баги/уязвимости обгоняют плановую работу.
2. **Постановка и статус — на карточке.** Полное описание, уточнения к постановке, решения «отправить на доработку» — прямо на карточке Notion (комментарии через `notion-create-comment`/`notion-get-comments`), не в чате и не в git-файле.
3. **Закрытие — Notion не заменяет git-историю.** Когда пункт реально закрыт (код смёржен, верифицирован) — компактная запись в `docs/plans/done/<модуль>.md` (дата · что сделано · ссылка на коммит/раздел · ссылка на Notion-карточку) плюс смена статуса карточки на «закрыто»/«завершённые». Ни один из двух шагов не заменяет другой — Notion остаётся источником контента и треда обсуждения для открытого, git (`DONE.md`) — источником истории закрытого.
4. **Новая находка** — сразу карточкой в Notion (не в git-файл) с `Report`-ссылкой на файл/секцию/строку, если применимо; git больше не первая точка фиксации для открытых пунктов.
5. **Поиск «делали ли уже это раньше»** — `docs/plans/done/` (`rag_query.py --type done_entry`, `grep -rn`) + `git log`/`git show`, не `BACKLOG.md`/`FIX.md` (заморожены, могут быть неполными/устаревшими относительно Notion).
