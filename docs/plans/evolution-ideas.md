## 2. Хаб переиспользуемых документов (Notebook Hub)

Блокнот кейсов (R-050) остаётся местом разбора: источники, чат, поиск материалов, проработка данных. Хаб — отдельный
слой для **переиспользуемого**: скиллы, агенты, промпты, правила, чанки знаний, шаблоны, геномы ролей, описания.

| # | Идея | Как |
|---|---|---|
| 2.1 | **Артефакт = неизменяемые версии** | semver + хэш содержимого; канал `черновик → канарейка → стабильная → устаревшая`; область (глобально/продукт/лес); происхождение (источник, коммит, автор — агент или человек); зависимости (скилл → правила → чанки); совместимость харнессов (Claude Code, Continue, `.agents`, Windsurf) |
| 2.2 | **Один факт — одно место** | факт/правило — один чанк; скиллы, CLAUDE.md, промпты ссылаются на него; хаб ловит дубли и висячие ссылки — прямой удар по главной потере R4 |
| 2.3 | **Подбор под задачу**: `library_resolve(card, budget)` | минимальный набор артефактов по триггерам и измеренной пользе вместо загрузки всех описаний скиллов (сейчас — обрезка `skillListingMaxDescChars` в геноме) |

| 2.6 | **Мост блокнот → хаб** | «продвинуть» ответ/решение из чата блокнота в черновик правила или скилла со ссылками на карточки-доказательства |
| 2.7 | **Семена → уроки** | вырубленный сектор оставляет семена; дистилляция семян даёт урок в хабе (что сработало, что нет, ссылки на брёвна) |

## 3. Эволюционирующий пайплайн

Пайплайн должен улучшать сам себя на трёх уровнях: промпты, сессии, качество. Общий цикл — **вариация → замер →
отбор → закрепление**, всё под контролем владельца и с откатом.

**Сделано 01.11 (задача владельца «система эволюционирует сама, без повторов и без потери качества»)** —
[`eval/evolve/`](../../eval/evolve/README.md), без хаба и сервисов, в git:

| Идея | Что работает | Чего нет |
|---|---|---|
| 2.1 версии | версия каждого скилла, правила, агента, команды, карточки роли, промпта, хука и `roles.json` — из git (число коммитов, последний `rev`, `dirty`), без файла версий и хука: нечему конфликтовать; вердикты A/B — `verdicts.jsonl` по id коммитов | каналов «черновик → канарейка → стабильная», области видимости, происхождения |

### 3.1 Промпты, геномы, капсулы

- **Всё, что запускает сессию, — версия в хабе**: пусковые промпты ролей (`eval/prompts/launch-*`), `SUCCESSOR-PROMPT*`,
  геномы, шаблоны капсул. У каждой запуска есть ссылка на версии, из которых он собран.
- **Золотой набор задач** (replay): 10–20 реальных закрытых карточек с известным хорошим исходом и стоимостью.
  Новая версия промпта/генома прогоняется на нём (или его части) до канарейки — регресс видно до прода.
- **Фитнес-функция** = $/PR, первый вызов, средний контекст, доля PR без доработок, найденные ревью дефекты. Версия
  проходит в стабильную, только если фитнес лучше и ни одна метрика качества не хуже (принцип «не оставлять на
  прежнем уровне»).
- **Источник вариаций**: наблюдения `task-observer` (`.claude/skill-observations/`), ретро после волны, находки
  ревью, отчёты `session-report` — превращаются в черновики изменений артефактов, а не в заметки в чате.
- **Ретро волны — автоматом**: после каждой волны сессий — отчёт eval (wake anatomy, context audit, стоимость по
  ролям) → карточка «что изменить в промптах/геномах» → черновики в хабе.

### 3.2 Создание и запуск сессий

- **Preflight лаунчера** (`spawn_session.sh`): до `exec claude` проверить и записать — геном и его версия,
  включена ли запись транскрипта, нет ли унаследованных маркеров дочерней сессии (см. §6), лимит окна 5 ч/недели,
  свободная аренда роли. Провал — понятная ошибка, а не тихая деградация.
- **Сессия регистрируется в лесу при старте**: роль, геном@версия, ветка, worktree, метка `t3-<роль>` — work_state
  пишется с первой минуты, наследник подхватывает аренды и журнал (уже есть механика, нужен автоматический старт).
- **Холодный старт только из капсулы**: наследник получает `contextPack` + ссылки, не историю; размер капсулы —
  метрика, растущая капсула — сигнал на дистилляцию.
- **Ротация по сигналу, а не по ощущению**: порог контекста (хук `context-threshold`), лимиты, ночной режим Нерва;
  Нерв сам предлагает наследника (пункт владельцу), а не ждёт, пока роль заметит.
- **Эфемерные роли только чтения** на дешёвых моделях/внешних движках — с жёстким egress (как рой П9).

### 3.3 Качество

- **Метрики качества рядом с метриками стоимости**: escape rate (дефект найден после мёржа), переоткрытые карточки,
  доля PR с доработкой, flaky-тесты, время от «на ревью» до «да».
- **Каждый инцидент — закон с тестом**: правило в `.claude/rules/` появляется вместе с проверкой (хук, тест, lint),
  иначе оно не закреплено.
- **Калибровка ревьюеров**: консилиум уже учится на вердиктах (`learning.py`) — распространить на линзы ревью PR:
  какая линза находит реальные дефекты, какая шумит; состав линз — по данным.
- **Бюджет ошибок**: рост «Ошибок» балансирует фичи (R-073) — сделать это правилом планировщика, а не ручным решением.

## 4. Loop-сервисы и системы

| Принцип | Сейчас | Развитие |
|---|---|---|
| Цикл без модели — первичен | Нерв (launchd, stdlib) будит сессию только на событие | вынести в Нерв всё, что сейчас поллят сессии: CI, очередь, лимиты, ревью |
| Событие, а не опрос | подписки на PR, тапы Нерва | у каждого loop — источник события; «проверка статуса не вызывает модель» (контракт 2) |
| У цикла есть стоп | — | у каждого loop: максимум тиков, бюджет токенов, условие выхода, «3 пустых проверки — остановись» |
| Сторож сторожа | heartbeat Нерва | внешняя проверка пульса (ops-консоль: молчание агента — алерт) |
| Идемпотентность | `ifVersion` в очереди, `fencingToken` в лесу | ключ идемпотентности у каждого действия цикла; повтор не дублирует |
| Дедупликация | — | одно событие — одно пробуждение одной роли, даже если пришло из GitHub, очереди и Нерва |
| Наблюдаемость | журнал Нерва append-only | журнал тиков с причиной пробуждения и стоимостью — вход для wake anatomy |

Инструменты Claude Code для циклов, которые стоит свести в один регламент: `/loop` и `ScheduleWakeup` (самотемп),
cron-задачи и `send_later` (расписание), `Monitor` (ожидание условия), подписки на PR (события), фоновые Bash/агенты
(уведомление по завершении). Вопрос — в §5.

## 5. Вопросы: лучшие практики Claude Code и методологии

- **Безопасность хаба**: egress-фильтр роя (секреты, PII, маскирование) — на всё, что хаб и блокнот отдают внешним
  моделям.

## 8. Программа непрерывности: работа переживает замену сессии, модели и harness

> Идеи владельца 01.11. Каждое утверждение о коде сверено с кодом 01.11. Колонка «Есть» — что уже работает, со
> ссылкой; новое не дублирует §1–§7, а ссылается на них.

**Цель продукта.** tAIBE — система длительной работы людей и ИИ-исполнителей. Состояние, обязательства, источники и
результаты живут вне диалога, а модель получает только достаточный рабочий контекст. Обещание «без потери
контекста» делится на три уровня:

| Уровень | Обещаем | Не обещаем |
|---|---|---|
| Канон | Принятые задачи, решения и обязательства не пропадают при конце сессии или очистке кэша | — |
| Рабочий пакет | Всё обязательное есть в пакете либо разрешается harness до действия; не влезает — явный `budget_conflict` | Молчаливую обрезку |
| Поведение модели | Качество проверяется тестами и наблюдением | Что текст в окне будет применён правильно |

Пять возможностей:
1. Любую сессию можно заменить без потери незавершённых обязательств.
2. Источники подбираются автоматически, а не исследованием всей очереди.
3. Координация, ожидание и восстановление идут без вызовов модели.
4. Скиллы и правила эволюционируют в фоне, не меняя условий идущих попыток.
5. На вопрос «почему система так сделала» отвечают правила и данные, а не объяснение, сгенерированное постфактум.

Архитектура — четыре контура, а не «суперагент»:
- **каноническое состояние** — доски: tasks, runs, decisions, commitments, leases, events, refs;
- **наблюдение и маршрутизация** — Нерв;
- **проекции и индексы** — DAMS, Serena;
- **компилятор контекста и harness-адаптер** — manifest, бюджет, provenance, tools, checkpoints, loop policy.

Отдельно идёт контур эволюции: наблюдение → кандидат → дешёвые проверки → поведенческий eval → judge → canary →
pin/rollback. Ни один компонент, кроме досок, не владеет статусом задачи.

### 8.4 Метрики и обязательные сценарии

Метрики:
- **непрерывность:** доля успешных resume, время восстановления, потерянные обязательства;
- **контекст:** размер пакета, покрытие обязательных refs, повторно отправленное;
- **поиск:** Recall@K на размеченном наборе, свежесть, p50/p95, доля ошибок;
- **доставка:** задержка, дубли, необработанные события, лишние пробуждения;
- **циклы:** вызовы до прогресса, пустые итерации, ложные остановки;
- **стоимость:** наблюдаемая и оценочная, кэш, квоты;
- **эволюция:** время проверки, переиспользованное, регрессии, откаты;
- **человек:** повторные вопросы, ручные восстановления, вмешательства.

«Агент открыл первый результат» — телеметрия, а не доказательство качества поиска. Цели README (первый вызов
≤ 55K, средний контекст ≤ 120K) — ориентиры, не единственный критерий: меньший контекст при большем числе
ошибочных итераций дороже.

Шесть fault-сценариев, каждый — тест:
1. Сессия прервана после команды, до checkpoint.
2. Два исполнителя одновременно продолжают одну задачу.
3. Решение владельца меняется, пока сессия работает со старой ревизией.
4. Индекс устарел или повреждён.
5. Модель недоступна посреди цикла.
6. Новая версия скилла дешевле, но нарушает один критический критерий.

Первый вертикальный эксперимент — одна типовая backend-задача в четырёх прогонах:
- непрерывно;
- с принудительным handoff;
- со сменой модели;
- после временной недоступности поиска.

Сравниваются результат, время до полезного действия, повторная работа, вмешательства владельца и токены.

### 8.5 Не первым

- Новый агент-координатор поверх ролей.
- Вторая векторная память до проверки DAMS. Эмбеддинги — отдельный эксперимент: вектор нового запроса всё равно
  нужен, без модели остаётся только лексический поиск.
- Второй сервис навигации по коду без сравнения с Serena.
- Kafka или отдельная шина без подтверждённой нагрузки.
- Склейка решений по похожести.
- Глобальная пересборка контекста на каждом шаге.
- Переписывание отправленной истории ради токенов.
- Единый порог релевантности.
- Эскалация каждого повтора владельцу.
- Продвижение скилла по двум удачным кейсам.
- Хеши вместо прав и provenance.

### 8.7 Испытательный контур: изменения проверяются в worktree, в работу идёт проверенное

Принцип владельца (01.11). Эволюция слоя и конкретные решения в продукте — код, логика, правила, скиллы, промпты,
геномы — разрабатываются и проверяются в отдельном worktree (`worktrees/<track>/<topic>`, правило
`.claude/rules/07-worktrees.md`). Рабочие экземпляры и живые сессии получают только то, что прошло проверки.

```text
кандидат в worktree (spike / feature / fix)
  → дешёвые гейты в этом worktree (make check, infra/checks, гейты досок, L1-бюджет)
  → поведенческие проверки на версии из worktree (ab.py --b <ветка>, replay событий, поисковые кейсы)
  → PR → CI → мёрж
  → живые сессии берут новую ревизию на границе единицы работы (пин manifest, §8.8 N19), не посреди шага
```

- **Изоляция.** Свои зависимости (`make wt-add` ставит), свой индекс, свой стенд. Живой инстанс, его доски и очередь
  не трогаются, пока кандидат не принят.
- **Сравнение.** `eval/evolve/ab.py --a board-agents --b <ветка кандидата>` сравнивает версии без копирования
  файлов. Вердикт пишется только по коммитам, рабочая копия не считается доказательством.
- **Откат.** Неудачный кандидат — удалённый worktree и ветка. Живой контур при этом не менялся.
- **Включение.** Новые попытки берут принятую ревизию. Идущая попытка доживает на той, с которой стартовала.

### 8.8 Runtime сессий: дополнение (идеи 01.11, вторая серия)

Свежая сверка с кодом 01.11, только чтение, без прогона тестов:

| Место | Что в коде | Риск |
|---|---|---|
| `eval/pipeline/capsule.py` `pack()` | При переполнении 2000 символов молча выбрасывает решения целиком, затем приёмку, затем ссылки. Отказ — только если не влезают цель, следующий шаг и «не делать» | Короткий пакет теряет идентификаторы решений, и наследник об этом не знает |
| `eval/nerve/nerve.py` `cmd_tap()` | Событие печатается в stdout, затем сохраняется курсор `state/tap-<role>.json` | Печать ≠ приём харнессом ≠ шаг агента: подтверждений доставки и обработки нет |
| Журнал вызовов MCP досок | Читается только SQL; вызов, отсечённый схемой, в него не попадает | Сессия заново исследует доску, чтобы узнать, кто уже звал инструмент и сколько это стоило |
| `eval/evolve/catalog.py` L1 | Не учитывает схемы MCP | Первый вызов Т3 — 83–84K при цели ≤ 55K (`eval/pipeline/PIPELINE.md`), а бюджет роли этого слоя не видит |

Новые направления. Где идея уточняет N1–N13, это сказано в первой колонке.

| # | Идея | Приёмка |
|---|---|---|
| N14 | **Четыре вида данных вместо переписки.** События — короткий конверт (`event_id`, `type`, `task_id`, `producer`, `consumer`, `correlation_id`, `causation_id`, `state_rev`, `artifact_refs`, `idempotency_key`). Состояние — версионированная запись `state_rev`. Артефакты — ссылка и hash. Решения — реестр, не чат. Строка пробуждения — указатель: id, тип, карточка, etag, одна строка; полный пакет тянется, только если `ifNoneMatch`/`since` сказали «изменилось» (неизменённая карточка — 17 токенов, полный пакет — около 1686, `boards/docs/impl/impl-r031-context.md`). Промежуточные CI-события схлопываются до пробуждения, а не после: в аудите вся цепочка, в пробуждение — последнее состояние. Уточняет N3 | Пробуждение без смены состояния стоит десятки токенов; доля пробуждений без коммита и без смены `work_state` падает |
| N15 | **Пакет не теряет идентификаторы.** Полный handoff хранится отдельно от лимита карточки (2000 символов) и бюджета капсулы. В коротком пакете всегда есть `task_id`, `state_rev`, `manifest_ref` и обязательные запреты. Ужимается текст, не id; обязательное поле не пропадает молча — ошибка сборки или явная пометка «неполный». У факта есть происхождение (файл, коммит, решение владельца, прогон): догадка агента — не факт. Отклонённые подходы лежат в индексе по задаче и области кода и достаются при совпадении, а не грузятся в каждую сессию. Уточняет N2 | Тест: переполненный пакет либо сохраняет все id, либо падает |
| N16 | **Поиск запускает код, а не модель.** Запись индекса — `id, kind, project_id, task_id, path, symbol, source_rev, content_hash, status, supersedes, text`. Индексируются решения и их область, карточки и связи, капсулы, разделы документов, пути и символы, коды ошибок тестов, ссылки на PR и коммиты, закрытые работы и причины отказа от подхода. Запрос собирает код: задача + изменённые пути + символы + коды ошибок + зависимости. Перестройка по `git diff --name-only`, вне `catalog.py --check`. На досках — полнотекст базы и выдержка заголовка, чтобы MCP не читал карточку ради 80 символов (`search` уже сжат 604 → 221 токен). Отдаётся id, одна строка и путь; индекс не кладётся в постоянный контекст. Индекс старше ревизии — ответ `stale` и откат на `git grep`, не на модель. На старте наследника — таймаут около 200 мс, иначе пропуск. Качество — пары «запрос → обязательный id» без судьи; промах `ask_once` — регрессионный кейс индекса, не повод для эмбеддингов. Журнал вызовов MCP читается как карточка: поля, бюджет, курсор. Уточняет N4–N5 | Набор пар «запрос → id» проходит без модели; поиск укладывается в 200 мс или честно пропускается |
| N17 | **Харнесс — адаптер, а не унификация.** Внутренний цикл модели остаётся у Claude Code, Continue, Windsurf. Внешний контракт: `start / resume / deliver_event / checkpoint / cancel / collect_usage` плюс возможности (нативное продолжение, хуки, структурный вывод, отчёт о расходе, кэш префикса). Адаптер сообщает, какой `state_rev` получил, какой пакет загрузил и ревизию правил. Нет нативного продолжения — новая сессия из состояния задачи. Порядок пакета ради кэша префикса: стабильные инструкции и инструменты → закреплённые правила роли → контекст задачи → новые события. Без меток времени в стабильной части, без перестановки инструментов, без подмены генома живой сессии на каждом коммите. Короткий список инструментов на старте, схема — в момент вызова. В L1-бюджет добавить схемы MCP (сейчас их нет в `catalog.py`). Уточняет N13 | Первый вызов роли ≤ 55K по замеру `context_audit.py`; смена ревизии слоя не сбрасывает кэш идущей сессии |
| N18 | **Луп — автомат.** Состояния единицы работы: `READY → RUNNING → WAITING_TOOL / WAITING_REVIEW / WAITING_OWNER / BLOCKED / DONE`. Переходы по известным условиям выполняет код: CI идёт — модель не будится; ответа владельца нет — очередь моделью не перечитывается; lease истёк — старый исполнитель не пишет; WIP занят — новая сессия не поднимается. Отпечаток зацикливания: `task_id + step_type + input_hashes + state_rev + error_signature` → стоп, диагностический пакет, разрешённый fallback или эскалация. Ожидание внешнего процесса и бесполезный повтор — разные политики и таймауты. Один арендованный объект — одна живая сессия: второй харнесс не стартует, пока жив fencing-токен. Уточняет N7 | Повтор с теми же входами и той же ошибкой без нового артефакта останавливается сам |
| N19 | **Пин ревизий на единицу работы.** Manifest запуска: `genome_rev, rules_rev, context_builder_rev, retrieval_rev, harness_adapter_rev`. Посреди шага инструкции не меняются без явной миграции. Порядок проверок кандидата: схемы и совместимость → обязательные id, решения и запреты на месте → бюджет L1 → поисковые кейсы без модели → replay записанных событий без модели → только потом слепое A/B → ограниченное внедрение и откат. Жёсткие условия, без которых дешевизна не считается: обязательное сохранено, нет повторного внешнего действия, права и fencing соблюдены, качество не хуже, задержка в пределе. Уточняет N9 | Время от изменения слоя до безопасного внедрения — без модели на шагах 1–5; судья не тратится на вариант, потерявший ссылку |
| N20 | **Реальные токены, а не оценка.** Учёт фактических input, output, cache read и cache write из `usage`, а не «символы на токен» (`eval/evolve/tokens.py` — оценка для сравнения версий). Иначе «текст короче» врёт про деньги. Уточняет N10 | Стоимость завершённой задачи с учётом повторов — по фактическим `usage` |

Образцы из жизни, по которым проверять проект:
- **передача смены** — как в диспетчерской: ситуация, фон, следующий шаг, «не делать», ссылки;
- **ревью** — как в очереди мёржа: три линзы читают один дигест диффа, посчитанный кодом, а не весь PR каждая;
- **WIP** — как на конвейере: WIP занят — Нерв молчит;
- **лимит** — как у пейджера: волна лимита живёт в ops-консоли, в сессию приходит одна строка «лимит снят, продолжай с
  `work_state`».

Продуктовая проверка — не coding-бенчмарк: решение человека в найме или в очереди владельца не переспрашивается.

Подтверждено в «не первым» (§8.5): поиск без векторной базы и без LLM-reranker на горячем пути. Рой для выжимки не
годится — 34 из 34 ссылок битые (`eval/pipeline/PIPELINE.md`). Cognee и codebase-memory как память чтения не
ставятся: они кладут модель в чтение и тормозят отбор версий.

### 8.9 Единый порядок (последовательность; волны 8.3 остаются картой зависимостей)

1. Капсула по задаче, линии и worktree; канон отдельно от короткого пакета; id не выкидываются молча (N2, N15).
2. Курсор на подписку, раздельные подтверждения доставки и обработки, запись только с живым fencing (N3, N14).
3. Preflight лаунчера: геном, транскрипт пишется, нет маркера дочерней сессии, лимит окна, свободная аренда (§3.2, §6).
4. Общий индекс и сборщик пакета с обязательными полями и бюджетом — развитие `ask_once` и `queue_focus`, не второй
   поиск (N4, N5, N16).
5. Учёт фактических input, output и cache tokens (N20, N10).
6. Минимальный хаб: версии, каналы, подбор артефактов под карточку (§2.1–2.4) — после того, как пакет не теряет id.
7. Золотой набор карточек и фитнес (§3.1).
8. Канарейка геномов с пином manifest на задачу (N19).
9. Контракт адаптера харнесса и автомат лупа с детектором отсутствия прогресса (N17, N18).
10. Replay событий и ограниченное внедрение изменений слоя через испытательный контур §8.7.
11. Ответы на вопросы §5 замером; принятый ответ становится правилом или скиллом, а не ещё одним документом.

Кандидаты всех шагов делаются и проверяются в worktree (§8.7).

Дополнительные метрики к §8.4:
- время от события до полезного действия;
- пробуждения без коммита и без смены `work_state`;
- доля повторно переданного контекста;
- успех восстановления после принудительного перезапуска на нескольких этапах против непрерывного прогона той же
  задачи;
- повторные внешние действия и записи устаревшего исполнителя.
