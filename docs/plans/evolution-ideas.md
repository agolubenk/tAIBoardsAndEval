## 2. Хаб переиспользуемых документов (Notebook Hub)

Блокнот кейсов (R-050) остаётся местом разбора: источники, чат, поиск материалов, проработка данных. Хаб — отдельный
слой для **переиспользуемого**: скиллы, агенты, промпты, правила, чанки знаний, шаблоны, геномы ролей, описания.

| # | Идея | Как |
|---|---|---|
| 2.1 | **Артефакт = неизменяемые версии** | semver + хэш содержимого; канал `черновик → канарейка → стабильная → устаревшая`; область (глобально/продукт/лес); происхождение (источник, коммит, автор — агент или человек); зависимости (скилл → правила → чанки); совместимость харнессов (Claude Code, Continue, `.agents`, Windsurf) |
| 2.2 | **Один факт — одно место** | факт/правило — один чанк; скиллы, CLAUDE.md, промпты ссылаются на него; хаб ловит дубли и висячие ссылки — прямой удар по главной потере R4 |
| 2.3 | **Подбор под задачу**: `library_resolve(card, budget)` | минимальный набор артефактов по триггерам и измеренной пользе вместо загрузки всех описаний скиллов (сейчас — обрезка `skillListingMaxDescChars` в геноме) |
| 2.4 | **Геном роли собирается из хаба** | геном = набор `артефакт@версия` + tool-scope; `build.py` рендерит из хаба; замер первого вызова на каждую сборку |
| 2.5 | **Статистика и замкнутый цикл (R-061)** | вызовы, токены, доля переделок по версии, привязка к карточкам через work_state; канарейка новой версии на части реальных карточек и сравнение замером eval |
| 2.6 | **Мост блокнот → хаб** | «продвинуть» ответ/решение из чата блокнота в черновик правила или скилла со ссылками на карточки-доказательства |
| 2.7 | **Семена → уроки** | вырубленный сектор оставляет семена; дистилляция семян даёт урок в хабе (что сработало, что нет, ссылки на брёвна) |
| 2.8 | **Ревью-гейт стабильных версий** | правка стабильной версии — дифф + линзы консилиума + «да» владельца; откат канала — только люди (матрица прав) |
| 2.9 | **Git — экспорт и история** (R-060) | `sync-agent-skills.sh` становится генератором из хаба; расхождение проверяется в обе стороны |
| 2.10 | **Кейсы вместо `.ai/task/`** | brief → recon → гипотезы → evidence → решение — структурированный кейс блокнота (сейчас папки дел живут только на машине); поиск похожих кейсов по секторам; типы «инцидент», «баг», «решение» |

## 3. Эволюционирующий пайплайн

Пайплайн должен улучшать сам себя на трёх уровнях: промпты, сессии, качество. Общий цикл — **вариация → замер →
отбор → закрепление**, всё под контролем владельца и с откатом.

### 3.1 Промпты, геномы, капсулы

- **Всё, что запускает сессию, — версия в хабе**: пусковые промпты ролей (`eval/prompts/launch-*`), `SUCCESSOR-PROMPT*`,
  геномы, шаблоны капсул. У каждой запуска есть ссылка на версии, из которых он собран.
- **Золотой набор задач** (replay): 10–20 реальных закрытых карточек с известным хорошим исходом и стоимостью.
  Новая версия промпта/генома прогоняется на нём (или его части) до канарейки — регресс видно до прода.
- **Фитнес-функция** = $/PR, первый вызов, средний контекст, доля PR без доработок, найденные ревью дефекты. Версия
  проходит в стабильную, только если фитнес лучше и ни одна метрика качества не хуже (принцип «не оставлять на
  прежнем уровне»).
- **Источник вариаций**: наблюдения `task-observer` (`.claude/skill-observations/`), ретро после волны, находки
  ревью, отчёты `session-report` — превращаются в черновики изменений артефактов, а не в заметки в чате.
- **Ретро волны — автоматом**: после каждой волны сессий — отчёт eval (wake anatomy, context audit, стоимость по
  ролям) → карточка «что изменить в промптах/геномах» → черновики в хабе.

### 3.2 Создание и запуск сессий

- **Preflight лаунчера** (`spawn_session.sh`): до `exec claude` проверить и записать — геном и его версия,
  включена ли запись транскрипта, нет ли унаследованных маркеров дочерней сессии (см. §6), лимит окна 5 ч/недели,
  свободная аренда роли. Провал — понятная ошибка, а не тихая деградация.
- **Сессия регистрируется в лесу при старте**: роль, геном@версия, ветка, worktree, метка `t3-<роль>` — work_state
  пишется с первой минуты, наследник подхватывает аренды и журнал (уже есть механика, нужен автоматический старт).
- **Холодный старт только из капсулы**: наследник получает `contextPack` + ссылки, не историю; размер капсулы —
  метрика, растущая капсула — сигнал на дистилляцию.
- **Ротация по сигналу, а не по ощущению**: порог контекста (хук `context-threshold`), лимиты, ночной режим Нерва;
  Нерв сам предлагает наследника (пункт владельцу), а не ждёт, пока роль заметит.
- **Эфемерные роли только чтения** на дешёвых моделях/внешних движках — с жёстким egress (как рой П9).

### 3.3 Качество

- **Метрики качества рядом с метриками стоимости**: escape rate (дефект найден после мёржа), переоткрытые карточки,
  доля PR с доработкой, flaky-тесты, время от «на ревью» до «да».
- **Каждый инцидент — закон с тестом**: правило в `.claude/rules/` появляется вместе с проверкой (хук, тест, lint),
  иначе оно не закреплено.
- **Калибровка ревьюеров**: консилиум уже учится на вердиктах (`learning.py`) — распространить на линзы ревью PR:
  какая линза находит реальные дефекты, какая шумит; состав линз — по данным.
- **Бюджет ошибок**: рост «Ошибок» балансирует фичи (R-073) — сделать это правилом планировщика, а не ручным решением.

## 4. Loop-сервисы и системы

| Принцип | Сейчас | Развитие |
|---|---|---|
| Цикл без модели — первичен | Нерв (launchd, stdlib) будит сессию только на событие | вынести в Нерв всё, что сейчас поллят сессии: CI, очередь, лимиты, ревью |
| Событие, а не опрос | подписки на PR, тапы Нерва | у каждого loop — источник события; «проверка статуса не вызывает модель» (контракт 2) |
| У цикла есть стоп | — | у каждого loop: максимум тиков, бюджет токенов, условие выхода, «3 пустых проверки — остановись» |
| Сторож сторожа | heartbeat Нерва | внешняя проверка пульса (ops-консоль: молчание агента — алерт) |
| Идемпотентность | `ifVersion` в очереди, `fencingToken` в лесу | ключ идемпотентности у каждого действия цикла; повтор не дублирует |
| Дедупликация | — | одно событие — одно пробуждение одной роли, даже если пришло из GitHub, очереди и Нерва |
| Наблюдаемость | журнал Нерва append-only | журнал тиков с причиной пробуждения и стоимостью — вход для wake anatomy |

Инструменты Claude Code для циклов, которые стоит свести в один регламент: `/loop` и `ScheduleWakeup` (самотемп),
cron-задачи и `send_later` (расписание), `Monitor` (ожидание условия), подписки на PR (события), фоновые Bash/агенты
(уведомление по завершении). Вопрос — в §5.

## 5. Вопросы: лучшие практики Claude Code и методологии

Ответ на каждый вопрос — замер или ссылка на документацию с датой; принятый ответ становится правилом/скиллом.

### Контекст и стоимость

1. Когда выгоднее `/compact`, а когда наследник из капсулы? Порог в токенах и в «качестве» (ошибки после сжатия)?
2. Как упорядочить системный контекст (CLAUDE.md, правила, скиллы, MCP) для максимального попадания в кэш промптов
   (TTL 1 ч) и минимума холодных перезаписей ($8/M)?
3. Сколько стоит каждый слой L1: CLAUDE.md, правила без `paths:`, список скиллов, описания MCP-инструментов? Что
   вынести в `paths:`/подбор по задаче?
4. Какие инструменты и плагины роли реально используют (по транскриптам) — что отрезать геномом без потерь?
5. Выход — самая дорогая статья ($20/M): какие ответы и отчёты можно сократить шаблоном без потери смысла?

### Хуки, правила, скиллы

6. Какие хуки подмешивают контекст «не туда» (R4-PLAN) и как это измерить: `additionalContext` по событиям и его

7. Хук — fail-open или fail-closed: где какой и с каким таймаутом?
8. Как оценивать скилл: срабатывание по описанию (ложные/пропущенные), польза, стоимость — `skill-creator` eval?
9. Правило без теста — сколько их и какие стоит закрепить проверкой?

### Субагенты, модели, режимы

10. Когда субагент экономит (свежий короткий контекст), а когда дороже (бриф + отчёт + потери передачи)? Порог?
11. Модель по роли: Opus/Sonnet/Haiku, effort, fast mode — карта «роль → модель» по фитнесу, а не по привычке.
12. Fork vs свежий агент vs workflow: критерии выбора и их цена.
13. `auto mode`: какие действия в нём безопасны для роли, какие должны оставаться под подтверждением?

### Сессии и окружение

16. Worktree на роль/задачу: изоляция зависимостей, кэшей сборки, MCP (Serena индексирует копию) — регламент.

## 7. Что ещё

- **Карта стоимости в реальном времени**: счётчик токенов на задачу (уже в card_meta `tokens`, `costUsd`) → дашборд
  по ролям и секторам; аномалия (задача дороже медианы ×3) — пункт Нерву.
- **Бюджетный планировщик**: дневной план консилиума учитывает остаток окна 5 ч и недельной квоты, а не только
  приоритеты.
- **Реестр фактов**: числа и пути, которые повторяются в документах (метрики, порты, адреса), — один источник,
  документы ссылаются; `docs_linkcheck` расширить до проверки фактов.
- **Безопасность хаба**: egress-фильтр роя (секреты, PII, маскирование) — на всё, что хаб и блокнот отдают внешним
  моделям.
