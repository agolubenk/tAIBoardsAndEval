## Откуда сигналы

Уже есть:
- **backend `/metrics`** (`apps/backend/src/modules/metrics/metrics.controller.ts`):
  - `hr_helper_bullmq_{waiting,active,failed,delayed}_total{queue,class}`;
  - `hr_helper_http_requests_total{method,route,status}` и `hr_helper_http_request_duration_seconds`;
  - `hr_helper_telegram_subscriptions_active` и `hr_helper_telegram_event_last_received_timestamp_seconds`.
- **SM `/metrics`** (`apps/telegram-sessions/src/session/metrics.service.ts`):
  - `telegram_session_evictions_total{pod_id}`;
  - `telegram_rpc_duration_seconds{method,pod_id}` — без метки исхода.
- **Встроенные правила консоли Ops** (`infra/ops-console/server/alerts/builtin.ts`): CPU, память, диск, 5xx nginx,
  контейнер остановлен или unhealthy, перезапуски, молчание агента, недоступность сайта, TLS, упавший деплой.
- **Бизнес-метрики агента** — `BUSINESS_CMDS` (`infra/ops-console/agent/hrh-business.sh`). Одна команда — одно число:
  только агрегаты, только чтение, с таймаутами. В консоли такое число становится метрикой `biz_<ключ>`, и на него
  заведено обычное правило `host_metric`.

Метрики приложения скрипт берёт изнутри контейнеров: `/metrics` backend и SM — через `docker exec` и `fetch` на
`127.0.0.1`, Postgres — через `psql` в контейнере базы с `default_transaction_read_only` и `statement_timeout=5s`,
ответы API Telegram — из журнала nginx (`docker logs`). В сеть стека агент не ходит, учётные данные базы на хосте не
хранятся. Выселения сессий считаются за последний час по истории значений счётчика. История лежит в
`/var/lib/hrh-ops/tg_evictions`: это `StateDirectory` юнита агента, единственное место, куда агенту можно писать.

Сбой чтения не выдаётся за ноль. Команда, которая упала (код выхода не 0, не число, таймаут 20 с), в метрики не
попадает: агент (с версии 1.3) присылает её имя в `businessFailed`. Две такие подряд поднимают алерт «Бизнес-метрики
не считаются» с именами команд в фактах. Без него P0-правило молча перестало бы видеть свою метрику.

## SLO и алерты

Агрегаты ниже — без персональных данных: только счётчики.

**Замер.** Бизнес-метрики агент считает раз в `BUSINESS_INTERVAL_SEC = 300` с, а отчёт шлёт каждые 15 с и повторяет в
нём последний замер. Вместе со значениями агент присылает время замера (`businessAt`), и консоль оценивает правила
`biz_*` только на новом замере (`server/agents/ingest.ts`). Поэтому «2 замера подряд» — это два разных замера,
≈ 5–10 минут, сколько бы отчётов их ни повторило. Пропуск (метрики нет в замере) обнуляет серию. Закрытие
симметрично: столько же нормальных замеров подряд, алерт не дребезжит. В тексте алерта, на странице правил и в
редакторе правила порог показан в замерах. Агент до 1.3 времени замера не шлёт — его метрики P0 консоль не оценивает
вовсе: их пороги заданы в замерах, а не в отчётах.

**«Два замера» таблицы 16.10 писались при замере раз в час.** Для мгновенных значений (застрявшие записи, доля
ошибок, покрытие) смысл не меняется. Для счётчиков за окно (сбоев за час, сбоев токена за 6 ч) «два часовых замера»
— это «держится дольше часа». При замере раз в 5 минут это 13 замеров. Одиночный сбой, который проходит со
следующей попыткой, не будит; закрывается такой алерт тоже через час нормальных замеров, то есть около 2 часов после
последнего сбоя. Если нужно строже — порог правила меняется на странице правил консоли (например, «больше 1 сбоя
за час, 2 замера»: второй сбой в течение часа будит через 5 минут).

**Объект алерта P0 — подсистема** («STT · vps», «Telegram · vps», «Huntflow · vps»). Критичный алерт открывает
инцидент, а инциденты собираются по объекту. Поэтому сбой Huntflow не втягивает в свой инцидент застрявшие записи
и заполненный диск сервера.

### Расшифровка встреч (STT)

| Что | Как считаем | SLO (старт) | Алерт |
|---|---|---|---|
| Записи без сбоя распознавания | за 7 дней: `failed` / (`ready` + `failed`) в `tenant_meeting_recordings`; отказы по типу файла не в счёт | ≥ 98 % | `biz_stt_failed_1h` — сбоев **распознавания** за час: `failed` с текстом «Распознавание не удалось/прервалось» (контракт закреплён тестом `meeting-transcription.service.spec.ts`). Скачивание по ссылке и приём частей падают со своими текстами — не в счёт. > 0 держится дольше часа (13 замеров) — `warning`; > 3 — `critical` с первого замера, повтор раз в час |
| Застрявшие записи | `processing` дольше 4 ч (файлы больше 1,5 ГБ, PS-03, — 6 ч), но не меньше двух длительностей записи, если она известна: whisper на CPU идёт примерно со скоростью звука, и 5,5 ч звука законно распознаются дольше 4 ч. Во время распознавания строка не обновляется; каждый повтор задачи заново ставит `processing` | 0 | `biz_stt_stuck` > 0 — `critical` с первого замера, повтор раз в 2 ч. Подсказка алерта — как вернуть запись |
| Записи без задачи | `uploaded` старше 30 минут сверх числа задач `waiting` + `delayed` очереди `meeting-stt`: у каждой `uploaded` должна быть задача. Сбой постановки только пишется в лог, а Redis на проде без сохранения | 0 | `biz_stt_orphaned` > 0 два замера подряд — `warning` |
| Очередь распознавания | `hr_helper_bullmq_waiting_total{queue="meeting-stt"}`. Серии нет, когда backend не достучался до Redis: это сбой чтения, а не 0 | не растёт 30 мин | `biz_stt_queue_waiting` > 5 семь замеров подряд (≈ 30 минут) — `warning` |
| Sidecar'ы whisper и diarization | контейнер жив | 99,5 % | встроенные «Контейнер остановлен / unhealthy» — уже есть |

### Telegram

| Что | Как считаем | SLO (старт) | Алерт |
|---|---|---|---|
| Ошибки API Telegram (платформа) | доля 5xx, **кроме 503**, среди ответов nginx на `/api/v1/integrations/telegram/*` за 5 минут: backend упал, не отвечает или падает с ошибкой кода. Считается, только если ошибок не меньше 3 и они хотя бы в 3 разных минутах окна. Первые 8 минут после запуска backend или SM — 0: 502 деплоя не будят. Упавший и не поднявшийся backend так не прячется — время его запуска не меняется. Счётчик backend `hr_helper_http_requests_total` для этого не годится: он не видит ответов, брошенных исключением, и 502 при упавшем backend | < 2 % | `biz_tg_api_5xx_pct` > 5 % два замера подряд — `critical`, повтор раз в час. Срабатывает на устойчивый сбой — ошибки не меньше 6 минут из 10; на прогоне журнала nginx за 36 ч прода — ни одного ложного срабатывания, против 12–19 % шанса на каждый деплой без этих условий |
| Отказы Telegram по аккаунтам | доля **503** среди тех же ответов, с теми же условиями. 503 backend отдаёт на circuit breaker SM, FLOOD_WAIT, конфликт владения сессией и таймаут MTProto — это проблема одного-двух аккаунтов, а не платформы. С #227 отказ пула SM в чтениях тоже даёт 503 вместо пустого ответа: один аккаунт в circuit breaker даёт поток 503 только от себя. nginx сам 503 не отдаёт (`limit_req_status 429`) | — | `biz_tg_api_503_pct` > 5 % два замера подряд — `warning`. Отдельно от critical по решению ревью 20.10: падение SM целиком и так видно по правилам контейнера и по живым подпискам |
| Шторм выселений сессий | выселения за последний час: сумма приростов `telegram_session_evictions_total` по истории замеров. Серии нет до первого выселения — это 0 | < 10 в час | `biz_tg_evictions_1h` > 30 два замера подряд — `warning` (так выглядел инцидент 25.09). На 1–2 аккаунтах шторм виден слабо: circuit breaker SM даёт одно выселение на волну. Точный сигнал — счётчики открытий circuit breaker и зависаний RPC в SM, раздел «Что осталось» |
| Живые realtime-подписки | `hr_helper_telegram_subscriptions_active` (backend) против `telegram_active_sessions` (живые клиенты пула SM). Знаменатель — пул, а не таблица сессий: отозванная сессия остаётся строкой в `telegram_user_sessions`, но клиента в пуле у неё нет. Первые 12 минут после запуска backend — 100: подписки восстанавливает крон раз в 10 минут, деплой — не авария | ≥ 95 % | `biz_tg_subs_coverage_pct` < 80 % два замера подряд (5–10 минут) — `warning`. Не 15 минут, как в таблице 16.10: клиента без подписки SM выселяет через 15 минут простоя, и покрытие снова становится 100 %, хотя причина могла остаться. При пуле до 4 клиентов один клиент без подписки — уже < 80 %: на проде сейчас 1 сессия, и её сломанный realtime — это 100 % пользователей Telegram. Истории этих значений нет, прогнать по прошлому нельзя — порог пересматривается через две недели вместе с остальными |
| Отказы по лимиту (429) | 429 nginx в минуту — после #180 | < 1 % запросов | нужна метрика агента `nginx_429_rpm` — рядом с `nginx_5xx_rpm` |

### Очереди

| Что | Как считаем | SLO (старт) | Алерт |
|---|---|---|---|
| Заполненность Redis очередей | `used_memory` от `maxmemory` у `redis-queue` (`redis-cli info memory` в его контейнере). ## Включение на сервере

Делает владелец после деплоя #226. Команды — пункт очереди владельца `s-p0-slo-agent`, откат — его второй блок.
До деплоя новые метрики и правила молчат: старый агент ключей P0 не шлёт, это тишина, а не ложные алерты.
Порядок выката: мёрж и деплой консоли → `s-p0-slo-agent` → проверка.

1. Охрана: в запущенной консоли есть правила v3 (строка `biz_stt_orphaned` в её сборке). Деплой не закончился или
   упал — команда отказывает, ничего не меняя. В чекауте `/opt/hr-helper` — агент 1.3 или новее.
2. Бэкап `/opt/hrh-ops`, `/etc/hrh-ops-agent.env` и юнита — один раз на выкат: время бэкапа помнит маркер
   `/var/backups/hrh-ops-slo.ts`, повторный запуск бэкап не перетирает.
3. `install.sh` ставит агента 1.3 (время замера и упавшие команды), скрипт и юнит со `StateDirectory`.
4. В `/etc/hrh-ops-agent.env` — `BUSINESS_INTERVAL_SEC=300` и `BUSINESS_CMDS` с 13 ключами: `companies`, `users`,
   `db_size_mb`, `stt_failed_1h`, `stt_stuck`, `stt_orphaned`, `stt_queue_waiting`, `tg_api_5xx_pct`,
   `tg_api_503_pct`, `tg_evictions_1h`, `tg_subs_coverage_pct`, `hf_refresh_rejected`, `hf_refresh_errors_6h`.
   Каждая команда — `/opt/hrh-ops/hrh-business.sh <ключ>`. Ключ Redis очередей сюда не входит — см. «Очереди».
5. Перезапуск агента. Не поднялся — команда печатает журнал и предлагает откат.

Проверка (то, чего у старой консоли нет): на странице правил есть «Бизнес-метрики не считаются»; через 5–6 минут на
странице сервера — метрики `biz_stt_*`, `biz_tg_*`, `biz_hf_*` и `biz_failed` = 0; после первого замера в
`/var/lib/hrh-ops` — файл `tg_evictions`.

Откат проверяет всё до первого изменения: маркер есть, бэкап полный, в нём прежний агент. Текущее состояние
откладывается в `*.pre-rollback-*`, так что и откат обратим. Логика выката и отката прогнана в песочнице: откат до
выката отказывает, повторный выкат не перетирает бэкап, повторный откат отказывает.

Цена раз в 5 минут: 7 запросов `psql`, 5 запусков `node` для `/metrics` внутри контейнеров, два чтения журнала
nginx за 5 минут и 5 `docker inspect`. Таймауты — 10–20 с. Прогон всех ключей на проде 19–20.10 под той же
песочницей systemd, что у агента, вернул числа. Сломанный контейнер даёт код выхода 1 и пустой вывод — это
`businessFailed`, а не 0.

## Что осталось

Известные пробелы: что метрики P0 не видят или видят с задержкой.

- **Шторм сессий на 1–2 аккаунтах.** Circuit breaker SM даёт одно выселение на волну, поэтому шторм вроде 25.09 на
  одном аккаунте не набирает 30 в час. Нужны счётчики SM `telegram_session_circuit_open_total` и
  `telegram_rpc_watchdog_timeouts_total` (без метки пользователя) — это правка SM, карточка в Notion «Задачи».
- **Переименование записи** меняет `updated_at`, и старый сбой распознавания снова попадает в окно «за час».
  Переименование есть только в API, без интерфейса.
- **Потери при приёме** (не сохранились аудио-чанки, не поставилось скачивание) — потеря данных, но в P0 не
  считается: тексты другие. Предложение — отдельный ключ, карточка в Notion «Задачи».
- **Зависший whisper** ограничен таймаутом 90 минут и с 22.10 виден как сбой распознавания через 90 минут: после
  таймаута задача не повторяется (`docs/ops/stt-whisper-models.md`, «Процессор»). Или как «Контейнер unhealthy».
- **Занят ≠ завис** (с 22.10, после #241) — только для пакетных сервисов из списка правила «Контейнер unhealthy»
  (по умолчанию `diarization,whisper`).
  - Если такой контейнер не отвечает на healthcheck, а его CPU не ниже порога правила (по умолчанию 20 % ядра), он
    считает задачу — например, диаризация во время «Переразметить». Это не тревога: в ленте отметка 🟡 в начале
    эпизода и 🟢 в конце, с длительностью и пиком CPU.
  - Тревога — unhealthy при простое (CPU ниже порога дольше 10 минут) или эпизод дольше 90 минут: зацикливание с
    CPU 100 % не молчит. 10 минут — запас на загрузку файла и модели перед расчётом и на флип docker в healthy.
  - Эпизод закрывается, когда healthcheck проходит 3 минуты подряд: мигание статуса на грани таймаута — одна задача,
    одна отметка, и потолок 90 минут не обнуляется. Пропуски отчётов агента потолок тоже не сбрасывают; новый эпизод
    без закрытия прежнего — только если агент молчал дольше 90 минут. Строки эпизодов старше суток убирает
    ежедневная уборка консоли.
  - В списке — имена compose-сервисов (`whisper`, а не образ `speaches`). Запятая в поле «метрика» разрешена только у
    этого правила: у правила по метрике это опечатка, API её отклоняет.
  - Порог выбран без истории — у контейнеров консоль хранит только текущий CPU. Пересмотреть по первым отметкам 🟢.
  - У остальных сервисов (backend, Session Manager, wiki, OnlyOffice, консоль) unhealthy при высоком CPU — авария,
    тревога сразу.
- **Redis на проде** — `allkeys-lru` без сохранения: очереди BullMQ теряются при перезапуске Redis и могут
  вытесняться при нехватке памяти. Метрика «Записи без задачи» это заметит, но причина — прод-конфиг, решение
  владельца `d-redis-queues`.

1. Закрыть пробелы:
   - счётчик backend `hr_helper_http_requests_total` пропускает ответы, брошенные исключением: перехватчик

     5xx Telegram считаются по nginx. Нужна запись и в ветке ошибки; карточка в Notion «Ошибки»;
   - метка исхода у `telegram_rpc_duration_seconds`;
