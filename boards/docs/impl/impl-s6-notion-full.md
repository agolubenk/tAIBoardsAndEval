## Зачем

Владелец просит перенести HR Helper / Lavaeon из Notion «в полном объёме и с полными данными». Сейчас зеркало
(`apps/api/src/import/notion-mirror/`) берёт две базы и теряет шесть видов данных (таблица ниже). Пока идёт переход,
главный — Notion (R-081): поток только Notion → t-boards, правка зеркальных полей на доске перезаписывается.

## Фаза 1 — без нового хранилища

1. **Все базы (G8).** `mirror-setup.sh` спрашивает у интеграции `POST /v1/search {filter: database}` все базы, к
   которым её пустили, и пишет их в `NOTION_MIRROR_DATABASES` (Задачи и Ошибки первыми). Проект на базу, как сейчас.
   Новую базу владелец подключает в Notion («Connections») и перезапускает `mirror-setup.sh`.
2. **Пересинхронизация меток и связей (G5).** Для изменённой карточки метки из набора меток Notion этой базы
   приводятся к значению в Notion; метки, заведённые на доске (не из набора Notion), не трогаются. Связи между двумя
   зеркальными карточками приводятся к Notion: недостающие добавляются, пропавшие в Notion удаляются. Связь
   зеркальной карточки с карточкой доски (не из Notion) не трогается.
3. **Пропавшие страницы (G6).** После полного чтения базы карточка, чья страница не пришла, архивируется с причиной
   `terminalReason = «удалена или в корзине Notion»`. Вернулась — разархивируется. Предохранитель: если за прогон
   пропадает больше `max(5, 10 %)` зеркальных карточек базы, архивация пропускается, в отчёт идёт предупреждение
   (так сбой выдачи или отозванный доступ не закроют всю доску).
4. **Комментарии (G2).** `GET /v1/comments?block_id=<page>` (нужна способность интеграции «Read comments»). Notion не
   меняет `last_edited_time` страницы от комментария, поэтому опрос: новые и изменённые страницы — каждый прогон;
   все страницы базы — один раз в сутки (прогон 08:07). Идемпотентность — по id комментария Notion в таблице связи
   `notion_comment_link (notion_comment_id PK, comment_id, task_id)`; правка текста в Notion обновляет комментарий.
   API отдаёт только открытые обсуждения — закрытые в Notion не появятся (ограничение Notion, пишется в отчёт).
   Автор — участник по email, иначе «Notion: <имя>» в тексте.
5. **Свойства (G7).** formula и rollup — значением (число, дата, текст, массив — через «, »); files — имена и ссылки
   (сами файлы — фаза 2); relation — ещё и заголовками целей текстом; created/last_edited time и by; place;
   verification. Всё в `extraFields` (R-024, видно в карточке, `card_meta`).
6. **Блоки (G4).** table → markdown-таблица; column_list/column → подряд; bookmark, embed, link_preview → ссылка;
   equation → `$$…$$`; synced_block → дети оригинала; child_page/child_database → ссылка с заголовком;
   file/pdf/video/audio → ссылка с пометкой «файл Notion» (до фазы 2).
7. **Отчёт.** В отчёт прогона: комментарии (новые, изменённые), архивировано, разархивировано, пропуск
   предохранителем, неизвестные типы свойств и блоков — счётчиками.

## Фаза 2 — связи между базами и файлы

1. **Связи между базами (G1).** `mapping.ts` сохраняет нерешённые цели связи как id страниц. После записи всех баз —
   проход по продукту: id страницы → карточка через `card_meta.notion_page_id` → связь `related` (свойства «Parent» и
   «Subtasks» — по-прежнему `subtask`) между проектами одного продукта. Граница продукта (R-002): связи наружу продукта
   не пишутся.
2. **Файлы (G3).** Свойство files и блоки image/file/pdf/video скачиваются в хранилище t-boards (TB-020) в тот же
   прогон (ссылка живёт час), дедупликация по пути файла в Notion; лимиты — 25 МБ на файл, 500 МБ на прогон, сверх —
   ссылка и предупреждение. Ссылки в описании переписываются на файл доски. Хранилище входит в бэкап.
   **Развилка владельцу:** том на VPS (просто, растит бэкап) или S3-совместимое (уже поддержано kaneo, нужен ключ).

## Ресурсы

- Notion: 3 запроса/с в среднем. Прогон = страниц/100 (выдача) + изменённые × страницы блоков + комментарии
  (изменённые; раз в сутки — все). На ~800 страниц суточный прогон ≈ 800 запросов ≈ 5 мин, обычный — секунды. Lease
  прогона 60 мин — хватает.
- VPS: базы читаются по одной, страницы — потоком по 100; файлы — по одному, без буфера в памяти.
- Доска: тяжёлое (комментарии, файлы) не входит в выдачу доски — только в карточку. Вес ответа доски не растёт.

## Приёмка

1. Тесты: на каждый пункт фазы — юнит-тест маппинга и интеграционный тест записи (PostgreSQL), включая предохранитель
   и повторный прогон без изменений (+0 везде).
2. Selftest: прогон на фикстуре из 3 баз с комментариями и пропавшей страницей.
3. Живой прогон (`s-tb-mirror`): по каждой базе reconcile — 0 расхождений; число комментариев и связей сходится с
   Notion; два прогона подряд — второй без изменений.
